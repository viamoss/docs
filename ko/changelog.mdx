# 변경 이력

Moss SDK(`@viamoss/moss-sdk`)와 Moss 대시보드에서 고객에게 드러나는 주요 변경
사항입니다. v0.13.0부터 SDK 버전은 Moss 플랫폼 버전을 따릅니다.

## 0.16.19 — 2026-11-03

### 추가

- **SDK 분석 이벤트.** 프로바이더 설정에 `onEvent`를 전달하면 Moss 사용 내역을
  분석 도구로 보낼 수 있습니다. 예:
  `onEvent: (e) => window.analytics?.track(e.name, e.properties)`. 각 이벤트는
  `{ name, properties }` 형태이며, 이름은 Segment의 "Object Action" 형식을
  따릅니다. 이벤트 12종이 채팅, 질문과 답변, 오류, 가이드 플랜, 피드백, 지원 티켓을
  다룹니다. 전체 목록은 `MOSS_EVENT_NAMES`에 있고, 이벤트별 속성은 SDK README에
  정리되어 있습니다. `Moss Question Asked`에는 `source: 'user' | 'host'`가 담기며,
  `'host'`는 `askMoss()`로 보낸 질문을 뜻하고 요청이 전송되는 시점에 한 번만
  집계됩니다. 질문 텍스트는 `eventQueryText`를 `'include'`나 함수로 설정하지 않는 한
  포함되지 않습니다. 핸들러에서 예외가 발생하면 로그만 남기고 무시하며, `onEvent`를
  설정하지 않으면 아무것도 달라지지 않습니다.
- **필요할 때만 Moss 시작하기.** 사용자가 요청할 때만 Moss를 마운트하는 호스트를
  위해, `@viamoss/moss-sdk/start`(React 미포함)의 `shouldStartMoss()`가 페이지 로드
  시점에 Moss를 마운트해야 하는지 알려 줍니다. 페이지가 바뀌기 전 이 탭에서 채팅이
  열려 있었을 때, 이 탭에서 가이드가 진행 중일 때, 이 탭에서 `askMoss()` 질문이 대기
  중일 때, 또는 사용자가 진행한 가이드 단계가 이 페이지에서 이어지기를 기다릴 때(기본
  30초) true를 반환합니다. true이면 Moss를 마운트하고, 채팅을 직접 열거나 토글하지
  마세요. `stability.afterReload.enabled: true`가 필요하며,
  `stability.afterReload.pendingTTL`을 설정했다면 같은 값을 전달하세요. 브라우저
  스토리지만 읽고 예외를 던지지 않습니다.
- **질문과 함께 Moss 열기.** `@viamoss/moss-sdk/start`에서도 제공되는
  `askMoss(question)`는 자체 어시스턴트나 도움말 위젯의 질문을 Moss에 넘깁니다.
  Moss는 새 채팅을 시작해 열고, 그 질문을 사용자의 첫 메시지로 보냅니다. 반환값은
  `{ accepted: true, id, queued }` 또는
  `{ accepted: false, reason: 'empty' | 'unavailable' }`이며 예외를 던지지 않습니다.
  `queued: true`이면 30초 안에 채팅을 열지 않은 상태로 Moss를 마운트하세요(`ttlMs`로
  조정 가능). Moss와 같은 창, 같은 오리진에서 호출하고, 채팅은 토글이나
  `[data-moss-trigger]` 클릭이 아니라 `openChat()`으로 여세요. 질문이 대기 중일 때
  토글하면 채팅이 닫히고 질문이 버려집니다. 진행 중인 채팅이나 가이드는 New chat을
  눌렀을 때와 같은 방식으로 종료됩니다.
- **Vertex AI `eu`, `us` 멀티 리전.** `GOOGLE_AUTH_MODE=vertex`와
  `GOOGLE_CLOUD_LOCATION=eu`로 설정하면 채팅, `gemini-embedding-2` 임베딩, 이미지
  주석이 모두 `aiplatform.eu.rep.googleapis.com`으로 전송됩니다. `us`도 같은
  방식으로 `aiplatform.us.rep.googleapis.com`을 사용합니다. 두 백엔드와 워커에 같은
  위치를 설정하고, 세 곳 모두에서 해당 호스트로 나가는 트래픽을 허용하세요.
  `global`이나 단일 리전의 Vertex는 이전과 같은 호스트로 같은 요청을 보냅니다.
- **OIDC 세션 갱신.** `moss-dashboard-oidc` 컨테이너에 `OIDC_REFRESH_TOKENS=true`
  (기본값은 꺼짐)를 설정하면 대시보드가 리프레시 토큰으로 사용자의 ID 토큰을
  갱신하므로, 세션이 IdP의 ID 토큰 수명(Okta 기준 60분)보다 오래 유지됩니다. 먼저
  IdP에서 Moss 애플리케이션의 Refresh Token grant를 허용하고, Okta 커스텀 인가 서버를
  쓴다면 액세스 정책에서 `offline_access`도 허용하세요. 액세스 정책을 바꾸지 않은
  채 이 설정을 켜면 모든 로그인이 실패합니다.
- **`security.txt`.** 백엔드가 로그인 없이, 모든 서비스 모드에서
  `/.well-known/security.txt`로 RFC 9116 파일을 제공하며, `/security.txt`는 이
  경로로 리디렉션됩니다. 기본 연락처는 `mailto:security@viamoss.ai`이며,
  `SECURITY_TXT_CONTACT`에 `mailto:` 또는 `https:` URI를 설정하면 자체 연락처를
  표시할 수 있습니다.

### 변경

- **이미지 주석 기본 모델.** `ANNOTATOR_LLM_MODEL`을 설정하지 않으면 워커가 low
  thinking의 `gemini-3.8-flash`를 사용합니다. 기존 기본값 `gemini-2.5-flash`는
  2026-10-20에 Google이 지원을 종료했습니다. `gemini-3.8-flash`를 명시한 경우에도
  low thinking으로 바뀌며, 출력 한도는 4,096토큰입니다. 다른 모델은 바뀌지 않습니다.
- **OIDC 로그인.** `OIDC_ADMIN_GROUPS`와 `OIDC_MEMBER_GROUPS` 어디에도 속하지 않는
  사용자는 로그인할 때 Access Denied 페이지를 봅니다. 대시보드를 제공하는 백엔드의
  `OIDC_AUDIENCE`에 OIDC 클라이언트 ID가 없으면 로그인할 때마다 로그인 페이지로
  돌아오므로, 클라이언트 ID를 추가하세요. 업그레이드 전에 로그인한 사용자는 한 번 더
  로그인해야 합니다.
- 두 대시보드 이미지 모두에서 대시보드 토스트가 오른쪽 아래에 표시됩니다. Copilot이나
  Playground의 메시지 입력란, Suggested Content의 저장/취소 바를 가리게 되면 위로
  올라갑니다.
- SDK가 탭마다 채팅과 가이드를 따로 유지합니다. `window.open()`으로 연 탭은 채팅이
  닫히고 가이드가 없는 상태로 시작하며, 새로고침 후 가이드는 실행 중이던 탭에서만
  이어집니다. 가이드 단계가 새 탭을 열면, 원래 탭에서 채팅이 열려 있던 경우 새
  탭에서도 채팅이 열립니다.
- 새로운 선택 설정: 대시보드의 `OIDC_REFRESH_TOKENS`, 백엔드의
  `SECURITY_TXT_CONTACT`. `GOOGLE_CLOUD_LOCATION`에는 `eu`와 `us`도 쓸 수 있습니다.
  Helm 차트의 `values.yaml`에서는 주석 처리된 `ANNOTATOR_LLM_MODEL` 예시만
  바뀝니다.
- 이번 릴리스에는 데이터베이스 마이그레이션이 없습니다.

### 수정

- OIDC 대시보드 세션이 더 이상 ID 토큰보다 오래 유지되지 않습니다. 이전에는 Okta에서
  로그인 후 약 한 시간이 지나면, 대시보드에는 로그인 상태로 표시되면서 모든 API
  호출이 401로 실패했습니다. 이제는 다음 페이지 로드 때 로그인 페이지("Your session
  has expired")로 이동했다가 같은 페이지로 돌아오며, IdP 세션이 유지되고 있으면
  대개 자격 증명을 다시 묻지 않습니다.
- 대시보드가 401 이후 재시도할 때 새 토큰을 요청하며, IdP가 로그인을 거부하면 로그인
  페이지에 그 사실이 표시됩니다.
- `gemini-3.8-flash`에서 `LLM_THINKING=minimal`은 `low`로 전송됩니다. 이전에는 이
  설정으로 보낸 채팅 요청이 모두 400으로 실패했습니다.
- SDK에서 New chat으로 대체된 뒤 채팅 시작이 실패해도, 새 채팅의 메시지 입력란이
  Retry 없이 비활성화된 채로 남지 않습니다.

### 보안

- **API 액션의 사용자 식별.** 설정된 API 액션은 사용자의 회사와 사용자 ID를 대화가
  아니라 서명된 SDK 토큰에서 가져옵니다. 회사는 JWT `metadata` 클레임의
  `company_id`(또는 `companyId`)에서 가져옵니다. 회사 유형 필드(`company_id`,
  `tenant_id`, `organization_id`, `org_id`와 각각의 `X-` 헤더 형식)는 서버가 채우며,
  토큰에 회사 정보가 없으면 이런 필드가 있는 액션은 거부됩니다. `user_id`는 로그인한
  사용자로 채워지고, 다른 사용자를 지정한 호출은 거부됩니다. API 액션을 쓰지 않는
  애플리케이션은 달라지는 것이 없습니다.
- **역할 제한 프로시저.** `allowed_roles`가 지정된 프로시저는 토큰의 `metadata.role`에
  해당 역할이 서명된 사용자에게만 실행됩니다. 호스트가 `role`을 서명하기 전까지 이런
  프로시저는 모든 사용자에게 숨겨집니다. 형식이 잘못된 `allowed_roles` 값은 아무도
  허용하지 않습니다.
- `APP_ENV`가 없거나 비어 있으면 production으로 간주합니다. 이 값을 설정하지 않은
  워커는 텔레메트리에 `production`을 보고하므로, `local`로 필터링하는 대시보드의
  수치가 달라질 수 있습니다.
- 이미지는 최신 베이스 이미지 패키지로 다시 빌드되었으며, 의존성 변경은 없습니다.

### 알려진 문제

- 가이드 하나를 진행하는 동안 Moss가 두 탭에 열려 있으면, 가이드를 실행하지 않는
  탭에서도 `Moss Plan Started`, `Moss Plan Step Completed`, `Moss Plan Finished`가
  발생해 중복 집계될 수 있습니다. 탭이 하나일 때는 정확하게 집계됩니다. 다음
  패치에서 수정됩니다.
- `eu`와 `us`에서는 `gemini-embedding-001`이 지원되지 않습니다. 이 모델로는 수집이
  실패하고, 채팅이 애플리케이션의 지식 기반 없이 답변합니다. 애플리케이션의 임베딩
  모델은 바꿀 수 없으므로, `gemini-embedding-2`로 옮기려면 새 애플리케이션을 만들고
  소스를 다시 수집해야 합니다.
- 차트의 채팅 기본값 `gemini-3-flash-preview`는 `global`에서만 제공됩니다. `eu`나
  `us`에서는 두 백엔드의 `LLM_MODEL_NAME`을 해당 위치에서 제공되는 모델(예:
  `gemini-3.8-flash`)로 설정하세요.
- 분석 채팅, 일일 인사이트 스윕, 모니터 채점, 프로시저 작성, 자가 복구, 세션 평가는
  `GOOGLE_AUTH_MODE`와 관계없이 `LLM_API_KEY`로 Gemini Developer API를 호출합니다.
  `eu`나 `us`에서는 이 호출이 리전 밖으로 나가지 않고 실패하도록 두 백엔드에서
  `LLM_API_KEY`를 비워 두고, 대시보드 백엔드에 `INSIGHT_SWEEP_ENABLED=false`를
  설정하세요.
- Okta가 갱신된 ID 토큰에서 groups 클레임을 빠뜨린다는 보고가 있습니다. 이 경우
  대시보드는 갱신된 토큰을 사용하지 않으며, 세션은 여전히 한 시간마다 종료됩니다.
  `OIDC_REFRESH_TOKENS`는 스테이징 환경에서 먼저 확인하세요.

## 0.16.16 — 2026-11-02

### 변경

- **지원 티켓: 카드 먼저.** 호스트 위임 방식에서 티켓이 필요해지면, Moss는 제목과
  설명이 갖춰지는 즉시 편집 가능한 티켓 카드를 보여 줍니다. 채팅에 티켓 내용을 풀어
  쓰거나, 채팅에서 확인을 요청하거나, 이메일 주소 같은 연락처를 묻지 않습니다.
  사용자가 카드를 제출하기 전에는 아무것도 등록되지 않으며, Moss는 등록이 확인된
  경우에만 티켓이 등록되었다고 안내합니다. 채팅에서 확인을 요청하는 프로시저 문구는
  삭제하세요.
- **티켓 필드는 사용자가 말한 내용으로만 미리 채워집니다.** 두 등록 방식 모두에
  적용되며, 티켓 필드에 없는 항목의 값은 버려집니다. 카드에 표시된 필드는 사용자가
  모두 수정할 수 있습니다. 영향도는 제목, 설명, 사용자 메시지에 담긴 사용자 본인의
  표현을 따르므로, 요청 유형 때문에 영향도가 올라가지 않습니다. 사용자가 장애를
  알리거나, 업무가 멈췄다거나 모두가 영향을 받는다고 말하면 Critical로 미리
  채워집니다. 그런 신호가 없으면 호스트 위임 카드는 영향도를 비워 두고, 직접 등록
  티켓은 Medium을 기본값으로 씁니다.
- **티켓 접수(Filing) 스위치 하나로 티켓을 켜고 끕니다.** Configure > Integrations >
  Zendesk의 Filing 행에서 Off로 두면 모든 프로시저, 기본 응답, 진행 중인 티켓 요청,
  제출 시점에 적용되며, 직접 등록 연결도 더 이상 드라이런하지 않습니다. 연결이
  일시 중지(Paused)되었거나 달리 등록할 수 없는 동안에도 프로시저는 티켓을 제안하지
  않습니다. 이 스위치는 관리자만 보고 바꿀 수 있습니다.
- **업그레이드 전에 각 Zendesk 연결의 Filing 설정을 정하세요.** Off로 표시되는데
  프로시저가 여전히 티켓을 제안하던 연결은 업그레이드 시점부터 제안을 멈춥니다.
  호스트 위임 연결은 업그레이드한 뒤에 Live로 전환하세요. 이전 릴리스에서는 Live가
  사용자의 이메일 주소를 묻는 기본 응답의 티켓 제안도 함께 켜기 때문입니다. 기본
  응답에서 티켓을 제안하지 않게 하려면 애플리케이션 설정에서
  `procedures.default_reply_policy`를 `false`로 설정하세요. 이 경우 기본 응답의
  지원팀 문의 안내도 함께 빠집니다. 직접 등록 연결의 Zendesk 양식이 요청자의 역할을
  필수로 요구한다면, Ticket intake 페이지에서 해당 필드에 고정 값을 지정하거나 티켓
  프로시저가 역할을 묻도록 하세요.
- SDK 0.16.16은 결과의 `ticketId`를 `string | number` 타입으로 받아 텍스트로
  전송합니다.
- `LLM_CLIENT_TYPE`에 더 이상 `baseten`을 쓸 수 없으며, 프로바이더 장애 조치 설정인
  `LLM_AUTOROUTER_ENABLED`와 `LLM_FALLBACK_PROVIDERS`는 무시됩니다. 백엔드는
  `LLM_CLIENT_TYPE`에 지정된 프로바이더 하나만 사용합니다.
- Bearer 로그인에서 발생한 트래픽 로그 감사 이벤트는 `auth_method`를 `clerk_jwt`
  대신 `jwt`로 기록합니다. 기존 이벤트는 `clerk_jwt`로 남아 있으므로, 이 값을 쓰는
  SIEM 필터를 업데이트하세요.
- 워커가 DTD를 선언한 사이트맵을 거부합니다.
- 0.16.7에서 업그레이드하면 0.16.8부터 0.16.15까지가 함께 적용되며, 이 가운데
  데이터베이스 마이그레이션이나 Helm values 변경이 있는 릴리스는 없습니다.
- 이번 릴리스에는 데이터베이스 마이그레이션이 없습니다. Helm 차트의 `values.yaml`은
  주석만 바뀝니다.

### 수정

- 백엔드의 응답이 기록되기 전에 같은 카드를 다시 제출하면(예: 응답이 유실된 경우)

  사용자에게는 티켓이 하나만 생깁니다. 값이 바뀐 재제출은 여전히 거부됩니다.
- 백엔드가 `ticketId`를 숫자나 텍스트로 반환할 수 있으며, 정수인 `errorCode`나

  번들과 다르게 기록되는 모든 값, 다시 입력해야 할 항목 체크리스트가 표시됩니다.
  대시보드 내보내기는 기본적으로 전체 번들을 생성하며, 설정만 담은 번들도 계속
  사용할 수 있습니다. 가이드 플로우는 번들에 포함되지 않습니다. 엔드포인트는
  `GET /api/v1/applications/{id}/export`와
  `POST /api/v1/applications/import?dry_run=true`입니다.
- **대시보드에서 관리하는 외관 컨트롤(1차).** 새로운 테마 슬라이스와 푸터 배경
  색조를 대시보드에서 편집할 수 있습니다. SDK는 대시보드에 저장된 값을 리프
  단위로 호스트 prop 위에 적용하므로, 우선순위는 프리셋, 호스트 prop, 대시보드
  값 순입니다. 대시보드 테마 값을 보려면 호스트가 SDK를 0.16.6으로 업그레이드해야
  합니다.
- SDK 채팅 창을 헤더 전체와 창 가장자리에서 드래그할 수 있습니다.
- 대시보드 토스트에 닫기 버튼이 추가되었고, 오류 토스트는 닫을 때까지 유지됩니다.

### 변경

- 설정 슬라이스의 마지막 리프를 지우면 빈 객체를 저장하는 대신 슬라이스 자체가
  제거됩니다.
- SDK 패키지 tarball에 더 이상 소스맵이 포함되지 않으며, 공개 README와 패키지
  메타데이터가 추가되었습니다.
- 분리 배포 환경의 업그레이드 순서: 백엔드, 대시보드, SDK 순입니다.
- 애플리케이션 정리(prune) 스크립트가 애플리케이션 소유 테이블 전체를 다루고,
  저장된 DOM 스냅샷 객체를 제거하며, 설정된 데이터베이스 스키마를 통해 테이블을
  찾습니다. 애플리케이션 간 참조가 감지되거나 테이블 수를 셀 수 없으면 실행을
  거부합니다.
- 이번 릴리스에는 데이터베이스 마이그레이션이 없습니다.

### 알려진 문제

- 링크만 저장된 푸터의 경우 공개 설정 엔드포인트가 `enabled: false`를 반환합니다.
- 설치 환경에 같은 이름의 애플리케이션이 이미 있는 조직으로 가져오기하면
  거부됩니다. 현재 애플리케이션 이름은 설치 환경 단위로 고유합니다.

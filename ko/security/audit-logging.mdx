감사 로그는 Moss에서 누가 무엇을 바꿨는지 기록합니다. 설정, 서명 키, 지식, 데이터 삭제, API 로그 읽기 등이 사람, 시각, 출발 주소, 결과와 함께 남습니다. 관리자는 **구성 > 감사 로그**에서 읽고, JSON이나 CSV로 내보내거나, 읽기 전용 키로 고객의 도구에 가져올 수 있습니다. Moss는 모든 애플리케이션의 감사 이벤트를 기록하며, 이를 끄는 스위치는 없습니다. 이벤트는 기본적으로 365일 동안 보관합니다.

<Info>
    감사 로그는 **API 로그**와 다릅니다. API 로그는 애플리케이션 API 호출의 요청과 응답을 담으며, 기본적으로 꺼져 있습니다. 자세한 내용은 [API 로그](/ko/dashboard/analytics)에 있습니다. 아래의 [감사 로그와 API 로그](#감사-로그와-api-로그)를 참조하세요.
</Info>

## 개요

| 질문 | 답변 |
|------|------|
| 어디서 읽나요? | **구성 > 감사 로그**에서 애플리케이션 하나씩 |
| 누가 읽을 수 있나요? | 조직 관리자, 그리고 애플리케이션의 감사 키를 가진 도구 |
| 무엇이 기록되나요? | 대시보드나 API로 한 변경, 멤버에게 거부된 관리자 전용 작업, API 로그 읽기, AI 어시스턴트의 도구 호출, 자동 삭제 실행처럼 Moss가 직접 한 변경 |
| 무엇이 기록되지 않나요? | 세션 열기와 내보내기, 그 밖의 대시보드 읽기 |
| 얼마나 보관하나요? | 기본 365일이며, 배포 운영자가 정합니다 |
| 이벤트를 수정하거나 삭제할 수 있나요? | 대시보드나 API로는 누구도 수정할 수 없습니다. 보관 기간이 끝나거나 관리자가 사용자 데이터를 삭제할 때만 삭제됩니다. |

## 기록되는 내용

### 이벤트 필드

| 필드 | 설명 |
|------|------|
| 시각 (`timestamp`) | 일어난 시각입니다. UTC로 저장하며, 대시보드는 브라우저의 시간대로 표시합니다. |
| 행위자 (`actor_id`, `actor_email`, `actor_type`) | 누가 했는지입니다. 대시보드 사용자(`user`), 읽기 전용 키(`api_key`), 또는 Moss 자신(`system`)입니다. 이메일을 알면 대시보드에 이메일이 표시됩니다. |
| 인증 방식 (`auth_method`) | 행위자가 로그인한 방식입니다. 대시보드 로그인은 `jwt`, AI 어시스턴트는 `mcp_pat` 또는 `mcp_oauth`, 그 밖에는 키 종류입니다. |
| 작업 (`action`) | 일어난 일입니다. 예: `jwt_key.revoke` |
| 대상 (`target_type`, `target_id`, `target_name`) | 작업의 대상입니다. 예: 키, 소스, 애플리케이션 |
| 결과 (`outcome`) | `success`, `failure`, 또는 관리자 역할이 없어 거부된 작업의 `denied` |
| 상태 (`status_code`) | 요청이 있었다면 그 요청의 HTTP 상태 |
| 출발 IP, 사용자 에이전트, 요청 ID | 요청이 온 곳 |
| 변경 사항 (`changes`) | 변경 전후 값을 기록하는 변경이라면 그 값 |
| 메타데이터 (`metadata`) | 개수나 내보내기에 쓴 필터 같은 추가 정보 |

토큰이나 비밀번호 같은 자격 증명 필드의 값은 **변경 사항**에서 `[REDACTED]`로 표시됩니다.

### 기록 대상

| 영역 | 작업 |
|------|------|
| 애플리케이션과 설정 | `application.create`, `application.update`, `application.config.update`, `application.sdk_config.update`, `application.instructions.update`, `application.exported`, `application.imported`, 그리고 0.17.0부터 `application.guidance.update` |
| 키 | `jwt_key.create`, `jwt_key.rotate`, `jwt_key.revoke`, `traffic_api_key.generate`, `traffic_api_key.revoke`, `audit_read_key.generate`, `audit_read_key.revoke` |
| 상호작용 요소 화이트리스트 | `whitelist_rule.create`, `whitelist_rule.update`, `whitelist_rule.delete`, `whitelist.config.update` |
| 지식 베이스 | `kb.source.*`, `kb.page.*`, `kb.markdown.upload`, `kb.ingestion.*` |
| 통합 | `document360.credentials.set`, `document360.credentials.clear`, 그리고 0.17.0부터 `intercom.*` |
| 프로시저와 검토 | `session.evaluate`, `session.message.evaluate`, 그리고 0.17.0부터 `procedure.delete` |
| 사용자 데이터 | `user.metadata.delete`, `data.deletion_request.create`, 그리고 0.17.0부터 `data.deletion_request.retry`와 `data.deletion_request.execute` |
| 데이터 및 개인정보(0.17.0부터) | `data.retention.update`, `data.retention.run`(자동 삭제 실행), `data.retention.operator_update`(Moss 관리자의 변경), `traffic_logging_config.update`(API 로그 기록 켜기·끄기) |
| API 로그 | `traffic_log.delete`, 그리고 0.17.0부터 `traffic_log.read`와 `traffic_log.export` |
| 모델(0.17.0부터) | 애플리케이션의 모델 변경(변경 전후 모델의 데이터 처리자와 함께 표시), `application.model.fallback_started`, `application.model.fallback_ended`, `application.model.requests_refused`, `application.model.default_answered` |
| AI 어시스턴트(0.17.0부터) | 모든 도구 호출의 `mcp.tool.call`, 그리고 연결과 설정 작업인 `mcp.grant.*`, `mcp.settings.update`, `mcp.oauth.consent` |
| 접근 | `auth.denied`: 멤버에게 거부된 관리자 전용 작업(HTTP 403) |
| 그 밖의 경우 | API로 애플리케이션, 조직, 지식 베이스를 바꿨는데 고유한 작업 이름이 없으면 `http.<method> <route>`로 기록하고, 메타데이터에 `uninstrumented: true`를 남깁니다. |

읽기에 관한 참고 사항:

- API 로그 읽기는 사람과 필터한 사용자마다 10분에 최대 한 번 기록됩니다. 0.17.0부터는 Moss가 읽기를 기록하지 못하면 API 로그를 반환하지 않습니다(HTTP 503 `audit_unavailable`).
- 대시보드에서 세션을 열거나 내보내는 일은 기록되지 않습니다. 대화를 읽을 수 있는 사람을 관리하려면 [최종 사용자의 대화를 볼 수 있는 사람](/ko/security/authentication#최종-사용자의-대화를-볼-수-있는-사람)을 참조하세요.

### 애플리케이션 페이지에 없는 이벤트

**감사 로그** 페이지에는 애플리케이션 하나의 이벤트가 표시됩니다. 조직 전체 이벤트는 이 페이지에 없습니다.

- `auth.login`: 로그인한 사람이 브라우저 탭에서 대시보드를 처음 열 때, 대시보드가 최선의 노력(best effort)으로 보냅니다. 모든 로그인이 아니라 대시보드 사용을 기록합니다. 요청에 실패한 탭이나 대시보드를 쓰지 않는 클라이언트는 이벤트를 남기지 않고, 새 탭을 열 때마다 이벤트가 하나씩 늘어납니다. 실패한 로그인은 Moss가 기록하지 않습니다.
- AI 어시스턴트 연결과 조직 설정

관리자는 [조직 엔드포인트](#자체-도구에서-감사-로그-읽기)로 이 이벤트를 읽거나, 관리자 역할로 연결한 AI 어시스턴트에게 요청할 수 있습니다. 만료된 감사 이벤트를 삭제하는 작업처럼 Moss 자체의 유지 관리 이벤트는 어떤 조직에도 표시되지 않습니다.

## 대시보드에서 감사 로그 보기

**구성 > 감사 로그**를 여세요. 관리자만 열 수 있으며, 멤버에게는 잠금 표시가 보입니다.

페이지는 최근 7일의 이벤트를 최신순으로, 한 페이지에 50개씩 보여 줍니다. 행을 펼치면 **변경 사항**과 **메타데이터**가 보입니다. 데이터 보존과 모델에 관한 변경은 문장으로 풀어서 표시합니다.

| 필터 | 형식 | 일치 조건 |
|------|------|-----------|
| **행위자** | 텍스트 | `actor_id`에 있는 행위자 ID와 정확히 같아야 합니다. 이메일 주소는 일치하지 않습니다. |
| **작업** | 텍스트 | 작업 이름과 정확히 같아야 합니다. 예: `jwt_key.revoke` |
| **결과** | 텍스트 | `success`, `failure` 또는 `denied` |
| **시작 날짜**, **종료 날짜** | 날짜와 시각, 브라우저의 시간대 기준 | 그 기간의 이벤트. 기본값: 최근 7일 |

<Tip>
    특정 사람으로 필터하려면 이벤트를 한 번 내보내 그 사람의 `actor_id`를 복사하세요. 표에는 이메일이 보이지만 **행위자** 필터는 ID와 비교합니다.
</Tip>

0.17.0부터 **구성 > 데이터 및 개인정보 > 변경 기록**을 누르면, 최근 90일의 데이터·개인정보 변경만 보이도록 필터된 같은 페이지가 열립니다. 이 필터를 지우려면 **모든 이벤트 보기**를 누르세요.

### 내보내기

**내보내기**를 누른 다음 **JSON으로 내보내기** 또는 **CSV로 내보내기**를 누르세요. 파일에는 지금 보이는 페이지만이 아니라 현재 필터에 맞는 모든 이벤트가 위의 모든 필드와 함께 담깁니다. 한 번에 최대 10,000개까지 내보낼 수 있으며, 그보다 많으면 거부되므로 날짜나 필터를 좁히세요. 일치하는 이벤트가 더 많으면 개수가 **10,000+ events**로 표시됩니다.

CSV 파일에서 `=`, `+`, `-`, `@`로 시작하는 셀은 앞에 `'`를 붙여 기록하므로, 스프레드시트가 수식으로 실행하지 않습니다.

## 자체 도구에서 감사 로그 읽기

요청은 대시보드 주소로 보내세요. Moss 호스팅 서비스는 `https://dashboard.viamoss.ai`이고, 자체 호스팅 설치는 고객사 대시보드의 주소입니다. 대시보드는 `/api/v1/` 요청을 Moss API로 전달합니다.

```bash
# 애플리케이션의 감사 이벤트 목록(최신순, 기본 한 페이지에 50개)
curl "https://dashboard.viamoss.ai/api/v1/applications/YOUR_APP_ID/audit-events?start_date=2026-11-01T00:00:00Z&end_date=2026-11-30T23:59:59Z" \
  -H "X-Audit-API-Key: YOUR_AUDIT_API_KEY"

# 같은 이벤트를 CSV로 내보내기(또는 format=json)
curl "https://dashboard.viamoss.ai/api/v1/applications/YOUR_APP_ID/audit-events/export?format=csv&start_date=2026-11-01T00:00:00Z" \
  -H "X-Audit-API-Key: YOUR_AUDIT_API_KEY" -o audit-events.csv
```

| 엔드포인트 | 반환 | 호출할 수 있는 사람 |
|------------|------|---------------------|
| `GET /api/v1/applications/{application_id}/audit-events` | `items`, `total`, `page`, `page_size`. `total`은 10,001에서 더 세지 않습니다. | 애플리케이션의 감사 키, 또는 관리자의 대시보드 로그인 토큰 |
| `GET /api/v1/applications/{application_id}/audit-events/export`(`format=json` 또는 `format=csv`) | 이벤트 최대 10,000개가 담긴 파일. 더 많으면 HTTP 400으로 거부 | 애플리케이션의 감사 키, 또는 관리자의 대시보드 로그인 토큰 |
| `GET /api/v1/organizations/{organization_id}/audit-events` | `auth.login`을 포함한 조직의 이벤트 | 관리자의 대시보드 로그인 토큰만. 감사 키로는 호출할 수 없습니다. |

대시보드는 조직 ID를 표시하지 않습니다. 내보낸 이벤트의 `organization_id` 필드에서 확인하세요.

쿼리 매개변수(모두 선택):

| 매개변수 | 형식 | 기본값 | 효과 |
|----------|------|--------|------|
| `page` | 정수, 1 이상 | `1` | 페이지 번호(목록만) |
| `page_size` | 정수, 1~100 | `50` | 한 페이지의 이벤트 수(목록만) |
| `start_date`, `end_date` | ISO 8601 날짜·시각 | 없음 | 기간. 오프셋이 없는 시각은 UTC로 읽습니다. |
| `actor_id` | 문자열 | 없음 | 정확한 행위자 ID |
| `action` | 문자열 | 없음 | 정확한 작업 이름 |
| `action_prefix` | 문자열, 반복 가능 | 없음 | 이 값 중 하나로 시작하는 작업. 예: `jwt_key.` |
| `target_type` | 문자열 | 없음 | 정확한 대상 종류. 예: `jwt_key` |
| `outcome` | 문자열 | 없음 | `success`, `failure` 또는 `denied` |
| `exclude_system` | 불리언 | `false` | Moss가 직접 만든 이벤트 제외 |

푸시나 스트리밍 전달은 없습니다. SIEM에 넣으려면 `start_date`를 옮겨 가며 목록 엔드포인트를 주기적으로 조회하세요.

### 감사 API 키

감사 키는 애플리케이션 하나의 감사 이벤트를 읽는 읽기 전용 키입니다.

- 자기 애플리케이션의 목록 엔드포인트와 내보내기 엔드포인트를 읽습니다. 다른 애플리케이션에 대한 요청은 HTTP 403을 받습니다. 아무것도 바꿀 수 없습니다.
- `audit_`로 시작합니다. Moss는 키를 한 번만 보여 주고 해시만 보관합니다.
- 애플리케이션마다 최대 하나입니다. 새 키를 만들면 이전 키가 대체되어 곧바로 동작을 멈춥니다.
- 키 생성과 폐기는 `audit_read_key.generate`와 `audit_read_key.revoke`로 기록됩니다.

0.17.0의 대시보드에는 감사 키를 다루는 화면이 없습니다. 감사 키는 API로 만들고 관리하며, 모든 호출은 조직의 관리자로 로그인한 상태로 인증되어야 합니다.

| 요청 | 효과 |
|------|------|
| `POST /api/v1/applications/{application_id}/audit-api-key` | 기존 키를 대체해 키를 만들고, `api_key`로 한 번만 반환합니다. |
| `DELETE /api/v1/applications/{application_id}/audit-api-key` | 키를 폐기합니다. |
| `GET /api/v1/applications/{application_id}/audit-api-key/status` | 키가 있는지 알려 줍니다(`has_audit_api_key`). |

키는 코드가 아닌 시크릿 관리자에 보관하세요. 교체하려면 새 키를 만들고 도구를 업데이트하세요. 새 키가 생기는 순간 이전 키는 동작을 멈춥니다.

## 로그 보존

| 기록 종류 | 보관 기간 | 정하는 사람 |
|-----------|-----------|-------------|
| 감사 이벤트 | 기본 365일이며, 그 뒤 매일 실행되는 작업이 삭제합니다. 법적 보존 중인 애플리케이션은 모든 이벤트를 보관합니다. | 배포 운영자(자체 호스팅 설치에서는 `AUDIT_RETENTION_DAYS`). 대시보드에서는 바꿀 수 없으며, **데이터 및 개인정보** 설정은 감사 이벤트에 적용되지 않습니다. |
| API 로그 | 기본값인 **자동 삭제** 꺼짐 상태에서는 삭제할 때까지 보관합니다. 켜면 기본 90일입니다. | 관리자가 **구성 > 데이터 및 개인정보**에서 정합니다. [데이터 및 개인정보](/ko/dashboard/data-privacy)를 참조하세요. |

실제 적용 기간은 계약, 문서화된 고객 지시 및 적법한 보존 의무에 따라 결정됩니다.
최소 보존 의무가 있으면 삭제 시점과 충돌하지 않도록 먼저 맞춰야 합니다.
해당 배포의 활성화된 삭제 일정은 Moss에 확인하세요.

자체 호스팅 설치에서는 이 일일 작업이 대시보드 백엔드에서 실행되며, 감사 이벤트를 삭제할 수 있는 데이터베이스 역할이 필요합니다. [자체 호스팅 운영](/ko/self-hosting/operations)을 참조하세요.

### 사용자 데이터를 삭제할 때

관리자가 사용자 데이터를 삭제하면(**구성 > 데이터 및 개인정보 > 사용자 데이터 삭제**) Moss는 그 사용자에 관한 감사 이벤트도 삭제합니다. 대시보드에는 이 항목이 "팀이 이 사용자의 대화를 검토하거나 열람한 기록을 포함한, 이 사용자에 관한 감사 기록"으로 표시됩니다. 다음이 포함됩니다.

- 팀이 그 사용자의 대화를 평가한 기록(`session.evaluate`, `session.message.evaluate`)
- 그 사용자로 필터한 API 로그의 읽기, 내보내기, 삭제
- 그 사용자의 채팅에 대한 AI 어시스턴트 도구 호출(`mcp.tool.call`)
- 그 사용자의 메타데이터를 이전에 삭제한 기록과, 그 사용자에 대한 이전 삭제 요청

관리자 작업에 관한 그 밖의 감사 기록은 남습니다. 배포 운영자가 감사 최소 보관 기간을 정했다면, 그 사용자에 관한 이벤트 중 내용이 없고 최소 기간보다 새로운 이벤트는 보관되며 삭제 증명서에 표시됩니다. 법적 보존 중에는 삭제가 진행되지 않습니다. 전체 절차는 [데이터 및 개인정보](/ko/dashboard/data-privacy)를 참조하세요.

## 로그 무결성

### 감사 이벤트의 수정·삭제 제한

- 애플리케이션 사용자는 대시보드나 감사 API에서 기존 감사 이벤트를 수정하거나 삭제할 수 없습니다.
- 이벤트는 보존 기간이 끝날 때와, 위에서 설명한 대로 관리자가 사용자 데이터를 삭제할 때만 삭제됩니다.

### 이벤트를 기록하지 못했을 때

대부분의 작업에서 기록은 최선의 노력으로 이루어집니다. Moss가 이벤트를 기록하지 못해도 작업 자체는 완료됩니다. 예외는 API 로그 읽기와 내보내기입니다. 기록하지 못하면 Moss가 이를 거부합니다.

### 타임스탬프

감사 이벤트 시각은 서버에서 UTC로 생성합니다.

## 감사 로그와 API 로그

| | 감사 로그 | API 로그 |
|---|---|---|
| 담는 내용 | 누가 무엇을 했는지, 변경 전후 값 | 애플리케이션 API 호출의 요청과 응답. 알려진 키와 개인정보 패턴은 마스킹 |
| 기본 상태 | 항상 켜짐 | 꺼짐. 관리자가 **API 로그**의 **API 로그 기록**이나 **구성 > 데이터 및 개인정보**의 **API 상세 로그 수집**으로 켭니다. |
| 위치 | **구성 > 감사 로그** | **분석** 그룹의 **API 로그**(0.17.0부터) |
| 읽을 수 있는 사람 | 관리자와 감사 키 | 관리자와 **구성 > 보안**의 **API 로그 접근 키**(`X-Traffic-API-Key`) |
| 보관 | 기본 365일, 운영자가 정함 | **데이터 및 개인정보**에서 정함 |

API 로그의 읽기, 내보내기, 삭제와 기록 켜기·끄기도 감사 로그에 기록됩니다.

## 모범 사례

### 정기적 검토

다음을 확인하도록 감사 로그를 주기적으로 검토하세요:

- 서명 키, 허용 도메인 등 **구성 > 보안** 설정의 변경
- 멤버가 관리자 전용 작업을 시도한 것을 보여 주는 `auth.denied` 이벤트
- API 로그 읽기와 내보내기
- 조직에서 어시스턴트를 허용한 경우 AI 어시스턴트의 도구 호출

### API 키 보안

감사 API 키 보호:

- 안전하게 저장 (코드에 포함하지 않음)
- 새 키를 만들어 주기적으로 교체 (새 키가 이전 키를 대체)
- 더 이상 쓰지 않는 도구의 키는 폐기

## 자주 묻는 질문

**대시보드 로그인이 기록되나요?**
일부만 기록됩니다. 로그인한 사람이 브라우저 탭에서 대시보드를 처음 열 때 대시보드가 최선의 노력으로 `auth.login` 이벤트를 보내므로, 모든 로그인이 아니라 대시보드 사용이 기록됩니다. 이 이벤트는 조직 전체 이벤트라서 애플리케이션의 **감사 로그** 페이지에는 없습니다. [조직 엔드포인트](#자체-도구에서-감사-로그-읽기)로 읽으세요. 실패한 로그인은 Moss가 기록하지 않습니다.

**누군가 대화를 읽으면 기록되나요?**
대시보드에서 세션을 열거나 내보내는 일은 기록되지 않습니다. API 로그 읽기와 AI 어시스턴트의 도구 호출은 기록됩니다.

**감사 이벤트를 SIEM으로 보낼 수 있나요?**
네. 애플리케이션의 감사 키로 `GET /api/v1/applications/{application_id}/audit-events`를 주기적으로 조회하세요. Moss가 이벤트를 밀어 보내지는 않습니다.

**감사 이벤트를 365일보다 길거나 짧게 보관할 수 있나요?**
대시보드에서는 바꿀 수 없습니다. 기간은 배포 운영자가 정하며, Moss 호스팅 서비스라면 Moss에 문의하세요.

**행위자 필터에 이메일을 입력하면 아무것도 나오지 않는 이유는 무엇인가요?**
필터는 이메일이 아니라 행위자 ID와 정확히 비교합니다. 내보낸 파일에서 `actor_id`를 복사하세요.

**사용자 데이터를 삭제하면 감사 이벤트는 어떻게 되나요?**
그 사용자에 관한 이벤트가 함께 삭제되고, 그 밖의 관리자 이벤트는 남습니다. [사용자 데이터를 삭제할 때](#사용자-데이터를-삭제할-때)를 참조하세요.

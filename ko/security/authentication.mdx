Moss는 두 종류의 호출자를 인증합니다. 최종 사용자는 SDK를 통해 Moss에 접근하며, 서버가 사용자마다 서명한 토큰을 사용합니다. 팀원은 대시보드에 로그인해 접근합니다. Moss 호스팅 서비스에서는 Clerk로, 자체 호스팅 설치에서는 고객사의 ID 공급자로 로그인합니다. 이 페이지에서는 두 방식과 대시보드의 두 역할, 역할별로 볼 수 있는 것, 그리고 한 조직의 데이터를 다른 조직과 분리하는 방법을 설명합니다.

## 개요

| 컨텍스트 | 방법 | 설명 |
|----------|------|------|
| **SDK** | JWT 토큰 | 서버가 애플리케이션의 키로 사용자마다 서명하는 단기 토큰입니다. Moss는 요청마다 검증합니다. |
| **대시보드 (Moss 호스팅)** | Clerk SSO | 조직 지원이 포함된 OAuth 기반 싱글 사인온 |
| **대시보드 (자체 호스팅)** | 고객사의 ID 공급자(OIDC) | 팀원은 고객사의 ID 공급자로 로그인하며, 그 그룹에 따라 각자의 역할이 정해집니다. |
| **고객 도구에서 읽는 감사 로그와 API 로그** | 읽기 전용 키 | 애플리케이션마다 각각 하나씩입니다. [감사 로깅](/ko/security/audit-logging)을 참조하세요. |
| **AI 어시스턴트** | 개인 토큰 또는 OAuth | 배포에서 제공하고 조직 관리자가 켠 경우에만 쓸 수 있습니다. 어시스턴트는 연결한 사람으로서 동작합니다. |

## JWT 인증

모든 SDK 요청에는 서버가 로그인한 사용자를 위해 서명한 JWT가 있어야 합니다. JWT는 SDK의 유일한 인증 수단입니다. SDK용 API 키는 없으며, 유효한 토큰이 없는 요청은 HTTP 401로 거부합니다. 예외는 위젯의 공개 시작 설정을 읽는 요청 하나뿐이며, [아래](#허용-도메인은-보조-검사입니다)에서 설명합니다. 로컬 개발 환경 밖에서는 인증을 끌 수 없습니다. 개발자 가이드는 [SDK 인증](/ko/sdk/authentication)입니다.

### 작동 방식

1. 서버가 앱에 로그인한 사용자를 위해 JWT에 서명합니다.
2. SDK가 모든 요청의 `Authorization` 헤더에 토큰을 담아 보냅니다.
3. Moss는 토큰의 `kid`가 가리키는 서명 키를 찾아 그 키의 알고리즘으로 서명을 검증하고, 클레임과 수명을 확인합니다.
4. Moss는 사용자 신원을 `sub` 클레임에서만 가져옵니다. 요청 본문이나 SDK의 `userId` 설정은 쓰지 않습니다.

### 토큰 구조

| 클레임 | 필수 | 설명 |
|--------|------|------|
| `sub` | 예 | 사용자 ID(주체). 비어 있지 않은 문자열입니다. |
| `app` | 예 | 애플리케이션 ID. 서명 키가 속한 애플리케이션이어야 합니다. |
| `exp` | 예 | 만료 타임스탬프 |
| `iat` | 예 | 발급 타임스탬프. `exp`에서 `iat`를 뺀 값은 최대 24시간입니다. |
| `iss`, `aud` | 애플리케이션에서 요구할 때만 | **구성 > 보안 > JWT 클레임 강제**에 설정한 값과 정확히 같아야 합니다. |
| `metadata` | 아니요 | 답변을 사용자에 맞추는 속성입니다. 아무것도 허용하거나 막지 않습니다. |

모든 오류 코드를 포함한 전체 규칙은 [클레임 참조](/ko/sdk/authentication#jwt-클레임-참조)에 있습니다.

### 보안 기능

- **애플리케이션 하나에 고정** - 키는 애플리케이션 하나에 속하며, 토큰의 `app`은 그 애플리케이션을 가리켜야 합니다.
- **알고리즘 고정** - 각 키는 자기 알고리즘(HS256, RS256 또는 ES256)에 고정됩니다. 다른 알고리즘으로 서명한 토큰은 거부되므로, 한 종류의 키를 다른 종류로 속일 수 없습니다.
- **만료 적용** - 토큰에는 유효한 `exp`와 `iat` 클레임이 있어야 하며, 수명은 최대 24시간입니다.
- **키 로테이션 지원** - 애플리케이션마다 활성 서명 키를 최대 5개까지 두고, 즉시 또는 24시간이나 72시간의 유예 기간 뒤에 폐기할 수 있습니다.
- **상수 시간 검증** - HS256 서명 검증에 타이밍에 안전한 비교 사용

### 서명 방식

Moss는 애플리케이션별로 두 가지 서명 방식을 지원합니다:

| 방식 | 알고리즘 | Moss가 저장하는 것 |
|------|----------|--------------------|
| **공유 비밀 키** | HS256 | Moss가 생성한 공유 비밀 키. 토큰 검증에 사용 |
| **비대칭 키** | RS256(RSA, 2,048~8,192비트), ES256(P-256) | 공개 키만 저장 |

비대칭 서명을 사용하면 키 쌍을 직접 생성하고 공개 키만 Moss에 등록합니다.
개인 키는 고객 인프라를 벗어나지 않으므로, Moss는 그 키로 고객을 대신해 토큰을
발급할 수 있는 자료를 보유하지 않습니다. 등록된 각 키는 해당 알고리즘에 고정되며,
로테이션 시에는 폐기된 키를 다시 등록하는 것이 아니라 새 키 쌍을 등록해야 합니다.

<Info>
    보안 정책상 대칭 비밀 키를 외부 업체와 공유할 수 없는 경우 비대칭 서명이
    적합합니다. 그 외의 경우에는 HS256이 더 간단합니다.
</Info>

### 키 관리

관리자는 **구성 > 보안 > JWT 서명 키**에서 키를 관리합니다:

- **키 ID (`kid`)** - `key_` 뒤에 12자가 붙은 고유 식별자로, 토큰 헤더에 포함
- **한 번만 표시** - HS256 시크릿은 키를 만들 때만 표시
- **폐기** - **즉시**, 또는 **24시간**이나 **72시간**의 유예 기간 뒤에 폐기. 폐기된 키는 **폐기됨** 상태로 목록에 남습니다. 폐기는 되돌릴 수 없으며, 예정된 폐기는 앞당길 수는 있지만 미룰 수는 없습니다.
- **마지막 사용 추적** - 키마다 생성 시각과 마지막 사용 시각 표시
- **감사** - 키의 생성, 로테이션, 폐기를 [감사 로그](/ko/security/audit-logging)에 기록

서명용 시크릿이나 개인 키가 유출되면 키를 **즉시** 폐기하세요. 이미 발급된 토큰을 포함해 그 키로 서명한 모든 토큰이 곧바로 `KEY_REVOKED`로 실패합니다. 그런 다음 새 키를 만드세요. 활성 키는 최대 5개까지 둘 수 있습니다. [서명 키 교체와 폐기](/ko/sdk/authentication#서명-키-교체와-폐기)를 참조하세요.

### 허용 도메인은 보조 검사입니다

애플리케이션마다 있는 **허용 도메인** 목록(**구성 > 보안 > 도메인 접근 제어**)은 모든 SDK 요청에서 페이지의 `Origin` 또는 `Referer` 헤더와 비교됩니다. 이 목록은 다른 웹사이트가 브라우저에서 이 애플리케이션의 어시스턴트를 쓰지 못하게 막지만, 보안 경계는 아닙니다.

- 브라우저 밖의 클라이언트는 `Origin`을 마음대로 보낼 수 있습니다. 그런 클라이언트를 인증하는 것은 서명된 토큰입니다.
- 목록이 비어 있으면 모든 페이지를 허용합니다.
- `Origin`도 `Referer`도 없는 요청은 통과합니다. 단, 배포에서 허용된 페이지를 요구하면 그렇지 않습니다(자체 호스팅 설치에서는 운영자 설정 `SDK_REQUIRE_ORIGIN`. [자체 호스팅 네트워크](/ko/self-hosting/network) 참조).
- SDK가 시작할 때 불러오는 위젯 설정(디자인, 어떤 캡처가 켜져 있는지 등)은 애플리케이션 ID를 아는 사람이면 누구나 토큰 없이 읽을 수 있습니다. 이 요청에도 허용 도메인 검사가 적용됩니다. SDK용 설정에는 시크릿을 절대 넣지 마세요.

일치 규칙은 [허용 도메인](/ko/sdk/authentication#허용-도메인)에 있습니다.

### 요청 제한

0.17.0부터 사용자(`sub`)마다 애플리케이션별로 1분에 채팅 30개를 시작하고 질문 60개를 보낼 수 있으며, 채팅마다 1분에 가이드 단계 120개를 완료할 수 있습니다. 채팅마다 녹화는 1분에 10번 업로드할 수 있습니다. 제한을 넘은 요청은 `Retry-After`와 함께 HTTP 429를 받으며, 질문이나 가이드 단계에서는 사용자에게 "요청이 너무 많습니다. 잠시 후 다시 시도해 주세요."가 표시됩니다. [요청 제한](/ko/sdk/authentication#요청-제한)을 참조하세요.

## 대시보드 인증

### Moss 호스팅 대시보드 (Clerk)

Moss 호스팅 대시보드는 엔터프라이즈급 SSO 기능을 제공하는 Clerk를 인증에 사용합니다.

#### 기능

- **OAuth 통합** - Google, GitHub 또는 이메일로 로그인
- **조직 지원** - 역할 기반 권한이 있는 멀티테넌트 접근
- **세션 관리** - 자동 갱신이 있는 보안 세션 토큰
- **MFA 지원** - 선택적 다중 인증

#### 조직 기반 접근

모든 대시보드 작업은 조직으로 범위가 지정됩니다:

- 애플리케이션은 조직에 속함
- 사용자는 여러 조직의 구성원이 될 수 있음
- 조직 전환 시 표시되는 애플리케이션 변경
- 대시보드의 API 호출에 JWT의 조직 컨텍스트 포함
- 활성 조직이 없는 로그인은 거부됨

역할은 Clerk의 조직 역할을 따릅니다. `org:admin`은 **관리자**이고, 그 밖의 역할은 모두 **멤버**입니다.

### 자체 호스팅 대시보드 (고객사의 ID 공급자)

자체 호스팅 설치에서는 Okta, Microsoft Entra ID, Keycloak 같은 고객사의 ID 공급자로 OpenID Connect(OIDC)를 통해 팀원이 로그인합니다. 설치 하나가 조직 하나를 담당합니다. 로그인 정책은 고객사의 ID 공급자에서 정합니다.

역할은 사용자 토큰에 담긴 그룹으로 정해집니다(운영자가 다른 클레임을 지정하지 않으면 `groups` 클레임).

| 사용자가 속한 곳 | 역할 |
|------------------|------|
| `OIDC_ADMIN_GROUPS`에 있는 그룹 | **관리자**(멤버 그룹보다 우선) |
| `OIDC_MEMBER_GROUPS`에 있는 그룹 | **멤버** |
| 둘 다 아니고, `OIDC_MEMBER_GROUPS`에 그룹이 지정된 경우 | 거부(HTTP 403) |
| 둘 다 아니고, `OIDC_MEMBER_GROUPS`가 비어 있거나 설정되지 않은 경우 | **멤버**: 로그인할 수 있는 사람은 누구나 |

로그인할 수 있는 사람을 제한하려면 `OIDC_MEMBER_GROUPS`를 설정하세요. 설정 방법은 [대시보드 로그인과 역할](/ko/self-hosting/overview#대시보드-로그인과-역할)에 있습니다.

## 역할

Moss의 역할은 **관리자**와 **멤버** 두 가지입니다. 역할은 조직의 모든 애플리케이션에 적용됩니다. 애플리케이션별 역할은 없으며, 역할은 Moss가 아니라 Clerk나 고객사의 ID 공급자에서 지정합니다. 대시보드 전체 안내는 [대시보드 개요](/ko/dashboard/overview)에 있습니다.

| | 멤버 | 관리자 |
|---|---|---|
| **분석**, **코파일럿**, **세션**, **사용자**, **모니터** | 예 | 예 |
| **제안**: 검토, 수락, 무시 | 예. 단, AI 어시스턴트 프롬프트를 바꾸는 제안의 수락은 제외 | 예 |
| 세션을 CSV나 JSON으로 내보내기 | 예 | 예 |
| **지식 베이스**와 **프로시저**(게시와 삭제 포함) | 예 | 예 |
| **추천 콘텐츠** | 보기만 가능 | 예 |
| **API 로그** | 아니요 | 예 |
| **구성** 그룹: 설정, 서명 키, 허용 도메인, 통합, **데이터 및 개인정보**, **감사 로그** | 아니요 | 예 |
| 애플리케이션 만들기, 가져오기, 내보내기, API 작업과 연결, 사용자 데이터 삭제 | 아니요 | 예 |

멤버가 관리자 전용 작업을 호출하면 Moss는 HTTP 403으로 응답하고 [감사 로그](/ko/security/audit-logging)에 `auth.denied` 이벤트를 기록합니다.

### 최종 사용자의 대화를 볼 수 있는 사람

조직의 모든 멤버와 관리자는 모든 애플리케이션의 모든 세션을 열 수 있습니다. 대화 기록과 세션 리플레이, **사용자** 목록, 이를 바탕으로 한 분석이 모두 포함됩니다. 누구나 세션을 내보낼 수도 있습니다.

- 세션을 열거나 내보내는 일은 감사 로그에 기록되지 않습니다. API 로그를 읽는 일은 기록됩니다.
- 세션 리플레이는 서명된 저장소 링크로 열립니다. 기본적으로 링크는 7일 동안 유효하며(배포 운영자가 `STORAGE_URL_EXPIRY_SECONDS`로 바꿀 수 있음), 링크를 가진 사람은 누구나 로그인하지 않고 리플레이를 열 수 있습니다.
- 조직의 **대화 내용** 설정이 켜져 있는 동안, 사람이 연결한 AI 어시스턴트는 그 사람으로서 대화 기록을 읽을 수 있습니다.
- 대화를 읽을 수 있는 사람을 제한하려면 조직에 속한 사람을 제한하세요. Clerk의 조직 구성원, 자체 호스팅 설치에서는 `OIDC_MEMBER_GROUPS`로 정합니다.

## 멀티테넌시 보안

Moss는 모든 계층에서 엄격한 테넌트 격리를 적용합니다:

### 데이터베이스 수준

대시보드 요청은 애플리케이션을 ID와 고객의 조직으로 함께 찾으므로, 다른 조직의 애플리케이션은 찾을 수 없습니다. SDK 요청은 토큰의 서명 키가 속한 애플리케이션과 토큰의 `sub`로 범위가 정해집니다. 0.17.0부터는 데이터베이스 제약 조건도, 레코드의 애플리케이션이 그 레코드가 속한 상위 레코드의 애플리케이션과 다르면 거부합니다. 예를 들어 대화 인사이트나 페이지 스냅샷은 그 채팅 세션과 애플리케이션이 같아야 합니다.

### API 수준

- 대시보드 사용자의 조직은 로그인에서 정해집니다. 호스팅 서비스에서는 Clerk 조직이고, 자체 호스팅 설치에서는 그 설치의 단일 조직입니다.
- 다른 조직의 애플리케이션에 대한 대시보드 요청은 거부됩니다. 대부분의 경로는 404 "Application not found"로 응답하므로, 응답만으로는 애플리케이션이 있는지 알 수 없습니다. 감사 로그와 API 로그를 읽는 경로는 다른 조직의 애플리케이션이면 403, 존재하지 않는 애플리케이션이면 404로 응답합니다.
- SDK 토큰에는 조직 정보가 없습니다. 각 토큰은 서명 키를 통해 애플리케이션 하나에 고정되며, `app`이 그 키의 애플리케이션과 다른 토큰은 거부됩니다(`APP_MISMATCH`).
- 감사 키와 API 로그 키는 만들 때 지정한 애플리케이션에서만 동작합니다.

### 감사 수준

- 대시보드에서 한 변경은 실패한 시도까지 기록됩니다.
- 관리자 역할이 없어 거부된 요청은 `auth.denied`로 기록됩니다.
- 읽기는 기록되지 않습니다. 예외는 API 로그 읽기와 AI 어시스턴트의 도구 호출입니다. 다른 조직의 애플리케이션을 읽기만 하는 요청은 거부되지만 기록되지 않습니다.
- Moss에는 감사 이벤트에 직접 설정할 수 있는 알림이 없습니다. 패턴을 지켜보려면 [감사 API](/ko/security/audit-logging#자체-도구에서-감사-로그-읽기)로 이벤트를 고객의 도구로 가져오세요.

## 세션 권한 부여

Moss는 인증과 별도로, 채팅을 지정하는 모든 요청에서 그 채팅의 주인을 확인합니다:

| 요청 | 검증 |
|------|------|
| 채팅 시작 | 애플리케이션에 대한 유효한 토큰 |
| 채팅 다시 열기, 메시지 보내기, 녹화 업로드 | 채팅이 토큰의 애플리케이션과 토큰의 `sub`에 속함 |

사용자의 것이 아닌 채팅에 대한 요청은 다음과 같은 응답을 받습니다.

| 요청 | 다른 사용자의 채팅 | 존재하지 않는 채팅 ID |
|------|--------------------|-----------------------|
| 메시지 보내기 | 403 `SESSION_UNAUTHORIZED` | 403 `SESSION_UNAUTHORIZED` |
| 채팅 다시 열기 | 403 `SESSION_UNAUTHORIZED` | 새 채팅이 시작됨 |
| 녹화 업로드 | 404 "Session not found" | 404 "Session not found" |

채팅 ID는 무작위이므로 추측할 수 없습니다. 채팅은 그 채팅을 시작한 `sub`에 계속 묶여 있으므로, 사람마다 다른 `sub`를 주세요.

## AI 어시스턴트 연결

배포에서 제공하고 조직 관리자가 **AI 어시스턴트 허용**을 켜면, 각자 자기 토큰으로 AI 어시스턴트를 Moss에 연결할 수 있습니다. 어시스턴트는 연결한 사람으로서 동작하며 그 사람보다 많은 권한을 갖지 않습니다. 모든 도구 호출은 감사 로그에 기록됩니다.

Moss는 누군가 Clerk나 고객사의 ID 공급자에서 조직을 떠나도 알 수 없습니다. 그 사람이 만든 연결은 만료되거나 관리자가 폐기할 때까지 계속 동작하므로, 떠난 사람의 연결은 **AI 어시스턴트** 페이지에서 폐기하세요. [AI 어시스턴트](/ko/dashboard/ai-assistants)를 참조하세요.

## 보안 권장 사항

### SDK 통합용

1. 앱이 인증한 사용자에게만, 서버의 세션에서 가져온 `sub`로 **서버에서만 토큰 서명**
2. 현재 토큰이 만료되기 전에 SDK가 새 토큰을 받아 오도록 **`getJwt` 사용**
3. **짧은 토큰 수명 설정** (15-60분 권장)
4. 모든 API 통신에 **HTTPS 사용**
5. 모든 애플리케이션에 **허용 도메인 입력**. 단, 이것만 믿지 마세요.

### 대시보드 접근용

1. 모든 팀 구성원에게 **MFA 활성화**
2. 모든 멤버가 모든 대화를 읽을 수 있으므로 **조직 구성원 정기 검토**
3. 조직에서 사용 가능한 경우 **SSO 사용**
4. **감사 로그**를 주기적으로 검토

## 자주 묻는 질문

**대화는 관리자만 볼 수 있나요, 멤버도 볼 수 있나요?**
모든 멤버가 조직 안 모든 애플리케이션의 모든 세션을 열고 내보낼 수 있습니다. [최종 사용자의 대화를 볼 수 있는 사람](#최종-사용자의-대화를-볼-수-있는-사람)을 참조하세요.

**자체 호스팅 설치에서는 역할이 어디서 정해지나요?**
고객사 ID 공급자의 그룹에서 정해집니다. `OIDC_ADMIN_GROUPS`는 **관리자**, `OIDC_MEMBER_GROUPS`는 **멤버**에 대응합니다. `OIDC_MEMBER_GROUPS`가 비어 있거나 설정되지 않았다면 로그인할 수 있는 사람은 누구나 멤버입니다.

**한 애플리케이션에만 접근하도록 권한을 줄 수 있나요?**
아니요. 역할은 조직의 모든 애플리케이션에 적용되며, 모든 멤버가 모든 애플리케이션의 대화를 읽을 수 있습니다.

**다른 조직의 애플리케이션에 대한 요청은 어떻게 되나요?**
거부됩니다. 대부분의 경로는 404로 응답하고, 감사 로그와 API 로그를 읽는 경로는 403으로 응답합니다. 이 두 경로는 존재하지 않는 애플리케이션에만 404로 응답합니다. SDK 토큰은 애플리케이션 하나에 고정되어 다른 애플리케이션에 접근할 수 없습니다.

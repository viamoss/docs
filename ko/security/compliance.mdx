## 개요

Moss는 글로벌 규정 준수 표준을 충족하고 사용자 개인정보를 보호하기 위해 최선을 다하고 있습니다. 이 페이지는 규정 요구 사항을 지원하는 규정 준수 상태와 기능을 설명합니다.

---

## GDPR 준수

Moss는 GDPR 준수 의무를 지원하는 기능을 제공합니다.

Moss는 고객 데이터를 수탁자 또는 재수탁자로서 처리합니다. 정보주체 권리 요청은
해당 고객에게 보내세요.

### 데이터 주체 권리

#### 접근권 (제15조)

권한 있는 고객 운영자는 다음 기능으로 데이터 접근 요청에 대응할 수 있습니다:

- 대시보드를 통한 채팅 히스토리 내보내기([세션 데이터 내보내기](/ko/dashboard/session-data-export) 참고)
- 대시보드의 세션 화면에서 세션 녹화 다시 보기. 대시보드에는 녹화를 내려받는 기능이 없습니다
- 활동에 대한 감사 로그 접근

#### 삭제권 (제17조)

Moss는 사용자와 연결된 데이터의 삭제를 지원합니다. 0.17.0부터 관리자는 대시보드의 **구성 > 데이터 및 개인정보 > 사용자 데이터 삭제**나 사용자 화면에서 사용자 한 명의 데이터를 삭제하며, API도 계속 쓸 수 있습니다. 절차, 상태, 삭제 증명서는 [데이터 및 개인정보](/ko/dashboard/data-privacy#사용자-데이터-삭제)에서 설명합니다.

**삭제되는 항목**(해당 애플리케이션 안에서):

- 사용자 프로필
- 모든 대화와 그 메시지, 가이드 계획, 스크린샷, 녹화, 페이지 스냅샷, 첨부 파일
- 해당 대화의 평가 점수, 인사이트, 모니터 결과, 헬프데스크 이관 기록
- 이 사용자 ID가 담긴 API 로그와 가이드 이벤트
- 팀이 이 사용자의 대화를 검토하거나 열람한 기록을 포함한, 사용자에 관한 감사 기록. 단, 감사 최소 기간으로 보관되는 기록은 제외(아래 참고)

Moss 관리자가 감사 최소 기간을 정해 두었다면(기본값은 없음), 사용자에 관한 감사 기록 가운데 내용이 담기지 않은 기록, 예를 들어 팀이 사용자의 대화를 평가한 기록, 사용자 메타데이터를 삭제한 기록, AI 어시스턴트의 도구 호출 기록은 최소 기간보다 최근의 것이면 보관됩니다. 이 기록은 일반 감사 보관 기간이 지나 삭제될 때까지 남으며, 삭제 증명서의 JSON에 보관된 기록으로 표시됩니다.

사용자의 대화를 인용한 제안은 남지만, 대화로 이어지는 연결과 대화를 바탕으로 쓴 텍스트는 지워집니다.

**삭제되지 않는 항목:**

- 백업과 이전 파일 버전 (만료될 때까지)
- Moss 밖의 사본 (이미 보낸 헬프데스크 티켓, 사용자 브라우저)
- 관리자 작업에 관한 그 밖의 감사 기록
- 삭제 증명으로 보관하는 요청 자체

**삭제 프로세스:**

1. 관리자가 ID로 사용자를 찾고, 삭제될 항목을 검토한 뒤 ID를 입력해 확인합니다. API로는 관리자로 로그인한 상태에서 `POST /api/v1/applications/{application_id}/deletion-requests`를 호출합니다.
2. Moss가 요청을 기록하고 실행합니다. 애플리케이션에 법적 보존이 걸려 있으면 요청이 거부되며(API에서는 `423`), 아무것도 기록되지 않습니다.
3. 요청의 상태에서 진행 상황을 확인합니다. **진행 중**, 다음 예약 삭제 실행을 기다리는 **대기 중**, **완료**, **데이터 없음**, 그리고 **다시 시도**할 수 있는 **실패**가 있습니다.
4. **완료** 상태가 되면 삭제 증명서에서 무엇이 삭제되고 무엇이 검증되었는지 확인할 수 있습니다. 삭제 증명서는 JSON으로도 제공됩니다.

요청은 해당 애플리케이션에 있는 사용자의 현재 레코드와 설정된 저장소의 파일을 대상으로 합니다.
백업과 외부 처리자 사본은 별도 삭제 절차로 처리합니다. 스토리지 삭제가 실패하면
요청은 미완료로 남고 이미 삭제한 항목의 기록을 유지하므로, **다시 시도**로 마저 끝낼 수
있습니다.

기록된 요청은 삭제 완료의 증거가 아닙니다. **완료** 상태가 될 때까지 상태를 확인한 뒤
삭제 증명서를 쓰세요. 자체 호스팅 설치에서는 요청이 보존 CronJob을 기다릴 수 있으므로,
자동 삭제를 꺼 두더라도 운영자가 이 작업을 설정해야 합니다.
고객 관리 인프라와 Moss가 보유한 사본의 운영 책임은 구분됩니다. 계약상 반환·삭제·증명
기한은 정기 보존기간과 별도로 적용됩니다.

#### 이동권 (제20조)

표준 형식으로 사용자 데이터 내보내기:

- 세션과 그 메시지 (CSV 또는 JSON), 세션 내보내기 기능으로
- 감사 로그 (JSON 또는 CSV)

### 적법한 근거

개인정보처리자가 처리에 적용할 적법 근거를 결정합니다:

| 근거 | 구현 |
|------|------|
| **동의** | SDK에는 자체 동의 요청 화면이 없습니다. 자체 동의 절차를 거친 뒤에만 SDK를 불러오세요(아래 참고) |
| **정당한 이익** | 개인정보처리자가 정당성을 확인한 목적 |
| **계약** | AI 어시스턴트 서비스 제공 |

사용자가 동의할 때까지 Moss를 시작하지 않으려면:

- **CDN 스크립트:** 스크립트를 불러오기 전에 `window.mossSettings`에 `collectionEnabled: false`를 넣으세요. 그러면 Moss가 시작되지 않습니다. 사용자가 동의한 뒤 `window.MossSDK.boot({ collectionEnabled: true })`를 호출하세요.
- **npm 패키지:** 사용자가 동의할 때까지 `AgentProvider`를 렌더링하지 않거나, 설정에 `collectionEnabled: false`를 넘기세요. 이 경우 아무것도 렌더링되지 않습니다.

### 데이터 처리 계약

요구 사항을 충족하는 데이터 처리 계약(DPA)은 영업팀에 문의하세요.

## SOC 2 Type II

Moss는 SOC 2 Type II 감사를 진행하고 있습니다.

### 신뢰 서비스 기준

| 기준 | 상태 | 설명 |
|------|------|------|
| **보안** | 진행 중 | 무단 접근에 대한 보호 |
| **가용성** | 진행 중 | 운영을 위한 시스템 가용성 |
| **기밀성** | 진행 중 | 기밀 정보 보호 |

### 제어

Moss는 다음 영역에서 제어를 구현합니다:

- **접근 제어** - 역할 기반 접근, MFA, 세션 관리
- **변경 관리** - 코드 검토, 배포 승인, 롤백 기능
- **사고 대응** - 감지, 에스컬레이션, 해결 절차
- **모니터링** - 실시간 알림, 감사 로깅, 이상 감지

### 일정

SOC 2 Type II 감사가 진행 중입니다. 현재 상태 및 감사 보고서는 영업팀에 문의하세요.

## ISO 27001

Moss는 ISO 27001 인증을 진행하고 있습니다.

### 정보 보안 관리

주요 영역:

- **위험 평가** - 정기적인 보안 위험 평가
- **자산 관리** - 정보 자산의 목록 및 분류
- **접근 제어** - 알아야 할 필요성 및 최소 권한 원칙
- **암호화** - 데이터 보호를 위한 암호화 표준
- **운영 보안** - 안전한 개발 및 배포 관행

### 일정

ISO 27001 인증이 진행 중입니다. 업데이트는 영업팀에 문의하세요.

## EU AI Act

Moss는 AI 기반 어시스턴트 시스템에 적용되는 EU AI Act 준수를 준비하고 있습니다.

### 투명성 요구 사항

Moss는 다음을 통해 투명성을 지원합니다:

- **명확한 AI 식별** - 사용자가 AI와 상호작용하고 있음을 인지
- **기능 공개** - AI 기능 및 제한 사항 문서화
- **결정 설명** - 해당되는 경우 AI 응답에 추론 포함

### 인간 감독

- **사용자 제어** - 사용자가 AI 제안을 무시하거나 재정의 가능
- **관리자 제어** - 애플리케이션 소유자가 AI 동작 사용자 정의 가능
- **감사 추적** - 주요 감사 이벤트와 선택적 상세 요청 로그로 검토 지원

### 위험 분류

적용 요건은 사용 목적과 조직의 역할에 따라 달라집니다:

- 투명성 의무
- 사용자 알림
- 인간 감독 기능

## 도메인 화이트리스트

SDK가 작동할 수 있는 위치 제한:

### 목적

- 다른 웹사이트가 내 애플리케이션 ID로 Moss를 불러오지 못하게 막기
- Moss에 접근할 수 있는 환경 제어

이 목록은 인증 수단이 아닙니다. 브라우저가 보내는 `Origin`과 `Referer` 헤더에 의존하므로, 브라우저 밖의 클라이언트는 막지 못합니다. 모든 SDK 요청에는 유효한 서명된 토큰이 있어야 합니다. [인증](/ko/security/authentication)을 참고하세요.

### 설정

대시보드의 **구성 > 보안 > 도메인 접근 제어**에서 허용 도메인을 추가하세요.

```
app.example.com
staging.example.com
localhost:3000
```

각 항목은 그 호스트와 정확히 일치해야 합니다. `*.example.com`은 `example.com`의 모든 하위 도메인과 일치하지만, `example.com` 자체와는 일치하지 않습니다.

### 적용

목록에 항목이 있으면 Moss는 SDK가 설정을 불러올 때와 모든 SDK 요청에서 페이지 주소를 확인합니다. 목록에 없는 페이지는 코드 `DOMAIN_NOT_ALLOWED`와 함께 `403`을 받습니다. 목록이 비어 있으면 모든 페이지를 허용합니다. 단, 설치 운영자가 허용 도메인을 필수로 설정했다면 예외입니다. 자세한 일치 규칙은 [SDK 인증](/ko/sdk/authentication#허용-도메인)에 있습니다.

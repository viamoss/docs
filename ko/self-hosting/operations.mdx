이 페이지는 설치 이후의 작업을 다룹니다. 요청이 느리거나 실패한 이유를 찾는 방법,
설치를 백업하고 복원하는 방법, 보존 작업을 실행하는 방법, 모델 공급자에서 안전
필터를 운영하는 방법입니다.

## 느리거나 실패한 요청 추적하기

채팅을 처리하는 `sdk-backend`에 `OTEL_EXPORTER_OTLP_ENDPOINT`를 OpenTelemetry
수집기의 기본 URL로 설정하세요. `dashboard-backend`와 워커의 스팬도 필요하면
그쪽에도 설정하세요. 설정하지 않으면 텔레메트리는 꺼져 있습니다.

| | |
|---|---|
| 프로토콜 | HTTP를 통한 OTLP. 트레이스, 메트릭, 로그는 각각 `<endpoint>/v1/traces`, `<endpoint>/v1/metrics`, `<endpoint>/v1/logs`로 갑니다. |
| `service.name` | 두 백엔드는 `moss-backend`, 워커는 `moss-worker` |
| 들어오는 트레이스 컨텍스트 | 게이트웨이가 보낸 W3C `traceparent` 헤더를 이어받으므로 Moss의 스팬이 고객사 트레이스에 합쳐집니다. |
| 수집 작업 | 워커에서 실행된 작업의 스팬은 그 작업을 시작한 요청에 연결됩니다. |

### 유용한 스팬

채팅 질문의 요청 스팬은 `POST /api/v1/query`입니다(0.17.0부터 로더의 실시간
단계를 쓰면 `POST /api/v1/query/activity`). 그 아래에는 다음 스팬이 있습니다.

| 스팬 | 재는 시간 |
|---|---|
| `session.hydrate` | 채팅 세션 불러오기 |
| `rag.search` | 지식 베이스 검색 |
| `llm.respond` | 답변 만들기: 프롬프트를 구성하고 모델을 호출 |
| `prompt.build` | 모델에 보낼 내용 구성. `llm.respond` 안에 있습니다. |
| `llm.invoke` | 모델 호출. `llm.provider`와 `llm.model` 속성이 붙습니다. 도구를 호출하는 턴(`llm.tool_loop`가 true)에서는 모델 호출 사이의 도구 호출도 포함합니다. |

`llm.invoke`의 시간을 모델과 도구로 나누려면, 아래에서 설명하는 그 턴의
`tool_loop_round` 로그 줄에 있는 `model_latency_ms`와 비교하세요. 그다음
[모델과 응답 시간](/ko/self-hosting/models-and-response-time#시간이-어디에-쓰이는지-확인하기)을
참고하세요.

### 로그

- **형식**: 백엔드는 한 줄에 JSON 객체 하나를 쓰며, 줄마다 `otelTraceID`와
  `otelSpanID`가 있어 로그 줄에서 해당 트레이스로 이동할 수 있습니다. 차트의
  워커도 JSON으로 씁니다(기본 `env`에 `LOG_FORMAT=json`이 있습니다).
  `LOG_FORMAT=pretty`로 하면 읽기 쉬운 텍스트로 씁니다.
- **요청 필드**: 0.17.0부터 요청을 처리하는 동안 백엔드가 쓰는 모든 로그 줄에
  `request_id`가 들어가며, `session_id`와 `turn_id`도 알게 되는 시점부터
  들어갑니다.
- **브라우저에서 보는 요청 ID**: 0.17.0부터 모든 백엔드 응답에 같은 `request_id`를
  담은 `X-Request-ID` 헤더가 있습니다. SDK 경로의 오류 응답과 처리되지 않은 서버
  오류(`500`)에는 `reference`도 들어 있습니다. 세션 ID와 턴 ID이며, 턴이 기록되지
  않았다면 요청 ID입니다.
- **모델 라운드**: 도구를 호출할 수 있는 턴에서는 `sdk-backend`가 모델 호출마다
  `tool_loop_round` 줄을 남기며, 여기에 `session_id`, `round`,
  `model_latency_ms`, 토큰 `usage`, 모델이 요청한 `tool_calls`,
  `tool_result_chars`가 들어 있습니다.
- **수준**: `LOG_LEVEL`(`DEBUG`, `INFO`, `WARNING`, `ERROR` 중 하나, 기본값
  `INFO`). OpenTelemetry로 로그를 내보낸다면 `INFO` 이하로 두세요.

실패한 요청의 브라우저 쪽은 [고급](/ko/sdk/advanced)을 참고하세요.

### 상태 확인

| 경로 | 응답 |
|---|---|
| `GET /health` | 프로세스가 살아 있는 동안 `200`. 차트의 liveness와 readiness 프로브가 이 경로를 씁니다. |
| `GET /health/ready` | 데이터베이스가 응답하는지, 그리고 실행 중인 워커가 Redis를 통해 모든 수집 작업을 실행할 수 있다고 답하는지를 5초 안에 확인합니다. 둘 다 통과하면 `200`, 아니면 의존성별 상태와 함께 `503`을 돌려주며, 5초가 지나면 `dependency check timed out`과 함께 `503`을 돌려줍니다. 오브젝트 스토리지에는 연결하지 않으며, `storage` 항목은 스토리지가 구성되어 있는지만 알려 줍니다. |

## 백업, 복원, 재설치

### 백업할 것

| 데이터 | 저장 위치 | 백업하나요? |
|---|---|---|
| 애플리케이션과 그 설정, 프로시저, 대화, 감사 로그, 관리자가 연동에 입력한 자격 증명(암호화되어 저장됨) | 애플리케이션 데이터베이스(`DATABASE_URL`) | 예. `pg_dump`나 데이터베이스 스냅샷을 쓰세요. |
| 지식 소스와 그 페이지 | 지식 베이스 데이터베이스(`KNOWLEDGE_BASE_DATABASE_URL`). 기본으로는 같은 데이터베이스입니다. | 예 |
| 지식 베이스 이미지 | 오브젝트 스토리지의 워커 `STORAGE_BUCKET` | 예. 답변이 저장된 위치로 이미지를 링크합니다. |
| 스크린샷, 세션 녹화, 페이지 스냅샷 | 오브젝트 스토리지 | 보관하려면 예 |
| `SECRET_ENCRYPTION_KEYS` | `moss-backend`와 `moss-worker` Secret | **항상 백업하세요.** 이 값이 없으면 저장된 연동 자격 증명을 복호화할 수 없어 관리자가 다시 입력해야 합니다. |
| 지식 베이스 검색 벡터 | Pinecone | 필요 없습니다. 각 소스를 새로고침하면 다시 만들 수 있습니다. |
| 수집 작업 큐와 요청 제한 카운터 | Redis | 아니요. 새 Redis에서 잃는 것은 대기 중이던 수집 작업뿐입니다. 중단된 새로고침을 다시 시작하세요. |
| 대시보드 사용자와 역할 | 고객사 ID 공급자 | Moss에서 백업할 것이 없습니다. |

업그레이드 전에는 매번 데이터베이스를 백업하세요. 0.17.0의 마이그레이션은 되돌릴
수 없습니다.

### 복원 또는 재설치

1. **데이터베이스를 복원하세요.** 애플리케이션 데이터베이스와 지식 베이스
   데이터베이스를 따로 둔다면 둘 다 복원합니다.
2. **백업을 만든 차트 버전이나 그 이후 버전을 같은 설정으로 설치하세요.** 특히
   다음이 같아야 합니다.
   - 두 백엔드와 워커의 `SECRET_ENCRYPTION_KEYS`
   - 애플리케이션이 속한 조직인 `ON_PREM_ORG_ID`
   - `global.storageBuckets`와 워커 `STORAGE_BUCKET`의 버킷 이름
   - Pinecone 키와 ID 공급자 설정
3. **마이그레이션 Job이 실행되게 두세요.** 새 파드가 시작되기 전에 두 데이터베이스에
   `alembic upgrade head`를 실행합니다. 이미 그 버전인 데이터베이스에서는 아무것도
   바꾸지 않습니다. 데이터베이스보다 오래된 차트는 설치하지 마세요. 오래된
   마이그레이션 Job은 자신이 모르는 새 데이터베이스에서 멈춥니다.
4. **Pinecone 인덱스를 잃었다면** 같은 이름과 설정으로 다시 만든 뒤(스크립트는
   차트 README의 Vector Store 섹션에 있습니다), 지식 베이스에서 각 소스를
   새로고침하세요. 웹사이트, Document360, Intercom은 **새로고침**, URL 목록은
   **URL 다시 수집**, 마크다운은 **마크다운 재처리**를 쓰세요.
5. **설치를 확인하세요.** 두 백엔드의 `GET /health/ready`가 `200`을 돌려주는지,
   대시보드에 로그인해 애플리케이션이 보이는지, 소스가 Ready로 표시되는지, 채팅에서
   질문 하나가 지식 베이스를 바탕으로 답을 받는지 확인합니다.

## 보존 CronJob

0.17.0부터 애플리케이션 관리자는 **구성 > 데이터 및 개인정보**에서 Moss가 데이터
종류별로 보관하는 기간을 정하고 **자동 삭제**를 켭니다. 관리자 쪽 내용은
[데이터 보존과 삭제](/ko/dashboard/data-privacy)를 참고하세요. 자동 삭제는
기본으로 꺼져 있으며, 기간을 저장해도 아무것도 삭제되지 않습니다. 실제 삭제는
운영자가 구성한 CronJob이 자동 삭제를 켠 애플리케이션에 대해 수행합니다. 같은
작업이 바로 실행되지 못한 사용자별 삭제도 마무리하므로, 자동 삭제를 켠
애플리케이션이 없더라도 구성해 두세요.

1. **데이터베이스 역할을 만드세요.** `roles.enabled: true`이면 마이그레이션 Job이
   `moss_lifecycle`과 `moss_lifecycle_monitor`를 만듭니다. 그렇지 않다면
   `lifecycle.provisionRole: true`를 설정하세요. 이때 마이그레이션 자격 증명에
   `CREATEROLE`이 필요합니다. 그다음 `moss_lifecycle`에 비밀번호나 RDS IAM 같은
   자격 증명을 부여하세요.
2. **`moss-lifecycle` Secret을 만드세요.** 여기에 `moss_lifecycle`로 연결하는
   `LIFECYCLE_DATABASE_URL`(`DATABASE_URL`로 대신하지 않습니다),
   `DATABASE_SCHEMA`, `S3_ENDPOINT`, `S3_REGION`, 그리고 S3 키나 워크로드 ID를
   넣습니다. 버킷 이름은 이 Secret이 아니라 `global.storageBuckets`에 설정하세요.
3. **`lifecycle.enabled: true`를 설정하고** 업그레이드한 뒤,
   `dashboard-backend`를 다시 시작하세요
   (`kubectl rollout restart deploy/<release>-dashboard-backend`). 그래야 데이터 및
   개인정보 화면에 작업이 실행 중으로 표시됩니다.

| 값 | 기본값 | 의미 |
|---|---|---|
| `lifecycle.enabled` | `false` | CronJob을 만듭니다. |
| `lifecycle.schedule` | `*/15 * * * *` | 실행 시점 |
| `lifecycle.expectedIntervalMinutes` | `15` | 실행 간격(분). 실행 없이 간격 두 번에 10분이 지나면 데이터 및 개인정보 화면과 아래 확인 작업이 이 작업을 실행되지 않는 것으로 보고합니다. |
| `lifecycle.maxApplications` | `25` | 한 번 실행에서 처리하는 애플리케이션 수. 자동 삭제를 켠 애플리케이션 수 이상으로 두세요. |
| `lifecycle.check.enabled` | `false` | 매시간 실행되는 두 번째 CronJob인 `run_retention --check`입니다. 자동 삭제를 켠 애플리케이션이 실행되지 않거나, 밀려 있거나, 실패했으면 이 작업이 실패합니다. 이 작업은 `moss_lifecycle_monitor`로 연결하므로, 이 역할에 자격 증명을 부여하고 그 `LIFECYCLE_DATABASE_URL`을 담은 `moss-lifecycle-monitor` Secret을 만드세요. 스토리지 자격 증명은 필요 없습니다. |

- **실패한 Job은 실제 실패입니다.** 작업이 이미 실행 중이거나, 밀려 있거나, 보류
  중이라서 끝난 실행은 0으로 종료합니다. 마지막 로그 줄은 JSON 요약입니다.
- **버킷이 일치해야 합니다.** 두 백엔드와 CronJob은 같은 `RECORDINGS_BUCKET`,
  `STORAGE_BUCKET`, `DOM_SNAPSHOTS_BUCKET`을 써야 하며, 그러지 않으면 엉뚱한
  버킷을 정리합니다. `global.storageBuckets`에 한 번만 설정하세요. 서로 다르면
  `helm template`이 실패합니다.
- **네트워크**: 이 Job에는 Postgres, 오브젝트 스토리지, DNS가 필요합니다.
- **감사 이벤트와 삭제 기록**은 따로 보존 기간이 있으며, `dashboard-backend`에
  설정합니다. 정리는 CronJob 없이 `dashboard-backend`가 매일 직접 합니다.
  - `AUDIT_RETENTION_DAYS`(기본값 `365`). 애플리케이션 설정으로는 바꿀 수 없으며,
    법적 보존 중인 애플리케이션은 모든 이벤트를 유지합니다.
  - `DELETION_PROOF_RETENTION_DAYS`: 완료된 사용자별 삭제 요청을 보관하는 기간.
    설정하지 않으면 계속 보관합니다.
  - `AUDIT_MINIMUM_DAYS`(0.17.0부터, 설정하지 않으면 0): 사용자의 데이터를 삭제할
    때, 그 사용자에 관한 애플리케이션의 관리자 감사 이벤트(내용 없음) 중 이 기간보다
    최근 것은 남깁니다. 이 값이 `AUDIT_RETENTION_DAYS`나 설정된
    `DELETION_PROOF_RETENTION_DAYS`보다 크면 `dashboard-backend`가 시작하지
    않습니다.
  - 정리 작업에는 감사 이벤트에 대한 `DELETE` 권한이 있는 데이터베이스 역할이
    필요합니다. 모든 작업에 데이터베이스 역할 하나를 쓴다면 그 역할에 권한이
    있습니다. `dashboard-backend`를 최소 권한 역할로 실행한다면, 차트 README의
    `MAINTENANCE_DATABASE_URL` 항목에 설명된 대로 `MAINTENANCE_DATABASE_URL`이
    `moss_maintenance` 역할로 연결하게 설정하세요. 그러지 않으면 정리 작업이
    실패하고 감사 로그가 계속 늘어납니다.
- **다루지 않는 것**: 내보낸 텔레메트리, 데이터베이스 백업, Moss 밖의 사본.
  Moss에서 삭제한 데이터도 백업에는 그 백업이 만료될 때까지 남습니다.

차트 README의 Data retention 섹션에는 규모 산정 규칙과 단계가 있습니다. 법적
보존과 최소 보존 기간은 운영자가 `dashboard-backend`에서
`python -m scripts.retention_operator`로 데이터베이스 소유자 자격 증명을 써서
설정합니다. 운영자 가이드는 Moss에 요청하세요.

## 클라우드 안전 필터와 함께 운영하기

Moss는 안전 필터를 구성하지 않습니다. Model Armor나 Gemini의 안전 설정은 고객사의
Google Cloud 프로젝트에서 켜며, Moss의 요청도 다른 요청과 똑같이 필터를 거칩니다.

0.16.24부터 필터가 요청이나 그 답변을 차단하면 Moss는 다음과 같이 동작합니다.

- "A safety filter blocked this request, so I can't answer it. If it keeps
  happening on this page, please contact your administrator."라고 답합니다.
- 다시 물어도 다시 차단되므로 재시도하지 않습니다.
- 턴을 실패가 아니라 차단으로 기록하고, 세션에 차단 단계를 표시합니다.
- 단계(요청 또는 답변)와 `MODEL_ARMOR`나 `SAFETY` 같은 공급자의 사유를 로그에
  남기며, 차단된 내용은 남기지 않습니다.

Moss는 Vertex AI와 Gemini API의 Gemini 응답에서 이 차단 신호를 읽습니다.

페이지 텍스트와 도움말 문서에 숨은 지시를 Moss가 어떻게 다루는지는
[보안 개요](/ko/security/overview)를 참고하세요.

## 자주 묻는 질문

**느린 요청은 어떻게 추적하나요?**
`sdk-backend`에 `OTEL_EXPORTER_OTLP_ENDPOINT`를 설정하고 `POST /api/v1/query`
아래의 스팬을 비교하세요. 0.17.0부터는 `X-Request-ID` 응답 헤더로 로그에서 찾을
`request_id`를 알 수 있습니다.

**무엇을 백업해야 하나요?**
데이터베이스와 `SECRET_ENCRYPTION_KEYS`입니다. 스크린샷과 녹화를 보관하려면
오브젝트 스토리지도 백업하세요. Pinecone 벡터는 다시 만들 수 있고, Redis에는
오래 남길 데이터가 없습니다.

**데이터베이스를 복원했습니다. 따로 초기화할 것이 있나요?**
없습니다. 같은 차트 버전이나 그 이후 버전을 같은 설정과 Secret으로 설치하세요.
이미 최신인 데이터베이스에서 마이그레이션 Job은 아무것도 바꾸지 않습니다.

**데이터 및 개인정보 화면에 보존 작업이 실행되지 않는다고 나옵니다. 왜 그런가요?**
보존 CronJob을 구성하지 않았거나, `lifecycle.enabled: true`를 설정한 뒤
`dashboard-backend`를 다시 시작하지 않았기 때문입니다.
[보존 CronJob](#보존-cronjob)을 참고하세요.

**Model Armor를 차단 모드로 두어도 안전한가요?**
Moss는 차단된 요청에 분명한 메시지로 답하고, 재시도하지 않으며, 턴을 차단으로
기록합니다. 그래서 사용자가 아무 답도 받지 못한 채 남지는 않습니다.

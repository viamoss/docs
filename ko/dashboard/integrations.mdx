**구성 > 연동**에서 애플리케이션을 외부 서비스에 연결합니다. 카드는 다섯 개이며 두 그룹으로 나뉩니다.

- **지식 소스**: [Document360](#document360)과 [Intercom](#intercom)은 도움말 문서를 지식 베이스로 가져옵니다. Intercom은 사용자를 지원팀에 연결하는 데도 씁니다.
- **액션 및 API**: [커스텀 API 액션](#커스텀-api-액션), [MCP 서버](#mcp-서버), [Zendesk](#zendesk)는 프로시저가 사용자를 대신해 작업하는 도구입니다. 자체 API를 호출하고, MCP 서버의 도구를 호출하고, 지원 티켓을 접수합니다.

구성 페이지는 관리자만 사용할 수 있습니다. 이 페이지의 모든 설정은 애플리케이션 하나에 적용되므로, 필요한 애플리케이션마다 따로 설정하세요.

<Note>
    이 페이지의 도구는 **게시된 프로시저**를 통해 사용됩니다. 프로시저는 쓸 수 있는 도구를 **사용할 수 있는 도구**에 지정하며, 어시스턴트는 그 프로시저가 실행 중일 때만 도구를 호출합니다. 단 하나의 예외는 아래에서 설명하는 Zendesk 또는 Intercom으로의 기본 상담 연결입니다. [프로시저](/ko/dashboard/procedures)를 참고하세요.
</Note>

<Note>
    **MCP 서버** 카드는 Moss가 **고객사의** MCP 서버에 있는 도구를 호출하게 합니다. 외부 AI 어시스턴트(데스크톱 채팅 앱 등)가 Moss에 연결하는 방법은 이것이 아니라 [AI 어시스턴트](/ko/dashboard/ai-assistants)입니다.
</Note>

## Document360

**Document360** 카드에는 Moss가 Document360 문서를 가져올 때 쓰는 자격 증명을 저장합니다. **API token**을 입력하세요. Project Versions, Categories, Articles에 GET 권한이 있는 v2 API 토큰을 쓰거나, 0.17.0부터는 enhanced(v3) API 키를 쓸 수 있습니다. v3 키에는 가져올 워크스페이스에 접근할 수 있는 Draft writer 또는 Editor 콘텐츠 역할이 필요합니다. **Host**를 고르세요(Default, US, 또는 직접 입력하는 `apihub.<region>.document360.io`). **Save**를 누른 다음 **Test connection**을 누르세요. 그다음 **콘텐츠 > 지식 베이스**에서 문서를 소스로 추가합니다. 소스를 가져오고 새로 고치는 방법은 [지식 베이스](/ko/dashboard/knowledge-base)에서 설명합니다.

## Intercom

<Info>
    0.17.0에서 새로 추가되었습니다.
</Info>

**Intercom** 카드는 Intercom 워크스페이스를 연결합니다. 하는 일은 두 가지입니다.

1. **헬프 센터 문서를 지식 소스로 사용.** 연결한 뒤 **콘텐츠 > 지식 베이스**에서 **Add Content > Intercom**으로 문서를 추가합니다. [지식 베이스](/ko/dashboard/knowledge-base)를 참고하세요.
2. **사용자를 지원팀에 연결.** 프로시저가 허용하거나 Intercom이 애플리케이션의 지원 창구일 때, 채팅 안의 Intercom 대화로 사용자를 지원팀에 넘깁니다.

### Intercom 연결

1. **구성 > 연동 > Intercom**을 엽니다.
2. **Access token**을 붙여 넣습니다. 토큰은 Intercom의 **Settings > Integrations > Developer Hub > 해당 앱 > Authentication**에서 만듭니다. 문서를 가져오려면 토큰이 헬프 센터 문서와 컬렉션을 읽을 수 있어야 합니다. 지원팀 연결에도 이 토큰을 쓰며, 대화를 열고, 답장하고, 내부 메모를 남기고, 태그를 달고, 속성을 설정하고, 팀에 배정하고, 읽음으로 표시합니다.
3. **Workspace region**을 고릅니다. **US**(`api.intercom.io`), **EU**(`api.eu.intercom.io`), **Australia**(`api.au.intercom.io`) 중 하나입니다. 저장할 때 이 리전을 기준으로 토큰을 확인합니다.
4. **Save**를 누릅니다. 그다음 **Test connection**을 누르면 Moss가 볼 수 있는 헬프 센터 컬렉션 수가 표시됩니다.

**Clear**는 저장된 토큰을 지웁니다. 이미 가져온 소스는 남지만, 토큰을 다시 입력할 때까지 Intercom에서 가져오기는 실패합니다. 지원팀 연결도 멈추고, **Handoff team** 설정도 사라집니다.

### 사용자를 지원팀에 연결하기

아래 설정은 토큰을 저장하면 나타납니다.

| 설정 | 하는 일 |
|---|---|
| **Handoff team** | 사용자가 상담원을 찾을 때 대화를 배정할 Intercom 팀입니다. Intercom Workflow가 이미 새 대화를 분배한다면 **Let my Intercom Workflow route it**을 고르세요. Moss는 두 가지를 동시에 하지 않습니다. |
| **Conversation attributes** | 워크스페이스에 있는 Sentiment 또는 Urgency 목록 속성마다 스위치가 하나씩 있습니다. 사용자가 상담원을 찾으면 Moss가 대화를 판정해 켜 둔 속성을 채우므로, Intercom 규칙에서 이 값을 활용할 수 있습니다. 직접 만든 규칙에 맡기려면 해당 스위치를 끄세요. 워크스페이스에 그런 속성이 없으면 Moss는 아무것도 쓰지 않습니다. |
| **곧바로 연결할 조건** | **감정**(긍정, 중립, 부정)과 **긴급도**(높음, 보통, 낮음)에 대한 조건입니다. Moss가 메시지마다 판정하고, 조건에 맞으면 AI가 답하지 않고 곧바로 Intercom 대화를 엽니다. **조건 저장**을 누르세요. |

조건은 애플리케이션의 기본 상담 연결이 Intercom일 때만 동작합니다. 다른 곳으로 연결된다면 카드에 그렇게 표시되고 조건은 꺼집니다. Zendesk **티켓 접수**도 **실제 접수**로 켜져 있으면 프로시저마다 넘길 곳을 정합니다. 프로시저의 **사용할 수 있는 도구 > 기본 제공**에서 `intercom_conversation` 또는 `zendesk_ticket`을 허용하세요.

Moss는 Intercom에서 사용자를 연락처로 찾습니다. Intercom 연락처의 `external_id`가 Moss 토큰의 `sub` 클레임에 있는 사용자 ID(페이지가 `userId`로 넘기는 값과 같은 값)여야 합니다. Moss는 연락처를 만들지 않습니다. 일치하는 연락처가 없으면 어시스턴트는 채팅에서 지원팀에 연결할 수 없다고 사용자에게 알립니다.

## 커스텀 API 액션

**커스텀 API 액션** 카드는 고객사의 HTTP API를 연결합니다. **커넥션**에는 베이스 URL과 자격 증명을 저장하고, 커넥션에 속한 **액션** 하나하나가 어시스턴트가 호출할 수 있는 작업 하나입니다(예: `track_shipment`).

### 커넥션 추가

**커넥션 추가**를 누르고 시작 방법을 고릅니다.

- **OpenAPI 스펙 가져오기**: OpenAPI 3.x JSON 스펙을 붙여 넣거나 URL을 입력하고 **스펙 분석**을 누른 뒤, 원하는 오퍼레이션을 선택하고 **선택 항목 가져오기**를 누릅니다. 오퍼레이션마다 액션이 하나씩 만들어집니다.
- **직접 입력**: 아래 필드를 채우고 **커넥션 생성**을 누른 다음, 커넥션 페이지에서 액션을 추가합니다.

| 필드 | 설명 |
|---|---|
| **표시 이름** | 대시보드에 보이는 이름입니다(예: "Shipping API"). |
| **커넥션 이름** | 프로시저에서 참조하는 식별자입니다(예: `shipping_api`). 애플리케이션 안에서 고유해야 합니다. |
| **인증 방식** | **없음**, **Bearer 토큰**(**Bearer 토큰** 입력), **API 키**(**헤더 이름**과 **키**), **기본 인증**(**사용자 이름**과 **비밀번호**) 중 하나입니다. 저장된 비밀 값은 "등록됨 — 비워 두면 그대로 유지됩니다"로 표시됩니다. 인증 방식을 바꾸면 저장된 자격 증명이 삭제됩니다. |
| **베이스 URL** | 공개 호스트의 `https://` URL이어야 합니다. 그 외의 URL은 요청을 만들어 보여 주기만 하고 전송하지 않습니다. |

### 액션 추가

커넥션 페이지에서 **액션 추가**를 누릅니다.

| 필드 | 설명 |
|---|---|
| **이름** | 어시스턴트가 호출할 때 쓰는 이름입니다. 영문, 숫자, 밑줄만 씁니다. |
| **표시 이름** | 대시보드에 보이는 이름입니다. |
| **설명** | 어시스턴트가 이 설명을 읽고 언제 액션을 호출할지 판단합니다. 모델이 읽는다고 생각하고 쓰세요. |
| **메서드**와 **경로** | 베이스 URL 기준의 엔드포인트입니다(예: `GET /track/shipments`). |
| **요청 필드** | 어시스턴트가 채우는 값마다 **필드 이름**, **전송 위치**(쿼리, 경로, 헤더, 본문. 0.17.0부터는 파일도 가능: 사용자가 채팅에 첨부한 파일을, 사용자가 해당 단계를 확인하면 multipart 파트로 보냅니다. 파일 첨부는 베타 채팅 옵션이며 [외관](/ko/sdk/appearance)을 참고하세요), **타입**(텍스트, 숫자, 정수, 예 / 아니요), **필수** 여부, 그리고 어시스턴트가 읽고 무엇을 넣을지 판단하는 **설명**을 지정합니다. |
| **배치 규칙** | 선택 사항이며 0.17.0부터 쓸 수 있습니다. 어시스턴트가 여러 액션을 한 번에 실행할 때, 확인 카드를 보여 주기 전에 검사합니다. **앞 단계 결과로 채우기**(같은 배치에서 앞선 액션의 결과로 필드 값을 채움), **id 존재 확인**(목록 액션의 결과에 id가 없으면 배치를 멈춤), **여러 필드 중 하나 필수**가 있습니다. |

이름이 `company_id`, `tenant_id`, `org_id`, `organization_id`인 필드는 어시스턴트가 무엇을 쓰든 사용자 토큰에 담긴 로그인한 사용자의 회사로 채워집니다. `user_id` 필드는 로그인한 사용자여야 합니다. [페이지에서 전달해야 하는 값](#페이지에서-전달해야-하는-값)을 참고하세요.

### 드라이 런과 실제 호출

새 커넥션은 **드라이 런** 상태입니다. Moss는 요청을 만들어 기록하지만 보내지는 않으며, 어시스턴트는 그 단계를 수행하지 못했다고 사용자에게 알립니다. 준비가 되면 커넥션 페이지에서 **활성화**를 켜세요. 그때부터 액션이 실제 API를 호출합니다. 커넥션 상태는 **실제 호출**, **드라이 런**, **인증 정보 필요**, **지원되지 않는 URL** 중 하나로 표시됩니다.

아무것도 호출하지 않고 액션을 확인하려면 액션을 열고 **테스트**를 누른 뒤, **테스트 입력값**을 넣고 **드라이 런 테스트 실행**을 누르세요. Moss가 보낼 요청이 **요청 (전송되지 않음)** 항목에 표시됩니다.

읽기 액션(`GET`, `HEAD`)은 어시스턴트가 호출하는 즉시 실행됩니다. 0.17.0부터 그 밖의 메서드는 데이터를 바꾸는 것으로 취급합니다. 어시스턴트가 확인 카드에 올리고, 사용자가 확인하기 전에는 아무것도 보내지 않습니다. 커넥션 페이지의 **최근 문제**(0.17.0 신규)에는 실패한 단계가 표시됩니다.

## MCP 서버

<Info>
    0.17.0에서 새로 추가되었습니다.
</Info>

**MCP 서버** 카드는 애플리케이션에 MCP 서버 하나를 연결합니다. Moss가 서버의 도구를 이름, 설명, 파라미터와 함께 불러오며, 프로시저는 이 도구를 API 액션처럼 쓸 수 있습니다.

### 서버 연결

1. **구성 > 연동 > MCP 서버**를 엽니다.
2. **표시 이름**과 **MCP URL**을 입력합니다. URL은 공개 호스트의 `https` 주소여야 합니다.
3. Moss가 서버에 로그인하는 방식(**로그인 방식**)을 고릅니다.

   | 로그인 방식 | 이럴 때 사용 | 입력 항목 |
   |---|---|---|
   | **없음** | 서버에 자격 증명이 필요 없을 때 | 없음 |
   | **Bearer 토큰** | 모든 사용자에게 토큰 하나로 충분할 때 | **Bearer 토큰** |
   | **세션 브리지** | 사용자마다 본인 자격으로 서버에서 작업해야 할 때. 사용자는 각자 호스트 페이지를 통해 로그인합니다. | **토큰 엔드포인트**, **브리지 grant type**, **브리지 코드 파라미터 이름**, **로그인 클라이언트 ID**와 **로그인 클라이언트 시크릿**, **교환 클라이언트 ID**와 **교환 클라이언트 시크릿**, 그리고 선택 항목인 **Scope**(공백으로 구분) |

4. **연결**을 누릅니다.

**없음**이나 **Bearer 토큰**이면 **지금 도구 불러오기**를 눌러 도구를 불러오세요. **세션 브리지**이면 로그인한 사용자의 세션이 처음 연결될 때 도구를 불러오고, 세션이 연결될 때마다 새로 고칩니다.

**세션 브리지**는 이렇게 동작합니다. 페이지가 SDK의 `getBridgeCode`로 백엔드에서 받은 일회용 코드를 Moss에 넘깁니다. Moss는 서버 고유의 grant type과 코드 파라미터로 **토큰 엔드포인트**에서 이 코드를 교환하고(로그인 클라이언트 사용), 그 결과를 표준 OAuth 토큰 교환(RFC 8693, 교환 클라이언트 사용)으로 MCP URL용 토큰과 바꿉니다. 클라이언트 시크릿은 Moss 서버 밖으로 나가지 않습니다.

### 페이지에서 전달해야 하는 값

- **로그인한 사용자.** 도구 호출은 세션 JWT의 사용자로서 실행됩니다. [인증](/ko/sdk/authentication)을 참고하세요.
- **도구가 회사를 인자로 받는다면, 사용자의 회사.** Moss는 JWT의 `metadata` 클레임에 있는 `company_id`(또는 `companyId`)로 회사 인자를 채웁니다. 브라우저가 보낸 값은 쓰지 않습니다. 토큰에 회사가 없으면 회사가 필요한 호출은 보내지 않습니다.
- **`getBridgeCode`(세션 브리지일 때만).** 백엔드에서 새 일회용 코드를 받아 반환하는 함수입니다. 세션에 MCP 토큰이 없거나 토큰이 1분 안에 만료될 때, Moss는 메시지를 보내기 전과 확인된 액션을 실행하기 전에 새 코드를 요청합니다. SDK 0.17.0에서 새로 추가되었습니다.

    ```tsx
        const res = await fetch('/api/moss/bridge-code', { method: 'POST' });
        if (!res.ok) throw new Error(`Bridge code request failed: ${res.status}`);
        return res.text();
      },
    }}>
      {children}
    </AgentProvider>
    ```
  </Tab>

`getBridgeCode`가 실패하거나 서버가 코드를 거부해도 메시지는 그대로 진행됩니다. 도구 호출만 실패하고, 문제는 **최근 문제**에 표시됩니다.

### 도구와 인자

커넥션 페이지는 서버의 도구를 두 그룹으로 나눠 보여 줍니다.

- **읽기 전용**: 서버가 읽기 전용으로 표시한 도구(MCP `readOnlyHint` 어노테이션)입니다. 어시스턴트가 필요할 때 바로 호출합니다.
- **데이터 변경 가능**: 그 밖의 모든 도구입니다. 어시스턴트가 이 호출을 확인 카드로 제안하며, 사용자가 확인하기 전에는 아무것도 실행되지 않습니다.

인자마다 **값 출처**에서 값을 어디서 가져올지 정합니다.

| 출처 | 의미 |
|---|---|
| **기본 규칙**(기본값) | `company_id`, `tenant_id`, `org_id`, `organization_id`에는 로그인한 사용자의 회사가 들어가고, `user_id`는 로그인한 사용자여야 하며, 나머지는 모델이 쓴 값입니다. |
| **로그인한 사용자의 회사** | 항상 사용자 토큰의 회사입니다. `account_id`처럼 다른 이름의 회사 인자에 쓰세요. |
| **로그인한 사용자** | 항상 로그인한 사용자입니다. |
| **모델이 쓴 값** | 어시스턴트가 쓴 값을 그대로 씁니다. |

입력 스키마에 `"contentEncoding": "base64"`가 지정된 인자에는, 사용자가 확인한 단계에서 사용자가 채팅에 첨부한 파일이 들어갑니다. 모델은 이 값을 쓰지 않습니다. 파일 첨부는 베타 채팅 옵션입니다. [외관](/ko/sdk/appearance)을 참고하세요.

도구 이름이 API 액션 이름과 같으면 API 액션이 그 이름을 쓰고 MCP 도구는 쓰이지 않으며, 페이지에 그렇게 표시됩니다. API 액션의 이름을 바꾸거나, 서버에서 도구 이름을 겹치지 않게 하세요.

**도구 변경 이력**에는 서버에서 추가, 삭제, 변경된 도구가 기록됩니다. 프로시저가 쓰는 도구를 서버가 더 이상 제공하지 않으면 페이지에 경고가 표시됩니다. 이는 Moss 오류가 아니라 서버의 변경입니다. 서버가 다시 제공하거나 프로시저에서 빼기 전까지 프로시저는 그 도구 없이 동작합니다.

### 드라이 런과 실제 호출

새 커넥션은 드라이 런 상태입니다. 도구 호출을 기록만 하고 보내지 않으며, 어시스턴트는 그 단계를 수행하지 못했다고 사용자에게 알립니다. 준비가 되면 **실제 호출**을 켜세요. 그때부터 도구가 실제 서버를 호출하고 결과를 받아옵니다. 끄면 다시 드라이 런으로 돌아갑니다.

### 문제가 생겼을 때

**최근 문제**에는 실패한 호출이, 그 문제를 고칠 수 있는 쪽과 함께 표시됩니다.

| 표시 | 고칠 쪽 |
|---|---|
| **MCP 서버** | MCP 서버의 오류나 변경입니다. 서버 운영자에게 확인하세요. |
| **연결 설정** | 이 페이지의 설정이나 호스트 페이지의 `getBridgeCode`입니다. |
| **Moss** | Moss 쪽 오류입니다. Moss에 알려 주세요. |

**연결 해제**를 누르면 커넥션이 삭제됩니다. 프로시저의 MCP 도구는 남지만, 서버를 다시 연결하기 전까지는 호출할 수 없습니다.

### 프로시저에서 도구 사용

프로시저 편집기의 **사용할 수 있는 도구 > MCP 도구**에서 도구를 고르거나, 프로시저 본문에 `@`를 입력해 도구를 넣으세요. [프로시저](/ko/dashboard/procedures)를 참고하세요.

## Zendesk

**Zendesk** 카드는 프로시저가 사용자를 대신해 Zendesk 지원 티켓을 접수하게 합니다. 티켓을 누가 접수할지 고릅니다.

| | **직접** | **호스트 위임** |
|---|---|---|
| Zendesk를 호출하는 쪽 | Moss가 여기 저장한 API 토큰으로 호출 | 고객사 백엔드가 페이지의 `onSupportTicket` 콜백을 통해 호출 |
| Moss가 저장하는 자격 증명 | 서브도메인, API 사용자 이메일, API 토큰 | 서브도메인만 |
| 사용자에게 보이는 것 | 어시스턴트가 채팅에서 사용자의 이메일과 문제를 물은 뒤 접수 | 어시스턴트가 카드에 티켓 초안을 보여 주고, 사용자가 검토하고 수정해 제출 |
| 요청자 | 사용자가 채팅에서 알려 준 이메일, 또는 페이지가 넘긴 `userMetadata`의 `email` | 고객사 백엔드가 자체 세션에서 붙임 |
| Moss가 티켓 양식을 읽는 방법 | 고객사 자격 증명으로 | 엔드유저처럼 익명으로 |
| 필요한 코드 | 없음 | [지원 티켓 핸드오프](/ko/sdk/support-ticket-handoff) |

Moss가 작성하는 모든 티켓에는 두 방식 모두 Zendesk 태그 `moss-created`가 붙습니다. Moss를 거쳐 들어온 티켓을 찾고, 분배하고, 집계할 때 쓰세요.

### Zendesk 연결

1. **구성 > 연동 > Zendesk**를 엽니다.
2. **생성 방식**을 고릅니다. **직접 — Moss가 고객사 Zendesk 자격 증명으로 티켓을 생성** 또는 **호스트 위임 — 고객사 백엔드가 생성하고, Moss는 자격 증명을 저장하지 않음** 중 하나입니다.
3. **서브도메인**을 입력합니다. 계정 이름만 넣으세요. 예를 들어 `acme.zendesk.com`이면 `acme`입니다.
4. **직접** 방식이면 **API 사용자 이메일**과 **API 토큰**을 입력합니다. 토큰은 Zendesk의 **관리 센터 > 앱 및 통합 > Zendesk API > 토큰 액세스**에서 만듭니다. 티켓은 이 사용자 계정으로 접수됩니다.
5. 선택 사항: [**세션 참조 필드**](#세션-참조-필드)를 입력합니다.
6. **연결 테스트 및 연결**을 누릅니다. Moss가 연결을 확인한 뒤(직접 방식은 자격 증명이 유효한지, 호스트 위임 방식은 엔드유저 티켓 양식을 익명으로 읽을 수 있는지) 티켓 양식을 읽어 옵니다.
7. **티켓 접수** 페이지를 열어 어시스턴트가 어떤 필드를 채우고 사용자에게 무엇이 보이는지 확인합니다. [티켓 접수 페이지](#티켓-접수-페이지)를 참고하세요.
8. **티켓 접수**를 **실제 접수**로 바꿉니다.

새 연결에서 티켓 접수는 **끄기** 상태로 시작하므로, 켜기 전까지는 아무것도 제안되지 않습니다.

**호스트 위임** 방식이면 페이지에 `onSupportTicket` 콜백도 필요하고, 티켓은 고객사 백엔드가 접수합니다. [지원 티켓 핸드오프](/ko/sdk/support-ticket-handoff)를 참고하세요. 아래의 **브로커 연동 규격** 페이지에서 개발자가 백엔드로 무엇을 전달받는지 정확히 볼 수 있습니다.

### Zendesk 패널

연결하면 패널에 상태(**연결됨**, **접수 꺼짐**, **중지됨**, **연결 안 됨**), **티켓 접수** 스위치, 그리고 **계정**, **방식**, **세션 참조 필드**, **스키마**(**자격 증명으로 조회** 또는 **익명으로 조회**), 확인할 변경이 있는지 함께 보여 주는 **마지막 동기화**, **연결 테스트** 항목이 표시됩니다(**계정**과 **세션 참조 필드**는 0.17.0에서 추가됨). **연결 테스트**를 누르면 연결을 다시 확인합니다.

0.17.0부터 **연결 설정 편집**에서 방식, 서브도메인, API 사용자, 세션 참조 필드를 바꿀 수 있습니다. **연결 테스트 후 저장**을 누르세요. 직접 방식에서는 서브도메인과 API 사용자를 바꾸지 않는 한 API 토큰을 비워 두면 저장된 토큰이 유지됩니다. **연결 설정 편집**으로 저장하면 티켓 접수 설정과 티켓 접수 페이지의 구성은 그대로 유지됩니다.

**연결 해제**를 누르면 연결이 삭제됩니다. 저장된 서브도메인(직접 방식이면 API 사용자와 토큰도), 티켓 접수 설정, 세션 참조 필드, 고정값을 포함한 티켓 접수 페이지의 구성이 모두 지워집니다. 다시 연결하면 티켓 접수는 **끄기**, 구성은 기본값에서 시작합니다. Zendesk 티켓을 접수하는 프로시저는 다시 연결할 때까지 멈춥니다.

### 티켓 접수 켜고 끄기

**티켓 접수** 스위치 하나로 Moss의 티켓 기능 전체를 켜고 끕니다.

| 상태 | 효과 |
|---|---|
| **실제 접수** | 티켓이 실제로 Zendesk에 접수됩니다. |
| **끄기** | Moss가 티켓 생성을 제안하지 않습니다. 모든 프로시저와 기본 상담 연결에서 티켓 도구가 빠지고, 이미 화면에 떠 있는 티켓 카드도 제출할 수 없습니다. 프로시저의 티켓 단계는 그대로 남으므로, 다시 실제 접수로 바꾸면 복구됩니다. |
| **중지됨**(자동) | Zendesk 양식이 바뀌어 Moss가 접수를 보류한 상태입니다. 원인을 해결할 때까지 아무것도 보내지 않습니다. [Zendesk 양식이 바뀔 때](#zendesk-양식이-바뀔-때)를 참고하세요. |

끄기는 드라이 런이 아닙니다. 꺼져 있는 동안 Moss는 티켓 초안을 아예 만들지 않습니다. 두 방식 모두에서 티켓이 제안되는 조건 전체는 [Moss가 티켓을 제안하는 조건](/ko/sdk/support-ticket-handoff#moss가-티켓을-제안하는-조건)을 참고하세요.

### 티켓 접수 페이지

Zendesk 패널에서 **티켓 접수** 페이지를 엽니다. 이 페이지에서는 어시스턴트가 어떤 필드를 채우는지, 티켓 카드에서 사용자에게 무엇이 보이는지, 양식을 어떻게 동기화하는지 확인합니다. 상단에는 양식을 마지막으로 동기화한 시점, 확인할 스키마 변경, 접수가 켜져 있는지가 표시됩니다. 티켓 카드는 호스트 위임 방식에만 있으므로, 직접 방식에서는 양식과 **채우는 주체** 설정만 의미가 있습니다.

**티켓 양식**에서 티켓을 접수할 Zendesk 양식을 활성 양식 중에서 고릅니다. 다른 양식을 골랐다면 **구성 저장**을 눌러 그 양식의 필드를 불러오세요.

**카드 구성** 탭에서는 양식의 필드마다 위치를 정합니다.

| 위치 | 의미 |
|---|---|
| **카드** | 카드에 바로 표시됩니다. 모든 사용자가 보내기 전에 읽고 수정할 수 있습니다. |
| **자세히** | 한 번 눌러야 보이는 **자세히 보기** 안에 표시됩니다. 여기 있는 필수 필드가 비어 있으면 카드가 이 영역을 펼치고 사용자에게 입력을 요청합니다. |
| **숨김** | Moss가 채워 접수하지만 사용자에게는 보이지 않습니다. Zendesk가 필수로 요구하는 필드인데 어시스턴트가 채우지 못하면 사용자에게 표시됩니다. |
| **백엔드** | 접수 시점에 고객사 백엔드가 채웁니다(호스트 위임 방식). Moss는 이 필드를 초안에서 빼고 값을 보지 않습니다. 백엔드가 자체 생성 요청에 값을 넣으면 Zendesk가 그 요청에서 확인합니다. |

기본적으로 제목과 내용은 카드에, 어시스턴트가 수집하는 필드는 **자세히 보기**에, 나머지는 숨김에 둡니다. 제목과 내용은 항상 어시스턴트가 쓰고 Moss가 반드시 보내므로 **백엔드**에 둘 수 없습니다. 카드에는 양식에서 정한 필드 이름으로, 없으면 **제목**과 **내용**으로 표시됩니다. 개발자는 [`chrome.ticketCard`](/ko/sdk/support-ticket-handoff#카드-문구)로 이 라벨을 바꿀 수 있습니다.

나머지 필드에는 누가 값을 채우는지(**채우는 주체**)도 표시됩니다.

| 채우는 주체 | 의미 |
|---|---|
| **대화 중 수집**(텍스트) 또는 **자동 분류**(드롭다운) | 어시스턴트가 대화 내용으로 채웁니다. |
| **사용자 속성** | 로그인한 사용자의 속성으로 채웁니다(역할 필드). 호스트 위임 방식에서는 **고객사 확인**으로 표시되며, 고객사 백엔드가 자체 세션과 대조해 확인합니다. |
| **고정값** | 직접 정한 고정 값입니다. 고정값 필드에 모두 값을 넣어야 저장할 수 있습니다. |
| **상담원이 입력** | Moss가 채우지 않고 상담원에게 남깁니다. |

어시스턴트가 값을 정하지 못하면, Zendesk가 요구하지 않는 숨김 필드는 티켓에서 빠지고 그 밖의 필드는 빈 채로 사용자에게 보여 직접 채우게 합니다. 호스트 위임 방식에서는 요청자(이름과 이메일)가 사용자에게 보이지 않으며, 고객사 백엔드가 접수 시점에 붙입니다.

모든 필드가 카드에 나타날 수 있는 것은 아닙니다. "Moss가 이 필드에 연결한 역할이 없어 카드에는 절대 나타나지 않습니다"라고 표시된 행은 카드나 **자세히 보기**에 둘 수 없습니다. 이런 필드는 값을 고정하거나 고객사 백엔드가 채울 때만 접수됩니다.

오른쪽의 **사용자에게 보이는 화면** 미리보기는 사용자가 실제로 보게 될 카드입니다. **구성 저장**을 눌러 변경 사항을 적용하거나 **저장된 상태로 되돌리기**를 누르세요.

호스트 위임 방식에서는 **초안 품질** 탭에 최근 30일간 확정된 접수를 기준으로, 필드마다 어시스턴트가 작성한 값이 그대로 Zendesk에 들어간 비율이 낮은 순서로 표시됩니다.

### Zendesk 양식이 바뀔 때

Moss는 매일, 그리고 티켓 접수 페이지에서 **다시 동기화**를 누를 때 양식을 다시 읽습니다. 직접 방식에서는 Zendesk가 접수를 거부했을 때도 다시 읽습니다. 새로 읽은 양식을 직전에 읽은 양식과 비교합니다.

| Zendesk의 변경 | Moss의 처리 |
|---|---|
| 드롭다운 옵션 추가, 선택 필드 추가, 양식 추가, 필드 이름 변경 | 할 일이 없습니다. 동기화할 때 반영됩니다. 다만 Moss는 카드 필드를 제목으로 찾으므로, 필드 이름을 바꾸면 카드에서 빠질 수 있습니다. 이름을 바꾼 뒤에는 카드 구성을 확인하세요. |
| 필드가 필수로 바뀌었거나 새 필수 필드가 생겼는데 티켓 접수 페이지에서 다루지 않는 경우 | **스키마가 변경되었습니다**가 표시되고 접수는 중지되지 않지만, 그 필드가 없는 티켓은 접수할 수 없습니다. 직접 방식에서는 Moss가 그 필드를 채울 수 없으면 티켓을 보내지 않고, 어시스턴트가 사용자에게 지원팀에 문의하라고 안내합니다. 호스트 위임 방식에서는 사용자가 채울 수 있는 행이 카드에 없으면 카드가 표시되지 않습니다. **티켓 접수** 페이지에서 그 필드에 **고정값**을 지정하거나, 호스트 위임 방식이면 **백엔드**에 둔 다음 **구성 저장**을 누르세요. 또는 Zendesk에서 그 필드를 선택 필드로 바꾸세요. |
| 드롭다운에서 옵션 삭제, 또는 대화 중 수집하는 필드의 옵션 변경 | **스키마가 변경되었습니다**가 표시됩니다. 접수는 계속됩니다. |
| 선택한 양식이 삭제되거나 비활성화됨 | 접수를 중지합니다. |
| Moss가 채우는 필드(대화 중 수집 또는 고정값)가 삭제되거나, 비활성화되거나, 타입이 바뀜 | 접수를 중지합니다. |
| 고정값으로 지정한 드롭다운 값이 더 이상 옵션에 없음 | 접수를 중지합니다. |
| 세션 참조 필드를 양식이나 티켓 접수 페이지에서 쓰게 됨 | 접수를 중지합니다. |
| 백엔드가 채우는 필드가 다른 필드의 필수 여부를 결정하게 됨 | 접수를 중지합니다. |

**스키마가 변경되었습니다** 알림은 두 번의 읽기 사이의 차이를 보여 주는 것이라, 처리했든 안 했든 다음 동기화 때 사라집니다. 보이는 즉시 처리하세요.

접수가 중지되면 패널에 **중지됨**이 표시되고 배너에 이유가 나옵니다. 그동안 아무것도 보내지 않습니다. Zendesk나 티켓 접수 페이지에서 원인을 고친 뒤 **다시 동기화**를 누르세요. 동기화에서 막는 원인이 더 이상 없으면 접수가 저절로 재개됩니다.

### 세션 참조 필드

선택 사항이며 두 방식 모두에서 쓸 수 있습니다. Zendesk에 상담원 전용 사용자 지정 필드를 만들고, 그 숫자 ID를 **세션 참조 필드**에 붙여 넣으세요. Moss가 모든 티켓의 이 필드에 채팅 세션 ID를 기록하므로, 상담원이 티켓이 어느 채팅에서 왔는지 찾아갈 수 있습니다. 요청자에게 보이면 안 되므로 이 필드를 엔드유저 양식에는 넣지 마세요. 비워 두면 아무것도 기록하지 않습니다. 양식이나 티켓 접수 페이지에서 이미 쓰는 필드의 ID는 넣을 수 없습니다.

### 브로커 연동 규격

호스트 위임 방식에서 양식이 동기화되면 패널에 **브로커 연동 규격** 링크가 나타납니다. 사용자가 티켓을 제출할 때 고객사 백엔드가 전달받는 내용과 백엔드가 더 채워야 하는 내용이, 양식과 티켓 접수 페이지의 구성을 바탕으로 정리되어 있습니다.

- **전달받는 것**: 콜백, 페이로드 키, 반환해야 하는 결과, 타임아웃.
- **handoffId로 중복을 걸러야 합니다**: 같은 핸드오프가 두 번 도착할 수 있는 이유와 대처 방법.
- **티켓 예시**: `ticket` 객체의 형태(**예시 JSON 복사**).
- **직접 채워야 하는 것**: 요청자처럼 백엔드가 넣어야 하는 필드.
- **필드 목록**: 양식의 필드마다 빠질 수 있는지, 어떻게 채워지는지.

**규격 JSON 내려받기**로 파일로 저장할 수 있습니다. 규격은 양식이나 티켓 접수 페이지의 구성이 바뀌면 함께 바뀝니다. 백엔드가 필드 목록을 따로 가지고 있을 필요는 없습니다. 전달받은 티켓을 그대로 보내고, **직접 채워야 하는 것**에 있는 항목만 더하면 됩니다.

### 자체 호스팅 설치

Moss는 Moss 서버에서 HTTPS로 Zendesk를 호출합니다. 네트워크에서 외부 트래픽이 프록시를 거치거나, 의도적으로 `zendesk.com`을 내부 주소로 해석한다면 운영자가 설정해야 합니다. [네트워크](/ko/self-hosting/network)를 참고하세요.

## 자주 묻는 질문

**Moss가 티켓 접수를 제안하지 않는 이유는 무엇인가요?**
**티켓 접수**가 **실제 접수**여야 하고, 연결이 **중지됨** 상태가 아니어야 하며, 게시된 프로시저가 `zendesk_ticket`을 허용해야 합니다(또는 Zendesk가 기본 상담 연결이어야 합니다). 호스트 위임 방식에서는 페이지가 `onSupportTicket`도 등록해야 합니다. 전체 점검 목록은 [Moss가 티켓을 제안하는 조건](/ko/sdk/support-ticket-handoff#moss가-티켓을-제안하는-조건)에 있습니다.

**Moss가 티켓을 접수하지 않게 하려면 어떻게 하나요?**
Zendesk 패널에서 **티켓 접수**를 **끄기**로 바꾸세요. 모든 프로시저에서 한꺼번에 티켓 제안이 멈추며, 다시 **실제 접수**로 바꾸면 복구됩니다.

**Zendesk 양식이 바뀌었습니다. 무엇을 해야 하나요?**
대개는 할 일이 없습니다. 새 옵션과 새 선택 필드는 다음 일일 동기화 때 반영됩니다. 새 필수 필드가 생겼다면 값을 정해야 티켓을 접수할 수 있습니다. **티켓 접수** 페이지에서 고정값을 지정하거나, 호스트 위임 방식이면 백엔드가 채우게 하세요. 패널에 확인할 변경이나 **중지됨**이 표시되면 **티켓 접수** 페이지를 열어 표시된 문제를 고치고 **다시 동기화**를 누르세요. [Zendesk 양식이 바뀔 때](#zendesk-양식이-바뀔-때)를 참고하세요.

**어떤 티켓이 Moss를 거쳐 들어왔는지 어떻게 알 수 있나요?**
Moss가 작성하는 모든 티켓에는 `moss-created` 태그가 붙습니다. 티켓이 어느 채팅에서 왔는지도 보려면 [세션 참조 필드](#세션-참조-필드)를 추가하세요.

**MCP 서버를 통해 Moss가 우리 제품에서 작업을 하게 하려면 어떻게 하나요?**
[MCP 서버](#mcp-서버) 카드에서 서버를 연결하세요. 사용자마다 본인 자격으로 작업해야 한다면 **세션 브리지**를 고르고 페이지에서 `getBridgeCode`를 넘기세요. 그다음 게시된 프로시저에서 도구를 허용하고 **실제 호출**을 켜세요.

**Document360은 어떤 키를 지원하나요?**
v2 API 토큰, 그리고 0.17.0부터는 enhanced(v3) API 키를 지원합니다. [Document360](#document360)을 참고하세요.

**번들 내보내기**는 애플리케이션 설정을 파일로 저장합니다. **번들 가져오기**는 그 파일로 다른 Moss 설치에 새 애플리케이션을 만듭니다. 스테이징에서 프로덕션으로, 호스팅 서비스에서 자체 호스팅 설치로, 한 리전에서 다른 리전의 두 번째 설치로 옮길 때 씁니다.

가져오기는 항상 새 애플리케이션 ID를 가진 **새** 애플리케이션을 만듭니다. 기존 애플리케이션을 업데이트하거나 덮어쓰지 않습니다.

## 시작하기 전에

- **양쪽 설치 모두에서 관리자 역할이 필요합니다.** [역할](/ko/dashboard/overview#역할)을 참고하세요.
- **두 설치의 메이저 버전과 마이너 버전이 같아야 합니다.** 예를 들어 0.17.x와 0.17.x입니다. 패치 버전은 달라도 됩니다. 0.16.x에서 내보낸 번들은 0.17.x로 가져올 수 없습니다. 원본을 업그레이드한 뒤 다시 내보내세요.
- **번들은 최대 10 MiB입니다.** 번들이 커지는 흔한 원인은 OpenAPI 명세가 큰 API 연결입니다.

## 애플리케이션 내보내기

1. 원본 설치에서 애플리케이션을 열고 **구성 > 일반**으로 이동합니다.
2. **애플리케이션 내보내기** 카드에서 **번들 내보내기**를 누릅니다.

브라우저가 JSON 파일을 내려받습니다. 번들이 10 MiB를 넘으면 내보내기가 거부되며, 무엇을 줄여야 하는지 알 수 있도록 메시지에 가장 큰 섹션이 표시됩니다.

## 번들 가져오기

1. 대상 설치에서 **애플리케이션**으로 이동합니다. 애플리케이션을 열기 전에 보이는 목록입니다.
2. **번들 가져오기**를 누릅니다.
3. **번들 파일**에서 JSON 파일을 고릅니다. Moss가 파일을 확인하고 보고서를 보여 줍니다. 아직 아무것도 생성되지 않습니다.
4. **애플리케이션 이름**은 비워 두면 번들에 기록된 이름을 쓰고, 새 이름을 입력할 수도 있습니다. 이름은 조직 안에서 고유해야 합니다. 이미 쓰는 이름이면 보고서에 표시되며, 다른 이름을 골라야 합니다.
5. **게시 및 활성 상태 유지**를 켤지 정합니다. 기본값은 꺼짐입니다.
    - **꺼짐**: 프로시저는 초안으로, 모니터는 꺼진 상태로 들어오므로 확인하기 전에는 새 설치에서 아무것도 실행되지 않습니다.
    - **켜짐**: 프로시저는 게시 또는 초안 상태를 그대로 유지하고, 모니터도 원래의 켜짐/꺼짐 상태를 유지합니다.
6. 보고서를 읽고 **애플리케이션 생성**을 누릅니다.

가져오기는 전부 성공하거나 전부 취소됩니다. 어느 한 부분이라도 실패하면 아무것도 생성되지 않으므로, 문제를 고친 뒤 다시 실행하면 됩니다. 성공하면 대시보드가 새 애플리케이션의 **구성 > 일반**을 엽니다.

### 보고서에 표시되는 내용

| 섹션 | 알려 주는 내용 |
|------|----------------|
| **버전 확인** | 번들을 내보낸 버전과 이 설치의 버전입니다. |
| **설정 N개가 적용됩니다** | 설정될 항목의 이름입니다. |
| **생성될 항목** | 프로시저, API 연결, 모니터와 그 밖의 객체를 이름별로 보여 줍니다. |
| **안전한 상태로 가져오는 항목** | 가져오기가 번들과 다르게 기록하는 값입니다. 예를 들어 초안으로 들어오는 프로시저가 여기에 나옵니다. |
| **이 환경에 없는 참조** | 가져오기에서 빼야 했던 연결 관계와 그 이유입니다. |
| **이 환경에서 다시 입력해야 하는 항목** | **다시 입력해야 하는 자격 증명**과 **자격 증명 입력 후 직접 생성해야 하는 항목**입니다. 후자는 자격 증명 없이는 만들 수 없었던 객체이며, 사용할 값도 함께 보여 줍니다. |
| **확인이 필요한 값** | 원본 환경을 가리키는 값이라 대상 환경에서는 맞지 않는 경우가 많은 값입니다. |
| **번들에 포함되지 않은 항목** | 내보내기에서 제외된 모든 항목입니다. |

## 함께 옮겨지는 항목

| 애플리케이션의 구성 요소 | 대상 환경에 들어오는 상태 |
|--------------------------|---------------------------|
| **외관**: 브랜딩, 테마 | 내보낸 그대로입니다. |
| **추천 콘텐츠**: 초기 화면, 예외 상태 | 내보낸 그대로입니다. |
| **동작**: 주요 기능 스위치, AI 어시스턴트 프롬프트, 계획 진행 추적, 세션 동작, Interactive Element Whitelist | 내보낸 그대로입니다. |
| **일반**: 언어, 임베딩 모델 | 내보낸 그대로입니다. 임베딩 모델은 가져온 뒤 바꿀 수 없습니다. |
| **설치**: 고급 설정 | 내보낸 그대로입니다. |
| **보안**: 허용 도메인, JWT 클레임 강제, 백엔드 개인정보 필터링 | 내보낸 그대로입니다. 대상 환경에 맞는지 도메인과 클레임을 확인하세요. |
| **데이터 및 개인정보**: 보존 기간 | 기본값에서 바꾼 기간만 옮겨집니다. 나머지는 대상 환경의 기본값을 따릅니다. |
| 프로시저 | **게시 및 활성 상태 유지**를 켜지 않았다면 초안으로 들어옵니다. |
| 커스텀 API 연결과 액션 | 자격 증명 없이, 꺼진 상태로 들어옵니다. |
| Zendesk 연결 | **호스트 위임**: 꺼진 상태로 생성됩니다. **직접**: 생성되지 않습니다. 보고서에 연결을 만들 때 쓸 값이 나오므로, API 사용자 이메일과 토큰을 준비해 직접 만드세요. |
| 모니터 | **게시 및 활성 상태 유지**를 켜지 않았다면 꺼진 상태로 들어옵니다. |
| 인텐트 태그 | 내보낸 그대로입니다. |
| 셀프 힐링 일정 (**제안 > 자동 실행**) | **모니터 자동 채점**을 포함해 항상 꺼진 상태로 들어옵니다. |
| Intercom 인계 규칙 | 내보낸 그대로입니다. |

0.17.0부터는 테마, 세션 동작, 세션 리플레이와 화면 기록 스위치, 고급 설정, 백엔드 개인정보 필터링, 보존 기간도 번들에 포함됩니다. 0.16.x의 번들에는 이 항목들이 빠져 있었습니다.

## 옮겨지지 않는 항목

| 번들에 없는 항목 | 대상 환경에서 할 일 |
|------------------|---------------------|
| 지식 베이스: 소스, 페이지, 업로드한 파일 | **지식 베이스**에서 소스를 다시 추가하고 동기화가 끝나기를 기다리세요. |
| **구성 > 동작**의 **모델** 선택 | 모델을 고르기 전까지 대상 환경의 기본 모델을 씁니다. |
| JWT 서명 키 | **구성 > 보안**에서 키를 생성하거나 등록하세요. |
| API 로그 접근 키 | 외부 도구로 API 로그를 읽는다면 **구성 > 보안**에서 새로 생성하세요. |
| Document360과 Intercom의 자격 증명, Intercom의 인계 팀과 속성 | **구성 > 연동**에서 다시 연결하세요. |
| MCP 서버 연결 | 대상 환경의 MCP 서버를 연결하세요. 그 서버의 도구를 쓰는 프로시저는 도구 이름을 그대로 유지하며, 서버가 해당 도구를 제공하면 동작합니다. |
| API 연결과 Zendesk 연결의 자격 증명 | 다시 입력한 뒤 연결을 켜세요. |
| **API 상세 로그 수집**과 **자동 삭제** | 둘 다 꺼진 상태로 시작합니다. 필요하면 **구성 > 데이터 및 개인정보**에서 켜세요. |
| 법적 보존과 최소 보존 기간 | 각 설치의 운영자가 설정합니다. |
| 세션, 사용자, 분석, 제안, API 로그, 감사 이벤트, 삭제 요청 | 할 일이 없습니다. 원본 설치의 이력입니다. |

대시보드 사용자와 그 역할은 애플리케이션에 속하지 않습니다. 각 설치에서 조직이나 로그인 공급자를 통해 정해집니다.

<Note>
    새 애플리케이션은 원본의 임베딩 모델을 그대로 씁니다. 대상 환경에서 그 모델로 애플리케이션을 만들 수 없으면 가져오기가 거부됩니다. 레거시 모델인 Gemini Embedding 001이 그 예입니다. 새 애플리케이션은 현재 모델을 써야 합니다.
</Note>

## 가져온 뒤 할 일

실제 사용자를 대상 환경으로 보내기 전에 아래 목록을 차례로 확인하세요.

1. **애플리케이션 ID.** **구성 > 일반**에서 새 ID를 복사합니다. 대상 환경용 앱 코드의 `applicationId`나 CDN 스크립트 URL의 `?applicationId=`를 새 ID로 바꾸세요.
2. **서명 키.** **구성 > 보안 > JWT 서명 키**에서 키를 생성하고, 이 환경의 토큰에 서명하는 백엔드에 시크릿을 넘겨주세요. 직접 만든 키 쌍으로 서명한다면, 원본에서 쓰는 공개 키를 **공개 키 등록**으로 그대로 등록할 수 있습니다.
3. **토큰 클레임.** **필수 발급자 (iss)**, **필수 대상 (aud)** 값을 확인하세요. 빈 값은 어떤 발급자나 대상도 허용하므로, 보고서는 비어 있을 때도 이 두 값을 보여 줍니다.
4. **허용 도메인.** 원본의 도메인을 대상 환경의 도메인으로 바꾸세요.
5. **그 밖에 확인할 값.** 보고서의 **확인이 필요한 값**을 하나씩 확인하세요. API 연결의 기본 URL, Zendesk 하위 도메인, 푸터와 추천 글의 링크, **DOM 대상 선택자**와 **로그 레벨** 값이 여기에 나옵니다.
6. **연결.** **구성 > 연동**에서 커스텀 API 연결과 Zendesk의 자격 증명을 다시 입력하고, Document360, Intercom, MCP 서버를 다시 연결한 뒤 연결을 켜세요.
7. **지식 베이스.** 소스를 추가하고 동기화가 끝나기를 기다리세요.
8. **모델.** 대상 환경이 모델 선택지를 제공한다면 **구성 > 동작 > 모델**에서 모델을 고르세요.
9. **프로시저와 모니터.** 상태를 유지하지 않았다면, 실제로 쓸 프로시저를 게시하고 모니터를 켜세요.
10. **자동 실행.** 사용한다면 **제안 > 자동 실행**에서 **자동 실행 사용**과 **모니터 자동 채점**을 켜세요.
11. **데이터 및 개인정보.** 보존 기간을 확인하고, 필요하면 **자동 삭제**와 **API 상세 로그 수집**을 켜세요.
12. **테스트.** 대상 환경에서 앱을 열고 Moss에게 질문해 보세요.

## 가져오기가 거부될 때

| 메시지 | 할 일 |
|--------|-------|
| "Import requires the same major and minor version. Patch releases may differ." | 두 설치를 같은 마이너 버전으로 맞춘 뒤 원본에서 다시 내보내세요. |
| "This bundle carries no platform version" | 정식 출시된 Moss 버전에서 번들을 다시 내보내세요. |
| "This build reports no platform version" | 대상 설치가 자신의 버전을 알려 주지 않는 경우입니다. 대상 설치의 운영자가 `APP_VERSION`을 설정한 뒤 다시 시도합니다. |
| "… 이름의 애플리케이션이 이미 있습니다" | **애플리케이션 이름**에 다른 이름을 입력하세요. |
| "올바른 번들 파일이 아닙니다" | **번들 내보내기**로 만든 JSON 파일을 수정하지 않은 상태로 고르세요. |
| "Bundle exceeds the … byte import limit" | 파일이 10 MiB를 넘었습니다. 원본에서 가장 큰 섹션을 줄인 뒤 다시 내보내세요. |

내보내기와 가져오기는 거부된 가져오기까지 모두 [감사 로그](/ko/security/audit-logging)에 기록됩니다.

## 자주 묻는 질문

**기존 애플리케이션을 번들로 업데이트할 수 있나요?**
아니요. 가져오기는 항상 새 애플리케이션을 만듭니다. 기존 애플리케이션을 교체하려면 새 이름으로 가져와 확인한 뒤, 앱이 새 애플리케이션 ID를 쓰도록 바꾸세요.

**가져온 뒤 연결이 모두 꺼져 있는 이유는 무엇인가요?**
자격 증명은 번들에 절대 담기지 않으므로 모든 연결이 꺼진 상태로 들어옵니다. **구성 > 연동**에서 자격 증명을 다시 입력한 뒤 연결을 켜세요.

**지식 베이스도 함께 옮겨지나요?**
아니요. 대상 환경에서 소스를 다시 추가하세요. [지식 베이스](/ko/dashboard/knowledge-base)를 참고하세요.

**다른 리전에서 두 번째 설치를 운영합니다. 그곳에서 새 애플리케이션 ID와 서명 키가 필요한가요?**
네. 가져온 애플리케이션은 자체 ID를 가지며, 서명 키는 절대 옮겨지지 않습니다. 그 리전의 앱은 새 ID를 써야 하고, 그 리전의 토큰 백엔드는 대상 설치가 아는 키로 서명해야 합니다.

**호스팅 서비스의 애플리케이션 번들을 자체 호스팅 설치로 가져올 수 있나요?**
네. 두 환경의 마이너 버전이 같으면 됩니다.

**대신 코드로 설정을 바꿀 수 있나요?**

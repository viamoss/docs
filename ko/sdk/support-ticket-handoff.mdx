# 지원 티켓 핸드오프

<Info>
    SDK 0.16.0부터 사용할 수 있습니다.
</Info>

Moss 어시스턴트는 대화로 지원 요청 내용을 모으고, Zendesk 티켓 초안을 작성해
사용자가 검토할 수 있도록 카드로 보여 줍니다. 사용자가 제출하면 SDK가 티켓을
**고객사 페이지**에 넘기고, 페이지는 고객사 백엔드를 통해 티켓을 접수합니다.
Moss는 고객사 Zendesk 계정의 자격 증명을 갖지 않으며, 요청자 정보는 고객사
백엔드가 자체 세션에서 붙입니다. 요청자 정보는 Moss를 거치지 않습니다.

이것은 Zendesk 연동의 **호스트 위임** 방식입니다. **직접** 방식에서는 Moss가
대시보드에 저장된 API 토큰으로 직접 티켓을 접수하므로 페이지에 코드가 필요
없습니다. 방식은 관리자가
[구성 > 연동 > Zendesk](/ko/dashboard/integrations#zendesk)에서 고릅니다.

## 설정 순서

1. 관리자가 Zendesk를 **호스트 위임** 방식으로 연결하고, **티켓 접수** 페이지에서
   티켓 카드를 구성합니다. [Zendesk](/ko/dashboard/integrations#zendesk)를
   참고하세요.
2. 게시된 프로시저가 티켓을 허용합니다. 프로시저 편집기의
   **사용할 수 있는 도구 > 기본 제공**에서 `zendesk_ticket`을 선택하세요.
   [프로시저](/ko/dashboard/procedures)를 참고하세요.
3. 페이지에서 `onSupportTicket`을 등록하고(아래 참고), 백엔드가 전달받은 티켓을
   접수합니다. 대시보드의 **브로커 연동 규격** 페이지에 백엔드가 전달받는 내용과
   직접 채워야 하는 내용이 정확히 나와 있습니다.
4. 관리자가 **티켓 접수**를 **실제 접수**로 바꿉니다.

## 동작 방식

1. **수집**: 어시스턴트가 대화에서 티켓 필드를 모읍니다. 값은 Moss가 마지막으로
   동기화한 Zendesk 양식을 기준으로 검증합니다.
2. **검토**: 위젯이 작성된 티켓을 채팅 안에 카드로 보여 줍니다. 사용자는 내용을
   수정한 뒤 제출하거나 취소할 수 있습니다. 카드에는 초안이 만료되는 시각이
   표시됩니다.
3. **핸드오프**: 사용자가 제출하면 Moss가 값을 다시 검사하고, SDK가 등록해 둔
   `onSupportTicket` 콜백을 호출해 티켓과 핸드오프 ID를 넘깁니다.
4. **접수**: 페이지가 두 값을 고객사의 세션 인증 채널로 백엔드에 보냅니다.
   백엔드가 요청자를 붙여 티켓을 접수합니다.
5. **확인**: 콜백이 결과를 반환합니다. 카드는 사용자에게 결과를 보여 주며, 티켓
   번호를 넘기면 함께 표시합니다.

## 콜백 등록

`onSupportTicket`을 등록하는 것은 기능을 지원한다는 신호이기도 합니다. SDK는
세션이 시작되거나 재개될 때 이를 알리고, 호스트 위임 방식에서 Moss는 이를 알린
세션에만 티켓 접수를 제안합니다. 콜백을 등록하지 않은 페이지에는 끝낼 수 없는
흐름이 제안되지 않습니다.

<Tabs>
  <Tab title="npm">
    ```tsx
    import { AgentProvider } from '@viamoss/moss-sdk';
    import type { SupportTicketHandoff, SupportTicketOutcome } from '@viamoss/moss-sdk';

    async function fileTicket({ handoffId, ticket }: SupportTicketHandoff): Promise<SupportTicketOutcome> {
      const res = await fetch('/api/support/moss-handoff', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ handoffId, ticket }),
      });
      if (!res.ok) {
        return { ok: false, errorCode: `HTTP_${res.status}` };
      }
      const filed = await res.json();
      return { ok: true, ticketId: filed.ticketId, ticketUrl: filed.ticketUrl };
    }

    <AgentProvider config={{
      apiUrl: 'https://moss-api.viamoss.ai',
      applicationId: 'YOUR_APP_ID',
      userId: currentUser.id,
      getJwt: () => fetchMossToken(),
      onSupportTicket: fileTicket,
    }}>
      {children}
    </AgentProvider>
    ```
  </Tab>
  <Tab title="CDN script">
    ```html
    <script>
      window.mossSettings = {
        getJwt: () => fetchMossToken(),
        onSupportTicket: async ({ handoffId, ticket }) => {
          const res = await fetch('/api/support/moss-handoff', {
            method: 'POST',
            headers: { 'Content-Type': 'application/json' },
            body: JSON.stringify({ handoffId, ticket }),
          });
          if (!res.ok) return { ok: false, errorCode: 'HTTP_' + res.status };
          const filed = await res.json();
          return { ok: true, ticketId: filed.ticketId, ticketUrl: filed.ticketUrl };
        },
      };
    </script>
    ```
    `window.mossSettings`는 Moss 스크립트를 불러오기 전에 설정하세요.
    [설치](/ko/sdk/installation)를 참고하세요.
  </Tab>
</Tabs>

전송은 콜백이 맡습니다. 애플리케이션에서 평소 쓰는 세션과 CSRF 방식을 그대로
쓰세요. SDK는 고객사의 쿠키를 건드리지 않습니다.

## Moss가 티켓을 제안하는 조건

Moss는 아래 조건이 **모두** 맞을 때만 티켓을 제안합니다. 티켓이 제안되지 않으면
순서대로 확인하세요. 4번과 5번은 호스트 위임 방식에만 해당하고, 나머지는 두 방식
모두에 해당합니다.

| # | 조건 | 확인할 곳 |
|---|---|---|
| 1 | Zendesk가 연결되어 있습니다(직접 방식이면 API 사용자와 토큰도 저장되어 있어야 합니다). | **구성 > 연동 > Zendesk**: 패널에 계정과 **방식**이 표시됩니다 |
| 2 | **티켓 접수**가 **실제 접수**입니다. 새 연결은 **끄기**로 시작합니다. | Zendesk 패널의 **티켓 접수** 스위치 |
| 3 | Zendesk 양식 변경 때문에 접수가 **중지됨** 상태가 아닙니다. | 패널의 상태와, 고칠 내용을 알려 주는 배너 |
| 4 | 호스트 위임 방식만: 티켓 양식이 동기화되어 있고, Zendesk가 요구하는 모든 필드를 카드의 행, 고정값, 백엔드 중 하나로 채울 수 있습니다. | **티켓 접수** 페이지에 "아직 동기화된 스키마가 없습니다" 대신 양식이 표시됩니다. "Moss가 이 필드에 연결한 역할이 없어"라고 표시된 필수 필드는 **고정값**이나 **백엔드**가 필요합니다 |
| 5 | 호스트 위임 방식만: 세션이 시작되거나 재개될 때 페이지가 `onSupportTicket`을 등록해 두었습니다. | 사용자가 있는 페이지의 SDK 설정 |
| 6 | 대화가 `zendesk_ticket`을 허용하는 게시된 프로시저 안에 있거나, **또는** 실행 중인 프로시저가 없고 Zendesk가 애플리케이션의 기본 상담 연결입니다(아래 참고). | 프로시저의 **사용할 수 있는 도구** |
| 7 | 이 대화에서 아직 티켓을 접수하지 않았습니다. | **세션**에서 해당 세션. Moss는 대화 하나에 티켓을 최대 하나만 접수합니다. 이미 접수했다면 어시스턴트가 사용자에게 처리 대기 중이라고 알립니다 |

조건이 모두 맞더라도, 어시스턴트는 프로시저의 단계나 사용자의 요청이 티켓을
필요로 할 때만 초안을 작성합니다.

**기본 상담 연결.** 실행 중인 프로시저가 없어도, 애플리케이션에 게시된 프로시저가
하나 이상 있고 Zendesk가 지원 창구라면 Moss는 기본 상담 연결로 티켓을 제안할 수
있습니다. Zendesk의 티켓 접수가 **실제 접수**이고 Intercom이 연결되어 있지 않으면,
기본 지원 창구는 Zendesk입니다. Intercom도 연결되어 있으면 프로시저만 결정합니다.
프로시저마다 `zendesk_ticket` 또는 `intercom_conversation`을 허용합니다.

0.17.0부터는 카드가 사용자의 응답을 기다리는 동안 채팅 입력창이 꺼지고,
입력창에는 "위의 문의 티켓 요약을 확인해 주세요…"라는 안내 문구가 표시됩니다.
입력창은 제출 결과가 나오거나, 사용자가 취소하거나, 초안이 만료되면 다시
켜집니다. 페이지를 새로 불러와도 카드는 그대로 남아 있습니다. 취소한 사용자는
같은 대화에서 티켓을 다시 요청할 수 있으며, 새 초안은 취소한 카드의 값에서
시작합니다. 사용자가 제출한 뒤 백엔드가 접수하는 동안에는 어시스턴트가 새 카드를
만들지 않습니다.

### 티켓 접수 끄기

관리자가 Zendesk 패널에서 쓰는 **티켓 접수** 스위치 하나로 끕니다. **끄기**로
바꾸면 모든 프로시저와 기본 상담 연결에서 티켓 제안이 멈추고, 이미 화면에 떠 있는
카드도 제출할 수 없습니다. 프로시저의 티켓 단계는 그대로 남으므로, 다시
**실제 접수**로 바꾸면 복구됩니다. 코드를 바꿀 필요는 없습니다.

### 일부 사용자에게만 적용하기

적용 대상 사용자에게만 `onSupportTicket`을 넘기세요. 콜백 없이 시작된 세션에는
티켓이 제안되지 않으므로(5번 조건), 나머지 사용자에게는 아무 변화가 없습니다.
SDK는 세션이 시작되거나 재개될 때마다(예: 다음에 페이지를 불러올 때) 콜백 등록
여부를 알리므로, 사용자를 대상에 넣거나 뺀 변경은 그때부터 적용됩니다.

```tsx
<AgentProvider config={{
  // ...
  onSupportTicket: user.inTicketRollout ? fileTicket : undefined,
}}>
```

이 방법은 호스트 위임 방식에서만 통합니다. 직접 방식에서는 Moss가 콜백 없이
접수하므로 `onSupportTicket`으로 제어할 수 없습니다.

## 핸드오프

콜백은 `SupportTicketHandoff`를 받습니다.

| 필드 | 타입 | 설명 |
|-------|------|-------------|
| `handoffId` | `string` | 이번 접수 결정을 식별합니다. 결과는 이 값으로 보고하고, 제출 한 번이 티켓 두 개가 되지 않도록 이 값으로 중복을 거르세요. |
| `ticket` | `SupportTicketPayload` | 접수할 티켓입니다. 사용자가 제출한 내용을, 제출 시점에 Moss가 양식에 맞춰 검증한 것입니다. |

`SupportTicketPayload`는 Zendesk 티켓 생성 형식을 Zendesk 표기 그대로 따르므로,
백엔드는 요청자만 붙여 변환 없이 바로 보낼 수 있습니다.

| 필드 | 타입 | 설명 |
|-------|------|-------------|
| `subject` | `string` | 티켓 제목 |
| `comment` | `{ html_body: string }` | HTML 형식의 티켓 본문. 설명 다음에 최근 채팅 메시지 12개가 이어지며, 메시지마다 400자에서 자릅니다 |
| `tags` | `string[]` | 항상 `moss-created`를 포함합니다(아래 참고) |
| `ticket_form_id` | `number` | **티켓 접수** 페이지에서 고른 Zendesk 양식. 타입상으로는 선택 항목이며, 양식이 동기화되면 포함됩니다 |
| `custom_fields` | `Array<{ id: number; value: string \| number \| boolean \| string[] \| null }>` | 필드 값. 설정되어 있으면 [세션 참조 필드](/ko/dashboard/integrations#세션-참조-필드)도 포함합니다 |

사용자가 정하지 않은 필드는 빈 값이 아니라 아예 빠집니다. Moss는 판단할 수 없는
값을 추측하지 않고 생략합니다. 페이로드에는 요청자(이름, 이메일)가 절대 들어가지
않습니다. 요청자는 백엔드가 붙이며, 관리자가 **티켓 접수** 페이지에서 **백엔드**에
둔 필드도 백엔드가 채웁니다.

### `moss-created` 태그

Moss가 작성하는 모든 티켓의 `ticket.tags`에는 Zendesk 태그 `moss-created`가
들어갑니다. 백엔드에서 티켓을 보낼 때 이 태그를 지우지 마세요. 지원팀은 이 태그로
Zendesk 보기, 트리거, 보고서에서 Moss를 거쳐 들어온 티켓을 찾고, 분배하고,
집계합니다. 백엔드에서 태그를 더 붙인다면 목록을 바꾸지 말고 뒤에 추가하세요.

## 결과 보고

콜백은 `SupportTicketOutcome`을 반환하세요.

```ts
type SupportTicketOutcome =
  | { ok: true; ticketId?: string | number; ticketUrl?: string }
  | { ok: false; errorCode?: string; errorDetail?: string };
```

`ticketId`는 티켓 시스템이 돌려준 그대로 정수로 넘기거나 텍스트로 넘길 수
있으며, Moss는 텍스트로 기록합니다. `Number.MAX_SAFE_INTEGER`를 넘는 숫자는 이미
반올림되었을 수 있어 Moss가 ID 없이 접수를 기록하므로, 그만큼 큰 ID는 텍스트로
넘기세요. 소수는 어떤 티켓도 가리키지 않으므로 같은 방식으로 버립니다.
0.16.16 이전 SDK는 `ticketId`의 타입이 `string`이므로, 타입을 쓰는 호스트가 숫자를
반환하려면 그 버전에서는 타입 캐스트가 필요합니다.

**반환값은 접수 확인 응답이 아니라 티켓의 최종 결과입니다.**

- `{ ok: true }`는 티켓이 실제로 생성된 뒤에만 반환하고, 백엔드가 티켓을 특정할
  수 있으면 `ticketId`를 함께 넘기세요. 사용자에게 "대신 접수해 드렸습니다"가
  표시되는 근거는 이 값뿐입니다.
- 접수에 실패했거나 거부되었다면 `{ ok: false }`를 반환하세요. `errorCode`와
  `errorDetail`은 핸드오프 감사 기록에 남고, 사용자에게는 표시되지 않습니다.
  Moss 0.16.16부터는 둘 중 정수로 보낸 값은 텍스트로 기록하고, 텍스트가 아닌 그
  밖의 값은 버립니다.
- SDK를 빨리 놓아 주려고 미리 반환하지 마세요. 15초가 지나도 응답이 없거나,
  reject되거나, boolean `ok`가 없는 값을 반환한 콜백은 실패가 아니라
  **알 수 없음**으로 처리합니다. 백엔드가 실제로 접수했을 수도 있으므로, 카드는
  요청을 전달했지만 확인받지 못했다고 사용자에게 알립니다. Moss에는 아무것도
  보고하지 않으며, 뒤늦은 반환은 무시합니다.

## 카드에 표시되는 내용

| 상황 | 카드에 표시되는 내용 |
|---|---|
| `{ ok: true, ticketId }`를 반환함 | "대신 접수해 드렸습니다 — 티켓 #`ticketId`" |
| `ticketId` 없이 `{ ok: true }`를 반환함 | "대신 접수해 드렸습니다" |
| `ticketUrl`(문자열)도 넘김 | **티켓 보기** 링크 |
| `{ ok: false }`를 반환함 | "티켓을 접수하지 못했어요"와 [대체 링크](#대체-링크) |
| 15초 안에 응답이 없거나 콜백에서 예외가 발생함 | "접수 요청을 전달했지만 처리 결과를 확인하지 못했습니다. 회신이 없으면 고객지원팀에 문의해 주세요." |
| 사용자가 취소함 | "접수하지 않았습니다"와 [대체 링크](#대체-링크). 초안은 이번 세션 동안 보관됩니다. |

티켓 번호는 콜백이 `ticketId`를 반환할 때만 표시됩니다. 이 방식에서 Moss는
Zendesk를 호출하지 않으므로 번호를 조회할 수 없습니다. 대시보드의 세션 대화
기록에도 같은 결과가 표시되며, 번호를 반환했다면 번호도 함께 나옵니다.

### 카드 문구

`appearance.chrome.ticketCard`를 설정하면 카드 문구를 직접 정할 수 있습니다. 키는
모두 선택 사항이며, 설정하지 않은 키는 SDK의 번역된 기본 문구를 그대로 씁니다.
직접 넣은 문구는 언어와 관계없이 그대로 표시되므로, 여러 언어를 지원한다면 직접
번역해 넣으세요.

| 키 | 표시 위치 | 기본값(한국어) |
|---|---|---|
| `titleLabel` | 제목 행의 라벨 | 양식에서 정한 필드 이름, 없으면 "제목" |
| `descriptionLabel` | 설명 행의 라벨 | 양식에서 정한 필드 이름, 없으면 "내용" |
| `privacyNote` | 카드 머리글 아래: 티켓이 접수되는 곳 | "고객지원팀으로 접수됩니다" |
| `submittingNote` | "티켓을 접수하는 중이에요…" 아래 | "고객지원팀으로 보내는 중" |
| `confirmedNote` | 성공 표시줄 옆 | "접수가 완료되었습니다 — 고객지원팀이 확인할 예정입니다." |
| `cancelledNote` | "접수하지 않았습니다" 행 안 | "작성하신 내용은 이번 대화 동안 보관해 둘게요 — 말씀만 주시면 이어서 진행할 수 있습니다." |
| `failedNote` | "티켓을 접수하지 못했어요" 행 안 | "고객지원팀에 전달되지 않았습니다." |

```tsx
appearance: {
  chrome: {
    ticketCard: {
      privacyNote: 'Filed with Acme Support',
      confirmedNote: 'We reply by email within one business day.',
    },
  },
},
```

`ticketCard`는 코드에서만 설정할 수 있습니다. 다른 외관 옵션은
[외관](/ko/sdk/appearance)을 참고하세요.

### 대체 링크

접수에 실패하거나 사용자가 취소하면, 사용자가 다른 경로를 찾을 수 있도록 카드에
채팅 푸터의 **티켓 열기** 링크(티켓 링크가 없으면 **도움말 센터** 링크)가
표시됩니다. 이 링크는 푸터가 표시될 때만 나타납니다. 대시보드의
**구성 > 외관 > 브랜딩**(**푸터 표시**, **티켓 라벨**, **티켓 URL**)이나 코드에서
설정하세요.

```tsx
appearance: {
  chrome: {
    footer: {
      enabled: true,
      openTicket: { label: 'Contact support', url: 'https://support.example.com/new', icon: 'ticket' },
    },
  },
},
```

### 티켓 접수 후 평가

콜백이 티켓 접수를 확인하면(`{ ok: true }`) Moss는 바로 사용자에게 대화 평가를
요청합니다. 평가 카드는 채팅 안에서 접수 확인 아래에 나타나므로 티켓 번호와 링크가
가려지지 않습니다. 평가는 사용자가 아직 같은 대화에 있고, 백엔드가 접수하는 동안
아무것도 보내지 않았고, 대화에 주고받은 메시지가 한 번 이상 있고, 아직 평가하지
않았을 때만 요청합니다. 평가하거나 건너뛰면 그 카드만 사라지고 대화는 이어집니다.
평가 방식은 `appearance.chrome.feedback.sessionRating`을 따릅니다(기본값은
`'thumbs'`, 0.17.0부터 `'stars'`도 가능). [외관](/ko/sdk/appearance)을
참고하세요.

## 이벤트

`onEvent`를 설정하면 SDK가 티켓 관련 이벤트 두 가지를 보냅니다.

| 이벤트 | 시점 | 속성 |
|---|---|---|
| `Moss Ticket Opened` | 어시스턴트가 새 티켓 카드를 보여 줄 때. 핸드오프마다 한 번이며, 페이지를 다시 불러와 복원된 카드에서는 다시 발생하지 않습니다 | `handoffId` |
| `Moss Ticket Submitted` | 사용자가 카드를 제출하고 결과가 정해졌을 때 | `handoffId`, `outcome`: `'filed'`, `'failed'`, `'unconfirmed'` |

`outcome`은 카드가 사용자에게 알린 결과입니다. `'unconfirmed'`는 어느 쪽으로도
확인되지 않았다는 뜻입니다. 두 이벤트 모두 공통 속성(`sessionId`, `userId`,
`timestamp`, `pageKey`)도 함께 담습니다. [이벤트](/ko/sdk/events)를 참고하세요.

## 반복 제출

Moss 0.16.16부터는 백엔드의 결과가 기록되기 전에 사용자가 같은 카드를 다시
제출하면(예: 응답이 유실되었거나 다른 탭에서 제출한 경우) Moss가 이를 받아들이고
같은 `handoffId`로 `onSupportTicket`을 다시 호출합니다. `handoffId`로 중복을
거르면 사용자에게는 티켓이 하나만 생깁니다. 처음 제출과 값이 다른 재제출은
거부되며 콜백까지 가지 않습니다.

<Warning>
    `handoffId`를 백엔드의 멱등성 키로 쓰세요. 같은 핸드오프가 두 번 도착하면
    처음 반환한 결과를 다시 반환하세요. 한 번의 제출로 두 번째 티켓을 만들면
    안 됩니다.
</Warning>

## 자주 묻는 질문

**Moss가 티켓 접수를 제안하지 않는 이유는 무엇인가요?**
[Moss가 티켓을 제안하는 조건](#moss가-티켓을-제안하는-조건)을 순서대로 확인하세요.
흔한 원인은 **티켓 접수**가 아직 **끄기**인 경우, `zendesk_ticket`을 허용하는
게시된 프로시저가 없는 경우, 페이지가 `onSupportTicket`을 등록하지 않은
경우입니다.

**티켓 접수를 끄려면 어떻게 하나요?**
관리자가 Zendesk 패널에서 **티켓 접수**를 **끄기**로 바꾸면 됩니다. 코드를 바꾸지
않아도 모든 프로시저에 한꺼번에 적용됩니다.
[티켓 접수 끄기](#티켓-접수-끄기)를 참고하세요.

**일부 사용자에게만 티켓 접수를 켤 수 있나요?**
호스트 위임 방식이라면 가능합니다. 해당 사용자에게만 `onSupportTicket`을
넘기세요. [일부 사용자에게만 적용하기](#일부-사용자에게만-적용하기)를 참고하세요.

**지원팀이 Moss를 거쳐 들어온 티켓을 어떻게 구분하나요?**
모든 티켓에 `moss-created` 태그가 붙습니다. 백엔드에서 티켓을 보낼 때 이 태그를
지우지 마세요. 어느 채팅에서 왔는지까지 보려면 관리자가
[세션 참조 필드](/ko/dashboard/integrations#세션-참조-필드)를 설정하면 됩니다.

**카드에 티켓 번호 없이 "대신 접수해 드렸습니다"만 나오는 이유는 무엇인가요?**
콜백이 `ticketId` 없이 `{ ok: true }`를 반환했기 때문입니다. 티켓 시스템이 돌려준
ID를 함께 반환하세요.

**Zendesk 양식이 바뀌면 어떻게 되나요?**
Moss는 매일 양식을 다시 읽습니다. 대부분의 변경은 따로 할 일이 없습니다. 일부
변경은 관리자가 고칠 때까지 접수를 중지합니다. 새 필수 필드는 접수를 중지하지는
않지만, 그 필드가 없는 티켓은 접수할 수 없습니다. 호스트 위임 방식에서는 카드가
표시되지 않고(사용자가 채울 수 있는 행이 카드에 있는 경우는 제외), 직접 방식에서는
Moss가 그 필드를 채울 수 없으면 티켓을 보내지 않고 어시스턴트가 사용자에게
지원팀에 문의하라고 안내합니다. 관리자는 **티켓 접수** 페이지에서 그 필드에
**고정값**을 지정하거나, 호스트 위임 방식이면 **백엔드**에 두어 백엔드가 채우게
하면 됩니다.
[Zendesk 양식이 바뀔 때](/ko/dashboard/integrations#zendesk-양식이-바뀔-때)를
참고하세요.

SDK가 Moss로 보내는 모든 요청에는 서버가 로그인한 사용자를 위해 서명한 JSON Web Token(JWT)이 실립니다. Moss는 요청마다 토큰의 서명, 클레임, 수명을 확인하고, 유효한 토큰이 없는 요청은 HTTP 401로 거부합니다. 예외는 애플리케이션의 공개 설정을 읽는 요청 하나뿐입니다. [허용 도메인](#허용-도메인)을 참조하세요. SDK에는 API 키가 없으며, 서명된 토큰이 SDK의 유일한 인증 수단입니다.

설정 순서는 다음과 같습니다.

1. [Moss 대시보드](https://dashboard.viamoss.ai)에서 **구성 > 보안**을 열고 **JWT 서명 키** 카드에서 키를 만드세요. 이 페이지는 조직 관리자만 열 수 있습니다.
2. 앱에 로그인한 사용자를 위해 토큰에 서명하는 엔드포인트를 서버에 추가하세요.
3. 그 엔드포인트를 호출하는 `getJwt` 함수를 SDK에 넘기세요.

## 작동 방식

```
User loads your app → your server signs a JWT → the SDK sends it with each request → Moss verifies it
```

1. 서명용 시크릿이나 개인 키는 서버가 보관합니다. 브라우저로는 절대 보내지 않습니다.
2. SDK는 토큰이 필요하면 `getJwt` 함수를 호출하고, 이 함수가 서버에 토큰을 요청합니다.
3. 서버는 앱에 누가 로그인했는지 확인하고, `sub`가 그 사용자의 ID인 토큰에 서명합니다.
4. SDK는 모든 요청의 `Authorization: Bearer` 헤더에 토큰을 담아 보냅니다.
5. Moss는 토큰의 `kid` 헤더가 가리키는 서명 키를 찾아 그 키의 알고리즘으로 서명을 검증하고, 클레임을 확인한 뒤 `sub`에서 사용자 신원을 가져옵니다.

<Warning>
    서버가 인증한 사용자에게만 토큰을 서명하고, `sub`는 요청이 아니라 서버의 세션에서 가져오세요. 어떤 `sub`의 유효한 토큰을 가진 사람은 Moss에서 그 사용자로 행동할 수 있고, 그 사용자의 채팅을 다시 여는 것도 가능합니다.
</Warning>

## 설정

### 1. 서명 키 만들기

**구성 > 보안**을 여세요. **JWT 서명 키** 카드에서 두 종류의 키를 만들 수 있습니다.

| 종류 | 버튼 | 알고리즘 | 서명 자료를 가진 쪽 | Moss가 저장하는 것 |
|------|------|----------|---------------------|--------------------|
| HMAC | **키 생성** | HS256 | Moss가 `moss_sk_`로 시작하는 시크릿을 만들어 한 번만 보여 줍니다. 서버와 Moss가 함께 보관합니다. | 토큰을 검증하는 데 필요한 시크릿 |
| 공개 키 | **공개 키 등록** | RS256(RSA, 2,048~8,192비트) 또는 ES256(P-256) | 키 쌍을 직접 만듭니다. 개인 키는 고객 시스템 밖으로 나가지 않습니다. | 공개 키만 |

키를 만들거나 등록하면 카드에 **키 ID**가 표시됩니다. `key_` 뒤에 12자가 붙은 형태입니다. 이 키로 서명하는 모든 토큰의 `kid` 헤더에 이 값을 넣으세요.

<Warning>
    HMAC 시크릿은 키를 만들 때 한 번만 표시됩니다. 서버의 시크릿 관리자나 환경 변수에 보관하세요. 잃어버렸다면 새 키를 만들고 이전 키를 폐기하세요.
</Warning>

공개 키를 쓰려면 키 쌍을 만든 다음 **공개 키 등록**을 누르고, **알고리즘**을 고른 뒤 **공개 키 (PEM)** 칸에 공개 키를 붙여 넣으세요.

```bash
# RS256: 2,048비트 RSA 키 쌍
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out moss-private.pem
openssl pkey -in moss-private.pem -pubout -out moss-public.pem

# ES256: P-256 키 쌍
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out moss-private.pem
openssl pkey -in moss-private.pem -pubout -out moss-public.pem
```

공개 키 하나를 PEM 형식(`-----BEGIN PUBLIC KEY-----`, RS256이라면 `-----BEGIN RSA PUBLIC KEY-----`도 가능)으로 붙여 넣으세요. Moss는 개인 키, 한 번에 붙여 넣은 여러 개의 키, RSA-PSS 키, 그리고 이 애플리케이션에 이미 있는 공개 키(폐기된 키 포함)를 거부합니다. 키를 교체하려면 새 키 쌍이 필요합니다.

<Info>
    보안 정책상 대칭 시크릿을 외부 업체와 공유할 수 없다면 공개 키를 선택하세요. 이 경우 Moss는 토큰을 검증하는 자료만 가지며, 그 키로 토큰에 서명할 수 있는 자료는 갖지 않습니다. 그 밖의 경우에는 HMAC이 더 간단합니다.
</Info>

### 2. 토큰 엔드포인트 만들기

로그인한 사용자를 위해 토큰에 서명하는 엔드포인트를 서버에 추가하세요. 두 예시 모두 HMAC 키를 사용합니다.

<Tabs>
  <Tab title="Node.js">
    ```javascript
    const jwt = require('jsonwebtoken');

    // requireAuth는 직접 만든 미들웨어로, 로그인한 사용자를 식별해야 합니다.
    app.get('/api/moss-token', requireAuth, (req, res) => {
      const token = jwt.sign(
        {
          sub: String(req.user.id),              // 필수: 사용자 ID(문자열)
          app: process.env.MOSS_APPLICATION_ID,  // 필수: Moss 애플리케이션 ID
          metadata: { role: req.user.role },     // 선택: 답변에 쓰일 속성
        },
        process.env.MOSS_JWT_SECRET,             // moss_sk_… 시크릿
        {
          algorithm: 'HS256',
          expiresIn: '1h',                       // exp를 설정합니다. iat는 jsonwebtoken이 추가합니다.
          keyid: process.env.MOSS_KEY_ID,        // key_… ID. kid 헤더로 전송됩니다.
        }
      );

      res.json({ token });
    });
    ```
  </Tab>

  <Tab title="Python">
    ```python
    import os
    from datetime import datetime, timedelta, timezone

    import jwt  # PyJWT
    from flask import jsonify

    @app.route('/api/moss-token')
    @require_auth  # 직접 만든 데코레이터로, 로그인한 사용자를 식별해야 합니다.
    def moss_token():
        now = datetime.now(timezone.utc)
        token = jwt.encode(
            {
                'sub': str(current_user.id),               # 필수: 사용자 ID(문자열)
                'app': os.environ['MOSS_APPLICATION_ID'],  # 필수: Moss 애플리케이션 ID
                'iat': now,                                # 필수
                'exp': now + timedelta(hours=1),           # 필수
                'metadata': {'role': current_user.role},   # 선택: 답변에 쓰일 속성
            },
            os.environ['MOSS_JWT_SECRET'],                 # moss_sk_… 시크릿
            algorithm='HS256',
            headers={'kid': os.environ['MOSS_KEY_ID']},    # key_… ID
        )

        return jsonify({'token': token})
    ```
  </Tab>
</Tabs>

공개 키를 등록했다면 개인 키와 그 알고리즘으로 서명하세요. 시크릿 대신 개인 키 PEM을 넣고 `algorithm: 'RS256'` 또는 `'ES256'`을 지정합니다. `kid`는 등록한 공개 키의 값을 쓰세요.

애플리케이션 ID는 **구성 > 일반**의 **애플리케이션 ID** 항목에 있습니다. 표시된 그대로 복사하세요. Moss는 `app` 값을 이 ID와 한 글자씩 비교합니다.

### 3. SDK 설정

엔드포인트에서 토큰을 받아 오는 `getJwt` 함수를 넘기세요. SDK가 이 함수를 언제 호출하는지는 [토큰 갱신](#토큰-갱신)에서 설명합니다.

<Tabs>
  <Tab title="React (npm)">
    ```tsx
    import { AgentProvider, AssistantButton } from '@viamoss/moss-sdk';

    <AgentProvider
      config={{
        apiUrl: 'https://moss-api.viamoss.ai',
        applicationId: 'YOUR_APPLICATION_ID',
        userId: String(currentUser.id), // 토큰의 sub와 같은 값
        getJwt: async () => {
          const res = await fetch('/api/moss-token');
          if (!res.ok) throw new Error(`Token request failed: ${res.status}`);
          const { token } = await res.json();
          return token;
        },
      }}
    >
      <AssistantButton />
    </AgentProvider>
    ```
  </Tab>

  <Tab title="CDN (스크립트 태그)">
    ```html
    <script>
      window.mossSettings = {
        userId: 'USER_ID', // 토큰의 sub와 같은 값
        getJwt: async function () {
          const res = await fetch('/api/moss-token');
          if (!res.ok) throw new Error('Token request failed: ' + res.status);
          const data = await res.json();
          return data.token;
        },
      };
    </script>
    <script
      src="https://cdn.viamoss.ai/moss-sdk@latest.min.js?applicationId=YOUR_APPLICATION_ID"
      data-api-base="https://moss-api.viamoss.ai"
    ></script>
    ```
  </Tab>
</Tabs>

SDK에는 `userId`가 꼭 필요합니다. `sub`와 같은 값으로 설정하세요. Moss는 사용자 신원을 토큰의 `sub`에서만 가져오므로, `userId` 설정으로 Moss가 인식하는 사용자가 바뀌지는 않습니다.

## JWT 클레임 참조

### 헤더

| 필드 | 필수 | 값 |
|------|------|-----|
| `kid` | 예 | 대시보드에 표시된 키의 **키 ID**. `key_` 뒤에 12자가 붙은 형태 |
| `alg` | 예 | 키의 알고리즘: `HS256`, `RS256` 또는 `ES256`. Moss는 키를 만들 때 정해진 알고리즘으로 검증하며, 다른 알고리즘으로 서명한 토큰은 거부합니다. |

### 클레임

| 클레임 | 필수 | 형식 | Moss가 하는 일 |
|--------|------|------|----------------|
| `sub` | 예 | 비어 있지 않은 문자열 | 사용자의 신원입니다. 채팅, 이전 채팅 목록, 요청 제한, 사용자 데이터 삭제가 모두 `sub` 단위로 동작하므로 사람마다 다른 값을 주세요. |
| `app` | 예 | 문자열 | 서명 키가 속한 애플리케이션의 ID와 정확히 같아야 합니다. **구성 > 일반**에 표시된 값 그대로입니다. |
| `exp` | 예 | 숫자(Unix 초) | 만료 시각입니다. 만료된 토큰은 거부합니다. |
| `iat` | 예 | 숫자(Unix 초) | 발급 시각입니다. `exp`에서 `iat`를 뺀 값은 최대 86,400초(24시간)입니다. |
| `iss` | **필수 발급자 (iss)** 값을 설정했을 때만 | 문자열 | 설정한 발급자와 정확히 같아야 합니다. 설정하지 않으면 확인하지 않습니다. |
| `aud` | **필수 대상 (aud)** 값을 설정했을 때만 | 문자열 | 설정한 대상과 정확히 같아야 하며, 배열이 아닌 문자열 하나여야 합니다. 설정하지 않으면 확인하지 않습니다. |
| `metadata` | 아니요 | 객체 | Moss가 모델에 넘겨 답변을 사용자에 맞추는 속성입니다. [사용자 정보를 Moss에 알리기](#사용자-정보를-moss에-알리기)를 참조하세요. |

`exp`와 `iat`는 JSON 숫자여야 하며, 문자열로 쓴 숫자는 거부합니다. 위의 클레임을 설정하세요. Moss는 그 밖의 클레임으로 사용자를 식별하거나 설명하지 않으므로 `email`, `name` 같은 개인정보는 토큰에 넣지 마세요. 토큰 라이브러리가 확인하는 표준 클레임은 토큰에 있으면 그대로 적용됩니다. 미래 시각의 `nbf`(not before)는 거부되고, `jti`는 문자열이어야 합니다.

Moss는 시계 오차를 허용하지 않습니다. 서버 시계를 동기화해 두세요. `iat`가 Moss의 시계보다 늦은 토큰은 `INVALID_TOKEN`으로 거부되고, `exp`는 초 단위로 확인합니다.

### 필수 발급자와 대상

공유 ID 서비스에서 토큰을 발급하는 경우처럼 Moss용으로 발급한 토큰만 받게 하려면 **구성 > 보안 > JWT 클레임 강제**에서 값을 설정하세요.

| 필드 | 형식 | 기본값 | 효과 |
|------|------|--------|------|
| **필수 발급자 (iss)** | 문자열, 최대 255자 | 비어 있음(확인 안 함) | 모든 토큰에 이 값과 정확히 같은 `iss`가 있어야 하며, 아니면 `ISSUER_MISMATCH`로 응답합니다. |
| **필수 대상 (aud)** | 문자열, 최대 255자 | 비어 있음(확인 안 함) | 모든 토큰에 이 값과 정확히 같은 `aud`가 문자열 하나로 있어야 하며, 아니면 `AUDIENCE_MISMATCH`로 응답합니다. |

**보안 설정 저장**을 눌러 저장하세요. 이 버튼은 **허용 도메인** 목록과 이 두 필드를 함께 저장합니다. 설정한 값은 애플리케이션의 모든 키에 적용됩니다.

## 토큰 갱신

Moss는 수명(`exp` 빼기 `iat`)이 24시간을 넘는 토큰을 거부합니다. 그 안에서 수명은 직접 정합니다. 수명이 짧을수록 유출된 토큰을 쓸 수 있는 시간이 줄어들고, `getJwt`를 쓰면 SDK가 현재 토큰이 만료되기 직전에 서버에 새 토큰을 요청합니다.

`getJwt`가 있으면 SDK는 다음과 같이 동작합니다.

- 토큰이 없거나 현재 토큰이 60초 안에 만료되면 `getJwt`를 호출합니다.
- Moss가 401을 반환하면 `getJwt`를 한 번 더 호출하고, 새 토큰으로 그 요청을 한 번 다시 보냅니다.
- `getJwt`가 오류를 던지면 그 요청은 로그인에 실패한 것으로 처리합니다.

<Tip>
    토큰 수명은 60초보다 충분히 길게 잡으세요. 그보다 짧은 토큰은 언제나 60초 갱신 구간 안에 있으므로, SDK가 요청할 때마다 `getJwt`를 호출합니다.
</Tip>

대신 고정 `jwt`를 넘기면 SDK는 그 토큰을 그대로 사용합니다. 토큰이 만료되면 모든 요청이 실패하고, 사용자에게는 아래에서 설명하는 로그인 오류가 표시됩니다. 고정 토큰은 테스트용이나 토큰보다 먼저 닫히는 페이지에만 쓰세요.

```tsx
<AgentProvider config={{
  // ...
  jwt: 'YOUR_STATIC_TOKEN',  // 갱신 없음
}}>
```

둘 다 넘기면 SDK는 먼저 `jwt`를 쓰고, 만료가 가까워지면 `getJwt`를 호출합니다.

`sub`가 같은 한 새 토큰으로 바뀌어도 채팅은 이어집니다. 다른 `sub`의 토큰으로는 그 채팅을 이어 갈 수 없으며, Moss는 403 `SESSION_UNAUTHORIZED`로 응답합니다. SDK가 시작하면서 저장된 채팅을 다시 열던 중이었다면, 저장된 채팅을 버리고 새 채팅을 시작합니다.

## 요청이 거부될 때 사용자에게 보이는 것

| 상황 | 동작 |
|------|------|
| 채팅을 시작할 때 | SDK가 약 30초 동안 재시도한 뒤 **연결 실패**와 "서버에 연결할 수 없습니다. 인터넷 연결을 확인해 주세요."를 **다시 시도** 버튼과 함께 표시합니다. 사용할 수 없을 때 보여 줄 대체 화면을 설정했다면 그 화면이 대신 표시됩니다. |
| 사용자가 질문하거나 가이드 단계가 실행될 때 | 위의 갱신과 재시도를 거친 뒤 채팅에 "이 페이지가 어시스턴트에 로그인하지 못했습니다."가 표시됩니다. |
| 사용자가 요청 제한을 넘었을 때 | 채팅에 "요청이 너무 많습니다. 잠시 후 다시 시도해 주세요."가 다시 시도 동작과 함께 표시됩니다. [요청 제한](#요청-제한)을 참조하세요. |

로그인 메시지와 요청 제한 메시지는 0.17.0에서 새로 생겼습니다. 0.17.0부터는 `onError` 핸들러도 이 문제를 받으며, `code`는 `sign_in_failed` 또는 `rate_limited`입니다.

원인을 찾으려면 브라우저의 네트워크 패널을 열고 실패한 응답을 확인하세요. 응답 본문의 `detail.code`에 이유가 적혀 있습니다.

```json
{ "detail": { "error": "Token has expired", "code": "TOKEN_EXPIRED" } }
```

| 상태 | `detail.code` | 원인 | 해결 |
|------|---------------|------|------|
| 401 | `MISSING_AUTH` | 요청에 `Authorization: Bearer` 헤더가 없습니다. | SDK에 `getJwt` 또는 `jwt`를 넘기세요. |
| 401 | `INVALID_TOKEN` | 토큰 형식이 잘못되었거나 서명이 검증되지 않습니다. `kid`가 없거나 Moss 키 ID가 아닌 경우, `alg`가 키의 알고리즘과 다른 경우, `sub`, `app`, `exp`, `iat` 중 하나가 없는 경우, `sub`가 비어 있는 경우, `exp`나 `iat`가 숫자가 아닌 경우, `metadata`가 객체가 아닌 경우, `iat`나 `nbf`가 미래인 경우, `jti`가 문자열이 아닌 경우도 해당합니다. | 서명할 때 [클레임 참조](#jwt-클레임-참조)와 대조해 확인하세요. |
| 401 | `TOKEN_EXPIRED` | `exp`가 지났습니다. | SDK가 새 토큰을 받아 오도록 `getJwt`를 쓰세요. |
| 401 | `TOKEN_LIFETIME_EXCEEDED` | `exp`에서 `iat`를 뺀 값이 24시간을 넘습니다. | 수명을 줄이세요. |
| 401 | `UNKNOWN_KEY` | 이 `kid`를 가진 키가 없습니다. | `MOSS_KEY_ID`가 요청을 보내는 Moss 배포에서 만든 키인지 확인하세요. 같은 배포에 있는 다른 애플리케이션의 키라면 대신 `APP_MISMATCH`가 반환됩니다. |
| 401 | `KEY_REVOKED` | 키가 폐기되었습니다. | 활성 키로 서명하세요. |
| 401 | `KEY_EXPIRED` | 키의 폐기 유예 기간이 끝났습니다. | 활성 키로 서명하세요. |
| 401 | `APP_MISMATCH` | `app`이 서명 키가 속한 애플리케이션의 ID가 아닙니다. | **구성 > 일반**에서 ID를 그대로 복사하세요. |
| 401 | `ISSUER_MISMATCH` | **필수 발급자 (iss)** 값이 설정되어 있는데 `iss`가 없거나 다릅니다. | 설정한 값과 정확히 맞추세요. |
| 401 | `AUDIENCE_MISMATCH` | **필수 대상 (aud)** 값이 설정되어 있는데 `aud`가 없거나, 다르거나, 배열입니다. | 설정한 값과 같은 문자열 하나로 `aud`를 보내세요. |
| 403 | `DOMAIN_NOT_ALLOWED` | 페이지가 애플리케이션의 **허용 도메인**에 없거나, 페이지의 origin이 `null`입니다. | [허용 도메인](#허용-도메인)을 참조하세요. |
| 403 | `ORIGIN_REQUIRED` | 배포에서 허용된 페이지를 요구하는데, 요청에 `Origin`이나 `Referer`가 없거나 애플리케이션에 허용 도메인이 없습니다. | **허용 도메인**에 도메인을 추가하세요. |
| 403 | `SESSION_UNAUTHORIZED` | 채팅이 다른 사용자나 다른 애플리케이션의 것입니다. | 한 사람에게는 같은 `sub`를 유지하세요. |
| 429 | `RATE_LIMITED` | 사용자가 요청 제한을 넘었습니다. `Retry-After` 헤더에 기다릴 시간(초)이 있습니다. | [요청 제한](#요청-제한)을 참조하세요. |
| 500 | `KEY_STORAGE_MISCONFIGURED` | 자체 호스팅: 운영자의 `SECRET_ENCRYPTION_KEYS` 설정이 없거나, 시크릿을 저장할 때 쓴 키를 더 이상 담고 있지 않습니다. 그래서 서버가 HMAC 키의 저장된 시크릿을 읽지 못합니다. | 운영자가 그 설정을 되돌려야 합니다. [자체 호스팅 운영](/ko/self-hosting/operations)을 참조하세요. |

## 서명 키 교체와 폐기

애플리케이션마다 활성 키는 최대 5개입니다. 폐기 유예 기간 중인 키도 기간이 끝날 때까지 개수에 포함됩니다. **JWT 서명 키** 카드에는 키마다 종류, 상태, 생성 시각, 마지막 사용 시각이 표시됩니다.

### 키 폐기

**폐기**를 누르고 **유예 기간**을 고르세요.

| 유예 기간 | 효과 |
|-----------|------|
| **즉시** | 이미 발급된 토큰을 포함해, 이 키로 서명한 토큰이 곧바로 `KEY_REVOKED`로 실패합니다. |
| **24시간** 또는 **72시간** | 기한까지 키가 계속 동작하며, 카드에는 **(날짜)에 폐기 예정**으로 표시됩니다. 기한이 지나면 `KEY_EXPIRED`로 실패합니다. |

폐기는 되돌릴 수 없습니다. 예정된 폐기는 키를 즉시 폐기해서 앞당길 수는 있지만 미룰 수는 없습니다.

### 키 교체

1. 새 키를 만드세요. HMAC은 **키 생성**, 공개 키는 새 키 쌍으로 **공개 키 등록**을 사용합니다.
2. 새 시크릿 또는 개인 키와 그 `kid`를 토큰 엔드포인트에 배포하세요.
3. 이전 키를 **24시간** 또는 **72시간** 유예 기간으로 폐기하세요. 이미 발급된 토큰은 만료될 때까지 계속 동작합니다.

새 키를 넣을 자리가 있어야 하므로, 애플리케이션에 이미 키가 5개 있다면 쓰지 않는 키부터 폐기하세요.

### 키가 유출되었을 때

1. 키를 **즉시** 폐기하세요. 그 키로 서명한 토큰은 모두 곧바로 동작을 멈춥니다.
2. 새 키를 만들어 토큰 엔드포인트에 배포하세요.

`getJwt`를 쓰면 SDK가 401을 받은 뒤 새 토큰을 받아 오므로, 서버가 새 키로 서명하기 시작하는 즉시 사용자가 복구됩니다. 키 생성과 폐기는 [감사 로그](/ko/security/audit-logging)에 `jwt_key.create`와 `jwt_key.revoke`로 기록됩니다.

## 허용 도메인

**구성 > 보안 > 도메인 접근 제어**의 **허용 도메인** 목록은 토큰 다음의 보조 검사입니다. Moss는 모든 SDK 요청마다 요청을 보낸 페이지를 이 목록과 비교합니다. 애플리케이션의 공개 설정을 읽는 요청(CDN 스크립트가 시작할 때 보냄)도 마찬가지입니다. 목록에 맞지 않는 페이지는 403 `DOMAIN_NOT_ALLOWED`를 받습니다.

항목마다 **추가**를 누른 뒤 **보안 설정 저장**을 누르세요.

항목이 일치하는 방식은 다음과 같습니다.

- 페이지는 요청의 `Origin` 헤더에서 읽고, `Origin`이 없으면 `Referer`에서 읽습니다.
- 항목은 호스트가 정확히 같을 때만 일치합니다. `app.example.com`은 `app.example.com`에만 일치합니다.
- `*.example.com`은 `app.example.com`, `eu.app.example.com`처럼 깊이와 관계없이 모든 하위 도메인에 일치하지만 `example.com` 자체에는 일치하지 않습니다. 둘 다 필요하면 항목을 둘 다 추가하세요.
- 포트가 없는 항목은 모든 포트에 일치합니다. `localhost:3000`처럼 포트가 있는 항목은 그 포트에만 일치합니다. 브라우저는 기본 포트를 `Origin`에서 빼므로 `app.example.com:443` 같은 항목은 절대 일치하지 않습니다.
- 샌드박스 iframe이나 `file://` 페이지처럼 origin이 `null`인 페이지는 목록에 항목이 하나라도 있으면 거부됩니다.

이 목록이 하는 일과 하지 않는 일은 다음과 같습니다.

- 다른 웹사이트가 브라우저에서 이 애플리케이션의 어시스턴트를 쓰지 못하게 막습니다. `Origin`은 브라우저가 정하며 페이지가 바꿀 수 없기 때문입니다.
- 브라우저 밖의 클라이언트는 막지 못합니다. 그런 클라이언트는 `Origin`을 마음대로 보낼 수 있습니다. 요청을 인증하는 것은 서명된 토큰입니다.
- 목록이 비어 있으면 모든 페이지를 허용합니다.
- `Origin`도 `Referer`도 없는 요청은 통과합니다. 단, 배포에서 허용된 페이지를 요구하면 그렇지 않습니다. 자체 호스팅 운영자는 `SDK_REQUIRE_ORIGIN`으로 이를 켭니다. 그러면 그런 요청과, 목록이 빈 애플리케이션에 대한 모든 요청이 403 `ORIGIN_REQUIRED`를 받습니다. [자체 호스팅 네트워크](/ko/self-hosting/network)를 참조하세요.
- 자체 호스팅 설치에서는 0.17.0부터 `CORS_ALLOWED_ORIGINS`가 SDK 요청에 적용되지 않습니다. 따라서 어떤 페이지가 SDK를 쓸 수 있는지는 이 목록으로만 확인합니다.

<Note>
    애플리케이션의 공개 설정은 토큰 없이 읽을 수 있어서, 애플리케이션 ID를 아는 사람은 누구나 읽을 수 있습니다. 이 요청에도 허용 도메인 검사가 적용되지만, 브라우저 밖의 클라이언트는 이 검사를 통과할 수 있습니다. SDK용 설정에는 시크릿을 절대 넣지 마세요.
</Note>

## 요청 제한

0.17.0부터 Moss는 사용자마다 SDK 요청 속도를 제한합니다.

| 요청 | 제한 | 집계 단위 |
|------|------|-----------|
| 채팅 시작 | 1분에 30회 | 사용자(`sub`)와 애플리케이션 |
| 질문 | 1분에 60회 | 사용자(`sub`)와 애플리케이션 |
| 가이드 단계 완료 | 1분에 120회 | 사용자(`sub`)와 채팅 |
| 세션 녹화 업로드 | 1분에 10회 | 채팅 |

제한을 넘은 요청은 429 `RATE_LIMITED`와 함께 초 단위의 `Retry-After` 헤더를 받습니다. 질문이나 가이드 단계에서는 채팅에 "요청이 너무 많습니다. 잠시 후 다시 시도해 주세요."가 다시 시도 동작과 함께 표시됩니다. 채팅을 시작할 때는 SDK가 약 30초 동안 재시도한 뒤 연결 오류를 표시합니다.

`sub`를 함께 쓰는 사용자들은 이 제한도 함께 씁니다. 자체 호스팅 설치에서는 운영자가 `SDK_RATE_LIMITS_ENABLED=false`로 제한을 끌 수 있습니다. [SDK 요청 제한](/ko/self-hosting/overview#sdk-요청-제한)을 참조하세요.

## 사용자 정보를 Moss에 알리기

사용자의 역할, 요금제, 권한 같은 속성은 토큰의 `metadata` 클레임에 넣으세요. SDK의 `userMetadata` 설정은 같은 속성을 서명 없이 페이지에서 받습니다. 둘이 같은 키를 설정하면 토큰의 값이 우선합니다.

```json
{
  "sub": "user_8842",
  "app": "YOUR_APPLICATION_ID",
  "iat": 1795000000,
  "exp": 1795003600,
  "metadata": { "role": "viewer", "plan": "team", "can_export": false }
}
```

Moss는 이 속성을 다음과 같이 사용합니다.

- 채팅이 시작되거나 다시 열릴 때 합쳐진 속성을 사용자 기록에 저장하고, 모델이 답변할 때 읽는 내용에 포함합니다.
- 모델은 이 속성을 보고 답변을 다듬습니다. 예를 들어 열람 권한만 있는 사용자에게는 내보내기를 할 수 없다고 먼저 알려 줍니다.
- 0.17.0부터는 속성마다 서버가 서명한 값인지 페이지가 보낸 값인지 표시되며, 모델은 이 속성을 근거로 무엇도 허용하거나 거부하지 말라는 지시를 받습니다.
- 이 속성은 Moss에서 아무것도 허용하거나 막지 않습니다. 사용자가 할 수 있는 일은 고객의 앱이 계속 직접 통제해야 합니다.

제한은 토큰과 페이지의 속성을 합친 뒤에 적용됩니다.

| 항목 | 값 |
|------|-----|
| 키 | 최대 20개 |
| 키 길이 | 최대 100자 |
| 값의 형식 | 문자열, 숫자, 불리언, 또는 문자열 목록 |
| 문자열, 숫자, 불리언 값 | 최대 200자 |
| 목록 값 | 괄호와 따옴표를 포함해 전체 최대 500자 |

<Warning>
    객체가 아닌 `metadata` 클레임은 토큰을 무효로 만듭니다(`INVALID_TOKEN`). 제한을 넘는 속성이 있으면 채팅이 시작되지 않고(HTTP 422), 사용자에게는 연결 오류가 표시됩니다. 전체 이름, 이메일, 전화번호 같은 원시 개인정보 대신 짧은 역할과 범주를 쓰세요.
</Warning>

## 자주 묻는 질문

**SDK에서 토큰 대신 API 키를 쓸 수 있나요?**
아니요. 모든 SDK 요청에는 서버가 서명한 토큰이 필요합니다. Moss의 API 키는 [감사 로그](/ko/security/audit-logging)와 API 로그를 고객의 도구에서 읽는 읽기 전용 키뿐입니다.

**토큰 수명은 얼마로 해야 하나요?**
Moss는 최대 24시간까지 받습니다. 그 안에서 수명이 짧을수록 유출된 토큰을 쓸 수 있는 시간이 줄어들고, `getJwt`를 쓰면 SDK가 토큰마다 만료가 가까워질 때 새 토큰을 받아 옵니다. 수명이 60초보다 짧으면 SDK가 요청할 때마다 토큰을 받아 옵니다.

**`APP_MISMATCH` 오류는 왜 생기나요?**
`app` 클레임은 `kid`가 가리키는 키의 애플리케이션 ID와 같아야 하며, **구성 > 일반**에 표시된 그대로여야 합니다. 다른 애플리케이션의 키나 대소문자가 다른 ID는 일치하지 않습니다. 다른 Moss 배포에서 만든 키는 대신 `UNKNOWN_KEY`를 받습니다.

**사용자가 할 수 있는 일을 Moss가 알고 미리 말해 줄 수 있나요?**
네. [사용자 정보를 Moss에 알리기](#사용자-정보를-moss에-알리기)처럼 사용자의 역할이나 권한을 토큰의 `metadata`에 넣으세요. Moss는 이 정보를 답변을 다듬는 데만 쓰며, 아무것도 허용하거나 막지 않습니다.

**허용 도메인 목록이 애플리케이션 ID를 보호하나요?**
다른 웹사이트가 브라우저에서 어시스턴트를 쓰지 못하게 막을 뿐입니다. 브라우저 밖의 클라이언트는 막지 못하고, 목록이 비어 있으면 모든 페이지를 허용합니다. 애플리케이션을 보호하는 것은 서명된 토큰입니다.

**우리 앱에서는 여러 사람이 로그인 하나를 함께 씁니다. 문제가 되나요?**
네. Moss는 `sub`가 같은 사람을 모두 한 사용자로 봅니다. 요청 제한을 함께 쓰고, 서로의 채팅을 다시 열 수 있습니다. 가능하면 사람마다 다른 `sub`를 주세요.

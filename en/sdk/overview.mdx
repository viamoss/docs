# SDK Overview

The Moss SDK embeds the Moss assistant in your web app. It reads the page the user is on, sends their questions with that context to your Moss backend, and shows the answers in a chat panel. When an answer is a set of steps, it can highlight the elements to click, one step at a time.

## How It Works

When a user asks a question or takes a guide step, the SDK:

1. **Waits for the page to settle**, so it doesn't read a half-rendered screen. See [Stability Tuning](/en/sdk/advanced#stability-tuning).
2. **Reads the page:** its visible structure and text, with sensitive parts redacted. If vision is on and the user allows screen capture, it also takes a screenshot of what the user shares (normally this tab), which is not redacted. See [Page data and privacy controls](/en/sdk/page-data).
3. **Sends the question and the page to your Moss backend**, which answers from your knowledge base and the conversation so far.
4. **Shows the answer** in the chat panel, and highlights elements on the page when the answer is a guide.

The chat panel and guide UI render inside a [shadow DOM](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM), so your style rules don't reach them. Components you render inside `AgentProvider`, such as `AssistantButton`, render in your page as ordinary elements. See [Shadow DOM](/en/sdk/advanced#shadow-dom).

## Integration Methods

| Method | Best for | Install |
|--------|----------|---------|
| **npm package** | React apps | `npm install @viamoss/moss-sdk` |
| **CDN script tag** | Any web page | `<script src="…">` |

Both show the same chat panel and guides. They differ in what you control:

| | npm package | CDN script |
|---|---|---|
| Settings | Your `config` prop | The dashboard's, with `window.mossSettings` on top |
| Launcher | `AssistantButton`, `FloatingActionBar`, your own button, or none | `AssistantButton`, always |
| Programmatic control | `useAgent()` hook, `askMoss()`, `shouldStartMoss()` | `window.MossSDK.boot()`, `identify()`, `updateConfig()`, `shutdown()` |
| Native dialog support | `installModalDialogEscape()` | Not available |

Both work with `data-moss-trigger` elements. See [Installation](/en/sdk/installation).

## What Gets Read and Sent

With each question and guide step, the SDK sends your backend:

- **Page text:** the visible elements' structure, labels and text, with redaction applied.
- **The page URL**, including its query string.
- **A screenshot of what the user shares**, normally this tab, only if vision is on and the user allows the browser's screen-capture prompt. It is not redacted.
- **A short timeline of recent user actions**, only if you turn on screen history.

Session recording for replay in the dashboard is a separate feature, off by default. What the user types is sent as written.

[Page data and privacy controls](/en/sdk/page-data) describes each of these exactly, with every control: `data-moss-redact`, `redactAllInputs`, `redactionSelectors`, `pageContext` and the collection switches.

### What Page Text Leaves Out

- **Hidden elements**: `display: none`, `visibility: hidden`, `opacity: 0`, and anything inside an `inert` subtree. One exception: the text a visible element's `aria-describedby` points to is read even when it is hidden.
- **Values of native form fields** (`input`, `textarea`, `select` and editable regions), while `redactAllInputs` is on (the default). A custom control built from other elements, such as a dropdown made of `div`s, is read as ordinary text; mark it with `data-moss-redact`.
- **Closed shadow roots and cross-origin iframes**, which the browser keeps from the SDK.

These limits are for page text. Session recordings and screen history, if you turn them on, also capture hidden elements, except those you block or redact. A vision screenshot shows whatever the shared screen shows. See [Page data](/en/sdk/page-data).

**Your cookies and storage** are not read. The SDK keeps its own state under keys that start with `moss`. To choose its interface language it also checks the `lng` query parameter, an `i18next` cookie and an `i18nextLng` `sessionStorage` entry.

<Info>
    All requests go over HTTPS to the `apiUrl` you configure. From 0.17.0, with `streamActivity` on, turns are answered as Server-Sent Events from the same backend; proxies in between must pass them. Vision screenshots, and from 0.17.0 attachments, upload directly to your Moss deployment's file storage through signed URLs. The SDK uses no WebSockets.
</Info>

### What Is Stored in the Browser

The SDK keeps a small amount of its own state in browser storage so a conversation survives navigation and reloads:

| Storage | What it holds | Lifetime |
|---------|---------------|----------|
| `sessionStorage` | This tab's chat messages, whether the chat is open, the panel's position and size, a running guide, a question waiting from `askMoss()` | Until the tab closes |
| `localStorage` | The current session's ID and timing, recent session IDs, guides finished on this device, the interface language, and a guide step on its way to the next page | Until cleared |

Page text and screenshots are not written to browser storage. With `stability.afterReload` on, a guide step's report, including the clicked element's redacted markup, is kept in `localStorage` for up to `pendingTTL` (30 seconds by default) so the next page can send it. The CDN script also stores the user's ID as `moss_user_id`.

## What Moss Changes on Your Page

- **A host element.** The npm package renders a fixed-position `<div>` where `AgentProvider` sits; the CDN script appends `<div id="moss-sdk-root">` to `<body>`.
- **Its own attributes on interactive elements.** Each time it reads the page, the SDK marks the buttons, links and fields it found with `data-` attributes of its own, so it can refer to them. Treat them as internal: they change on every read.
- **Highlights during a guide.** The highlighted element gets an attribute that a `<style>` element the SDK adds to your `<head>` (and to the shadow root or same-origin frame that holds the element) outlines, and numbered badges are positioned over the page. The attribute and badges are removed when the step ends.
- **`data-moss-trigger` elements.** A click on one opens or closes the chat and calls `preventDefault()`, so a link with the attribute doesn't navigate. From 0.17.0, if your application shows support conversations in the Moss panel, unread replies add a count badge inside each trigger and a `data-moss-unread` attribute to it; see [Custom Triggers](/en/sdk/installation#custom-triggers).
- **`fetch` and `XMLHttpRequest`.** To tell when your page's requests have finished, the SDK wraps `window.fetch` and `XMLHttpRequest`'s `open` and `send` in your page, from when the provider mounts, and in same-origin frames. Requests pass through unchanged.
- **A web font link**, if your appearance sets `typography.fontFaceUrl`.
- **`window.name`.** When the chat opens in a window your page hasn't named, the SDK names it (`moss-tab-…`) to tell tabs apart. A name your page set is left as it is.

`pageSanitizationScript`, if you set it, also changes your page; see [Advanced](/en/sdk/advanced#programmatic-page-changes).

# Changelog

Notable customer-visible changes to the Moss SDK (`@viamoss/moss-sdk`) and the
Moss dashboard. From v0.13.0, the SDK version tracks the Moss platform version.

## 0.16.26 — 2026-11-18

SDK only: `@viamoss/moss-sdk` 0.16.26 is on npm. There are no new server
images or Helm chart. SDK 0.16.26 works with a 0.16.25 server, and hosted Moss
is unchanged.

### Fixed

- The Next button beside the chat input on guide steps is now as tall as the
  input and lines up with it. Before, it was slightly shorter and sat a few
  pixels lower than the input box.

## 0.16.24–0.16.25 — 2026-11-16

0.16.24 and 0.16.25 are described together. 0.16.24 wasn't published to npm
or rolled out to hosted Moss, so the SDK and hosted Moss go from 0.16.23
straight to 0.16.25. 0.16.24's self-hosted images and Helm chart were
published, but install 0.16.25 instead.

### Added

- **New appearance settings.** All of them are optional, and set under
  `appearance.chrome` in your integration's code; none is in the dashboard.
  Unset, nothing looks different.
  - `relatedArticles.variant`: `'list'` shows the related articles under an
    answer as plain rows, with titles in the primary text color, a small
    sentence-case "Related articles" label and a document icon in the primary
    color. `'cards'`, the default, keeps the bordered cards.
  - `guideOffer.label` and `guideOffer.icon`: the text and icon of the button
    that offers a guide. The icon is `'emoji'` (🚀, the default), `'outline'`
    (an outline rocket in the button's text color) or `'none'`.
  - `message.paragraphGap`: the space between paragraphs, lists and other
    blocks in an answer, as a CSS length. Unset, they sit directly on one
    another.
  - `startScreen.queryIcons`: your own icon for each built-in
    suggested-question icon name. Every question uses `document` unless
    `zeroState.suggestedQueryIcons` is `'per-query'`. A name without an entry
    keeps the built-in icon.
  - `startScreen.queryFontWeight`, `queryGap`, `articlesPaddingX` and
    `articlesRowGap`: the weight of the suggested questions and the gap
    between them, and the side padding of the recommended articles and the gap
    between their rows.
  - `inputBar.paddingY` and `inputBar.lineHeight`: the input text's top and
    bottom padding, and its line height as a number (`'1.5'`), a length
    (`'20px'`) or a percentage (`'150%'`).
  - `inputBar.focusBorder`: the input's border color while it has focus.
  - `icon` on the footer links: `'external-link'`, `'ticket'`, `'none'`, or
    your own element, such as an inline SVG. The Help center icon follows its
    label, and the Open a ticket icon precedes it. Unset, Help center keeps
    "↗" and Open a ticket has no icon.
  - `guide.pageTint`: dims the page around a guide's highlight. `true` lays a
    36% dark tint over it. An object sets `color`, `opacity` (0 to 1), or
    both. The chat never dims, clicks still reach the page, and an open modal
    dialog stays clear. The tint holds through step changes and lifts on a
    step with nothing highlighted. Off by default.
  - `guide.targetBadges`: `'step'` numbers the highlight's badge
    with the guide's step number, as in the guide bar. Every target of a step
    shows that same number, so several targets don't read as separate steps,
    and targets in one group, such as a row of tabs, share one badge.
    `'within-step'`, the default, keeps today's numbering.
  - `guide.nextInBar`: `false` moves Next from the guide bar to
    beside the input box. Next moves beside the input on every step, click
    steps included, and hides while Moss works and once the guide is finished.
    The guide bar then shows only the plan and its progress, and the chat's
    step loader shows that Moss is working. Unset or `true`, the default,
    keeps the guide bar's Next. With both
    `nextInBar` and `nextBesideInput` set to `false` there's no Next at all,
    and development builds warn in the console.
  - `loader`: `'steps'` shows a short list of what Moss is doing
    while it works, such as "Reading the page" and "Planning the next step".
    Screen readers hear the row in progress, except while the guide bar is
    already announcing "Working…". `'line'`, the default, keeps the one-line
    indicator.
- **Next beside the input box.** On a guide step with nothing to click, and on
  file-upload and confirmation steps, Next also shows beside the input box.
  Other click steps look the same as before, and it doesn't show once the
  guide is finished. The guide bar's Next stays. To keep Next only in the
  guide bar, set `chrome.guide.nextBesideInput: false`.
- **Self-hosted: Zendesk calls through a proxy.** A new backend setting,
  `ZENDESK_USE_ENV_PROXY`, is off by default. When it's on, Moss's Zendesk
  calls (connecting, syncing the ticket form and filing tickets) go through the
  `http://` proxy named in `HTTPS_PROXY`. A value without a scheme, such as
  `proxy.example.com:3128`, is read as `http://`, and `NO_PROXY` is honoured.
  An `https://` or malformed proxy value isn't used: the request isn't sent,
  and the sync banner or the connection check says this server couldn't reach
  Zendesk through the proxy. With the setting off, nothing changes.

### Changed

- **You can type while Moss answers.** The input stays editable during a
  reply. Send and Enter wait until the reply has arrived, and the text stays
  in the box. The input is disabled only while the connection is down.
- **Next sends what you typed.** With text in the input, a guide's Next sends
  it as your message. With an empty input, Next goes to the next step, as
  before.
- **No related articles while a guide runs.** Replies during a running guide
  don't show the related-articles list. The answer that offers the guide keeps
  it. Sources that your application's instructions ask for in the answer text
  are unchanged.
- **The guide bar shows when Moss is working.** While a request runs, a spinner and "Working…" take
  Next's place, and screen readers announce it. When the request ends, Next
  comes back, with the focus if it had it.
- **The guide offer's default label is "Start guide", and it's translated.**
  It was "Guide me", in English for every user. Korean users now see 가이드
  시작.
- **One line of input text is centred on the send button.** When
  `chrome.inputBar` is set, in code or in the dashboard, the send button sits a
  few pixels higher. With several lines, it stays level with the last one.
- **Zendesk connection errors name the cause.** With host-brokered filing,
  when **Test & connect** or **Test connection** can't read the end-user ticket
  form, the message now says why: the HTTP status, a DNS failure, a timeout, a
  TLS failure, a failed connection, or a reply that isn't a ticket form. A 404
  also asks you to check the subdomain. Zendesk's reply itself is never shown.
- **Zendesk sync errors name the cause too.** When a ticket-form sync fails,
  the "Last sync had a problem" banner, in Configure > Integrations > Zendesk
  and on the Ticket intake page, now says why: the HTTP status Zendesk
  answered, a DNS failure, a timeout, a TLS failure, a failed connection, or a
  reply that couldn't be read. It no longer shows text from Zendesk's reply.
- **Guide steps and guide offers.**
  - When a step only asks the user to check something, such as a setting or a
    status, and the page shows the check passing, Moss says so and gives the
    next step in the same reply. If the page shows something else, Moss says
    what it shows and stays on the step.
  - Choices on the page, such as radio buttons, selects and links, are
    highlighted, and the user's pick moves the guide on.
  - A step with nothing to click ends by pointing to Next, without saying
    where Next is on the screen.
  - Moss treats a "where is…" question as a how-to. When the answer lists
    several places in your application, Moss names the most common one and
    offers a guide there. Questions about places outside your application get
    no offer. The offer is the answer's last sentence, before any Sources list
    your instructions ask for.
- **Browser extensions send the SDK version they bundle, so they get the
  current guide behavior.** Extension builds sent no SDK version, so their
  sessions got the older guide behavior whatever the application's
  `stateless_turn_policy` setting said. Every extension built from this release
  sends it. Once its new build is installed:
  - Ending a guide in the chat ends it for Moss too, so the next question
    isn't answered inside the guide the user left. That covers closing the
    chat when `closingChatEndsGuide` is on, and filing a support ticket during
    a guide.
  - Asking Moss to stop ("stop guiding me", "exit the guide") ends the guide.
  - A guide with no progress ends on its own: after 2 hours if it was only
    offered, after 24 hours if it was running.
  - Moss decides on each question whether to answer it or guide, instead of
    keeping the mode an earlier question set.

  An extension switches only when its new build is installed. Pages that load
  a released SDK from npm or the CDN already had this behavior. An application
  with `stateless_turn_policy: false` keeps the older behavior.
- **SDK pre-releases get the current guide behavior.** A pre-release of any
  version after 0.10.0, such as `0.17.0-beta.3`, is now treated like a release.
  A page that loads one switches when the backend is upgraded, with no new
  install. Before, every pre-release got the older behavior. A pre-release of
  0.10.0 itself still does.
- **Several highlighted places are named, not numbered.** With
  `guide.targetBadges: 'step'`, every highlight of a step shows the step's
  number. When a guide step highlights more than one place, Moss's reply now
  names each one ("Click **Search** or **Share**") instead of numbering
  them 1, 2, 3. This needs the SDK from this release. It also covers the
  reply that starts a guide and highlights its first step.

- No database migrations in this release.

### Fixed

- **A guide's Exit button is back.** Open the guide bar's step list: "Exit
  guide" is at the end of it, and asks before it ends the guide. Exiting
  removes the guide's highlight, and Moss ends the guide too.
- After a guide's Exit, clicking the element its step highlighted no longer
  sends the step.
- After pressing Next, clicking the highlighted element no longer sends the
  step a second time. If Next's request fails, the step comes back, so Next
  can be pressed again.
- After exiting a guide with the keyboard, the focus stays in the message
  input.
- **The chat panel fits short browser windows.** In a window shorter than
  the panel, the panel opened with its header, and the New chat and Close
  buttons, off screen. It now fits inside the window, shrinking if it has
  to, and gets its full size back in a taller window. The same goes after a
  resize, after Reset Chat Position, and for a position saved on an earlier
  visit.
- **Screen readers name the chat header's buttons.** New chat and Close, and
  on the classic header Reset Chat Position and Change Language, now have
  names.
- **Screen readers hear once that Moss is working.** With the default
  loader, a running guide was announced twice, and nothing was announced
  while a request ran after a guide had finished. Each is now announced
  once, and the default loader no longer re-announces as its text animates.
- **Coming back to a session too old to resume.** The "Starting fresh" card
  no longer has a working indicator behind it, and nothing can be sent to
  the old session from behind the card.
- **One session per first open.** Loading a page or opening the chat for the
  first time starts at most one session. Before, it could start a second,
  empty one. The app's settings are also read once per page load, not twice.
- **Dashboard: long application names.** The desktop sidebar keeps its
  width, and at phone width the pages no longer scroll sideways.
- **`openChat` and `toggleChat` open the chat at the position you pass.**
  The position applies to that open only and isn't saved. If the user moves
  or resizes the chat during that open, their placement is kept.
- **Next stays available when a click step's setup gives up.** When a
  step's target couldn't be found, or Next or Exit was pressed while it was
  being set up, Next beside the input could stay hidden for the rest of the
  guide.
- Guides work on more pages whose forms have fields named after built-in
  page properties or methods, such as `submit`, `closest` or `matches`.
- **A request the model provider's safety filter blocks gets its own answer.**
  When a filter such as Model Armor or Gemini's safety settings blocks a
  request or its reply, Moss answers "A safety filter blocked this request, so
  I can't answer it. If it keeps happening on this page, please contact your
  administrator." It used to ask the user to rephrase. A blocked request counts
  as blocked, not as an error, and the session shows a blocked step.
- **SDK rate limits: an unreachable limit store is logged as an error.** With
  `SDK_RATE_LIMITS_ENABLED` on, a run of skipped checks is logged as an error
  whatever the cause. Before, only timeouts counted, so a store that refused
  connections was logged as a warning only.
- **Each question reaches Moss once.** With the conversation log that's the
  default since 0.16.1, every typed question went twice into the conversation
  Moss reads. So Moss took a conversation's first question for a later one and
  didn't work out the user's goal for the first answer, and a very short
  question searched the help articles with its words repeated. The first
  answer stays as fast as before, and Moss now works out the goal alongside it.
- **Clicking a guide's first step right after Moss offers it no longer ends
  the guide** with "I couldn't recover this guide."
- Pressing Next while a click step is still setting up now moves the guide on.
  Before, the press could be lost, and the guide bar kept showing "Working…".
- With `closingChatEndsGuide` on, closing the chat right after pressing Next or
  sending a message no longer leaves the chat busy when it's reopened.
- Guide highlights no longer fail on pages whose forms have fields named after
  built-in page properties.
- **Self-hosted: deleting a user's data and missing buckets.** A deletion is
  no longer certified complete when the user's files were stored in a bucket
  that the dashboard backend can't find. The certificate notes the missing
  bucket, and the request can be retried once the bucket is configured.
  - **Helm:** `global.storageBuckets.recordings` and `.screenshots` now set the
    bucket names for both backends. Rendering fails when the two backends name
    different buckets, so `helm template`, `install` and `upgrade` stop with a
    message that names the setting. Set each name to the bucket the install
    already uses; nothing moves.
  - **Upgrading with `--reuse-values`:** add
    `--set global.storageBuckets.recordings=rrweb-recordings`, or upgrade
    without `--reuse-values`. An install that never changed these names and
    upgrades without it needs no action.
  - **Known limit:** for an application that recorded sessions before 0.16.1
    and has since set session recording to anything but on, recordings from
    before 0.16.1 may not be checked.

### Security

- **Python, CVE-2026-119170 (High): fixed.** The backend and worker images
  require the Python 3.14.10 build that fixes it.
- **soupsieve 4.0** in the backend and worker, which fixes CVE-2026-126190
  and CVE-2026-126191 (High).
- **opentelemetry-api 1.45.2** in the backend and worker, which fixes
  CVE-2026-126360 (Medium).
- **URL rules:** page addresses are matched against URL rules with a length
  limit and a time limit, so an unusual address can't hold up the service.

### Known issues

- The 0.16.23 known issues still apply, except the one about a guide's Exit
  control and the note about a missing recordings or snapshots bucket, both
  fixed above.

## 0.16.23 — 2026-11-13

### Added

- **Closing the chat can end a running guide.** With
  `closingChatEndsGuide: true` in the SDK config, closing the chat while a
  guide runs ends the guide, as its Exit control does. The highlight comes
  off, and a page refresh brings nothing back. It applies to the close button,
  a `data-moss-trigger` toggle, `AssistantButton`, `closeChat()` and
  `toggleChat()`. A guide only offered, a guide already finished, a guide
  running in another tab and Moss's own closes are left alone. It is off by
  default, and nothing changes until you turn it on.
- New optional backend settings, all off or unchanged by default:
  - `SDK_REQUIRE_ORIGIN`: when on, SDK requests that carry no Origin or
    Referer, and every request for an application with no allowed domains,
    get 403 `ORIGIN_REQUIRED`. Leave it off unless every application has its
    list filled in.
  - `SDK_RATE_LIMITS_ENABLED`: per-minute limits on SDK session starts,
    queries, streams and recording uploads, kept in Redis. A slow or
    unreachable Redis lets requests through. Current SDKs don't wait out a
    429, so a limited request fails its turn.
  - `LLM_REQUEST_TIMEOUT_SECONDS` (default `45`): the first attempt's timeout
    for each model request in a chat turn.

### Changed

- **Allowed domains are checked by exact host, on every SDK request.** Check
  each application's list before you upgrade:
  - An entry matches only that exact host: `example.com` no longer matches
    `app.example.com`. For subdomains, add a `*.` entry such as
    `*.example.com`. A `*.` entry matches subdomains at any depth but not the
    bare domain, so list both if Moss runs on both.
  - The check covers every SDK request from the page, not only the first
    configuration load. A page the list doesn't cover gets 403
    `DOMAIN_NOT_ALLOWED`, and Moss doesn't load there.
  - An entry with a port matches only that port. Browsers leave out the
    default port, so an entry ending in `:443` never matches an https page.
  - `Origin: null`, which browsers send from sandboxed iframes and local
    files, is refused when the list isn't empty.
  - An empty list is unchanged.
- **Screenshot uploads need the user's token.** SDK 0.16.23 sends it. Older
  SDKs fall back to sending the screenshot inside the chat request, a few MB
  each, so check that your ingress accepts bodies that size on
  `/api/v1/query` until the SDK is upgraded. Upgrade the backend and
  dashboard first, then the SDK.
- **Saving a guide from the SDK needs the authoring grant.** Save as Guide in
  debug mode and in Moss Studio now needs a token with `authoring: true`, and
  saves only the token user's own session. An ordinary end-user token gets
  403, and the button says the user may not save guides. The dashboard's own
  save is unchanged.
- **A signed token with an empty subject is refused.** A JWT whose `sub` is
  empty, blank or not a string gets 401 `INVALID_TOKEN`, instead of running as
  the user named in the request. Tokens with a real subject are unaffected.
- **A model request that hangs ends sooner.** Each request a chat turn makes
  has a timeout, then one retry with what is left of the turn's 120 seconds.
  A hung request now ends at about 118 seconds with "I'm sorry, that took too
  long to answer. Please try again." instead of the high-traffic message. A
  slow but working request completes on its retry.
- **Deletion requests that fail are marked failed,** with details, instead of
  staying in progress, and can be retried.
- No database migrations in this release, and the Helm chart's values are
  unchanged.

### Fixed

- A native modal dialog opened with `showModal()` no longer turns the page
  grey under Moss when the page styles `::backdrop`, and the chat no longer
  inherits the dialog's text layout, so its messages wrap.
- A page whose form has a control named after a form property, such as
  `parentElement` or `id`, no longer hangs the tab or breaks page capture.
- Deleting a user's data now completes when their chats have analytics
  insights, evaluation scores, monitor flags, action logs, page snapshots or
  guides. It also removes their model-call logs and proactive-guide events.
- A rate-limited model request that the client gave up on is retried.

### Security

- **Redaction.** Redacted content no longer reaches Moss through a parent's
  text, accessible names and labels, interaction HTML, element fingerprints,
  the validation summary or a clicked element's text. This holds across open
  shadow roots and same-origin frames. Redacted alerts and fields are listed
  by tag only, so the summary still shows that they're there.
- **glibc, CVE-2026-84243 (High): fixed.** All four images ship glibc 2.44-r17,
  which includes the 2.44-r16 fix.
- **Python, CVE-2026-119170 (High): not affected.** It applies only when
  OpenSSL runs in FIPS mode, and no image installs a FIPS provider. Scanners
  may still report it.
- **Chrome for Testing 157.0.8103.78** in the worker, which fixes
  CVE-2026-125350 (High) and the advisories published on 11 November.
- Python dependency updates, and addresses containing a NUL character are
  refused before any lookup.
- The SDK package is published with an exact, integrity-checked npm.

### Known issues

- After a guide's own Exit control, a click on the step's target still sends
  the step. Closing the chat with `closingChatEndsGuide` on doesn't have this
  gap.
- Self-hosted: if `RECORDINGS_BUCKET` or `DOM_SNAPSHOTS_BUCKET` names a bucket
  that doesn't exist, the deletion certificate reports the erasure complete
  without the request's note about the missing bucket. Check that both name
  your real buckets. A fix is planned for 0.16.24.
- The 0.16.22 known issues still apply.

## 0.16.22 — 2026-11-10

### Added

- **Returning after inactivity.** Configure > Behavior > Session Behavior has
  a new field, "When a user returns after inactivity": "Ask to continue or
  start new" (the default, as before) or "Start a new chat". With "Start a new
  chat", a user who comes back to a session past its inactivity timeout (30
  minutes by default) or its max age (2 hours by default) gets a new chat, with
  no card and no rating. This applies when Moss loads into a timed-out session,
  and when the user reopens the chat on a page left open, with the launcher,
  `openChat()` or a `data-moss-trigger` element. The previous chat can't be
  reopened.
  - In the SDK, `sessionConfig.onReturnAfterInactivity` takes `'new_chat'` or
    `'ask'`. A value in your config wins. Left unset, the application's
    dashboard setting applies, delivered at session start by backend 0.16.22
    and later; without one, `'ask'`. For npm embeds, only this field comes
    from the dashboard: the inactivity timeout, max age and `showNotification`
    stay the ones in your config. A config built with `convertBackendConfig()`
    takes all four from the dashboard.
  - Update the backend and dashboard before the SDK. An older backend drops
    the setting on save without an error, and an older SDK ignores it. SDK
    0.16.22 on an older backend asks, unless your config sets the field.
  - Moss's own opens, such as `askMoss()` and proactive or onboarding flows,
    don't check. `openChat()` followed by `sendMessage()` sends the message in
    the new chat once it connects. Moss holds one such message, and logs a
    console warning when it can't send it.
  - Guide steps taken with the chat closed, and activity on the same session
    in another tab, count as activity. A guide idle past the timeout ends with
    its session; if it ran in this tab, `Moss Plan Finished` reports it with
    `outcome: 'abandoned'` under the old session's `sessionId`.
- **Moving the chat window.** The chat window also moves from the empty space
  in the conversation and around the message box, not only from its header and
  edges, so a window whose header is off screen can be dragged back. Messages,
  links, buttons, cards, the guide bar and the scrollbar don't drag, and a drag
  selects no text. On touch, the conversation scrolls, and the window moves
  from the header, the edges and the area around the message box.

### Changed

- **The worker refuses private addresses on its own fetches.** Image
  downloads, sitemaps, discovery's page sampling, and Document360 discovery and
  scraping now reach public addresses only. Check these before you upgrade:
  - **A forward proxy is no longer used for Document360, image and sitemap
    fetches.** These fetches connect directly and ignore `HTTP_PROXY` and
    `HTTPS_PROXY`, and there is no setting yet to send them through a proxy.
    If your worker's egress requires one, contact us before upgrading. Firecrawl,
    the LLM and embedding providers, Pinecone, storage uploads, Slack and the
    browser's page loads during discovery are unchanged.
  - Images and sitemaps on an intranet stop working until their host or range
    is listed in the new worker setting `WORKER_FETCH_ALLOWLIST`
    (comma-separated hosts and CIDRs, such as
    `wiki.corp.example.com,10.20.0.0/16`). It is empty by default.
  - `localhost` needs its own entry. Cloud metadata addresses can never be
    allowed. An invalid entry stops the worker at boot. Your object storage
    (`S3_ENDPOINT`) needs no entry.
  - A refused image is recorded as failed and keeps its original address. A
    discovery start URL on a refused host fails at once. A downloaded body that
    isn't an image is never stored.
- **Document360 API host.** It must be a Document360 host
  (`*.document360.io` or `*.document360.com`, such as `apihub.document360.io`).
  Any other host is refused when it's saved, and one saved earlier is refused
  at sync, with a message to enter it again. A help center on its own domain
  is fine, because that isn't the API host.
- **Zendesk subdomain.** It must be the account name only, such as `acme`, not
  a full address. Upper case is accepted and stored in lower case.
- **CSV exports** (conversations, traffic logs and the audit log). A cell that
  starts with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading
  apostrophe, so spreadsheets open it as text, never as a formula. That
  includes negative numbers: `-1` exports as `'-1`.
- **Slack alerts.** Alert text is escaped and length-limited. Worker job
  alerts carry the outcome, an error code and counts, but not the raw error
  text; the details stay in the job's record in Moss.
- New optional setting: `WORKER_FETCH_ALLOWLIST`, on the worker. In the Helm
  chart's `values.yaml`, only commented examples for it are added.
- **Support tickets during a guide.** While a ticket card is open, the guide
  bar is hidden. Cancelling the card brings the guide back on the same step.
  When the ticket is filed, or its outcome is unconfirmed, the guide ends and
  stays ended: `onEvent` reports `Moss Ticket Submitted`, then
  `Moss Plan Finished` with `outcome: 'abandoned'`. A ticket reported as failed
  leaves the guide running. A guide started after the ticket shows its bar as
  usual.
- **The ticket card opens on Moss's reply.** When Moss drafts a support ticket,
  the chat opens on Moss's message above the ticket form, not on the bottom of
  the form.
- **Rating after a filed ticket.** Once a support ticket is filed, "Was this
  conversation helpful?" appears at once, under the ticket confirmation, so the
  ticket number and its link stay in view. Answering it leaves the conversation
  as it is, and New chat doesn't ask again for that conversation. The next
  message or guide step removes it. It doesn't appear for a ticket that failed,
  came back unconfirmed or was cancelled. A rating that can't be sent brings
  the buttons back.
- **A guide step after a long pause.** When a user idles past the inactivity
  timeout mid-guide, then clicks a step's target that loads a new page, the new
  page keeps the session and continues the guide, with no card to continue or
  start new.
- **Saving session settings.** A configuration save merges `sessionConfig`
  with the stored settings: a save that sends only some session settings keeps
  the others, and a setting sent as `null` is cleared. A save with
  `sessionConfig: null` no longer clears them all.
- **Default loading-indicator selectors.** With the loading-indicators
  stability layer on and its default selectors, `skeleton`, `spinner` and
  `loader` classes match in any case.
- Every SDK change in this release works on any backend, except the dashboard
  setting for returning after inactivity, which needs backend 0.16.22.
- No database migrations in this release. The one new environment setting is
  the worker's optional `WORKER_FETCH_ALLOWLIST`, above.

### Fixed

- Moss no longer reads a page that is still drawing its loading placeholders.
  Before it sends a turn's page context, the SDK waits up to 4 seconds for
  visible placeholders, such as skeletons, to clear, so answers describe the
  loaded page instead of saying it is still loading. With none on screen there
  is no wait. Placeholders that never clear cost one wait, and are then skipped
  until they're gone or the page's address changes. The settings are under
  `stability.placeholderGuard` (`enabled`, `timeoutMs`, `excludeSelectors`,
  `additionalSelectors` and `selectors`). When you set
  `stability.loadingIndicators.selectors`, the wait uses that list.
- A turn that starts while an earlier one is still waiting for the page to
  settle now waits too. It could read the page with no wait.
- A guide step whose click opens a new tab, through a `target=_blank` link,
  `window.open()` or a link that redirects, brings the chat up in the new tab
  at the next step, and the step is sent once. A same-tab redirect, or a page
  that rewrites its address as it loads, no longer stalls the guide. Switching
  tabs right after a step's click no longer ends the guide. This fixes the
  0.16.21 known issue for a page whose address changes as it loads.

### Security

- Integration hosts for Document360 and Zendesk are now validated, and CSV
  exports open safely in spreadsheets.
- Alerts and audit records are hardened against untrusted input.
- **Worker fetches of private addresses (High).** A crawled page could point
  an image or sitemap link at an internal address, and the worker would fetch
  it. The worker now refuses private, loopback, link-local and metadata
  addresses on its own fetches, and stores only bodies that are images.
- The images are rebuilt on current base-image packages, with no dependency
  changes.

### Known issues

- Some valid images are refused and keep their original address: a UTF-16
  SVG, an SVG that ends in a comment containing `</svg>`, an AVIF or HEIC whose
  last box has size 0, and an SVG with a prefixed DOCTYPE name.
- The 0.16.21 known issues for a guide whose starting answer is lost, in one
  tab or with a second tab, still apply, as do the other two 0.16.20 known
  issues for guides in more than one tab.
- "Retry failed pages" counts and retries only pages that couldn't be fetched.
  To run pages that failed indexing again, refresh the source or edit the page.
- With "Start a new chat", a chat left open while the user is away keeps its
  conversation: Moss checks only as it loads and as the chat opens. Calling
  `openChat()` and then `askMoss()` in one handler, past the timeout, starts
  one extra session that is never used.
- If the page reloads mid-guide while a ticket card is open, the step's
  highlight comes back with the guide bar hidden, and a click on it completes
  the step. When a ticket is filed in a tab that only shows the guide, the tab
  running it reports `Moss Plan Finished` but keeps the guide bar until a later

## 0.16.20 — 2026-11-04

### Added

- **Pinecone private endpoint (AWS PrivateLink).** With
  `PINECONE_USE_PRIVATE_ENDPOINT=true` (off by default), sdk-backend,
  dashboard-backend and the worker still look the index up on
  `api.pinecone.io`, then send all data-plane traffic (search, fetch, upsert
  and delete) to the index's private host,
  `<index>.svc.private.<...>.pinecone.io`, which Moss reads from the index
  description; there is no host to configure. `api.pinecone.io` must stay
  reachable from all three workloads.
  - There is no fallback to the public host. If the index's Pinecone project
    has no private endpoint, Moss doesn't connect to the index: chats answer
    without the application's knowledge base, deleting a source fails, and
    chunking jobs fail before they touch a source's pages or vectors. Each
    logs an error that names the index and the setting.
  - Set it on all three workloads, with the upper-case name and the same
    value. `true`, `t`, `yes`, `y`, `on` and `1` turn it on, in any case;
    `false`, `f`, `no`, `n`, `off` and `0` leave it off. Any other value,
    including an empty one or one with surrounding spaces or quotes, stops the
    backends from starting and fails every chunking job.
  - Each process logs `Pinecone data-plane host: private` (or `public`) the
    first time it opens the index. The line shows the host Moss picked, not
    that it is reachable.
  - Before turning on Pinecone's private-endpoint-only restriction for the
    project, check that Pinecone answers through the private host, since a
    wrong DNS record or security group still logs `private`. On sdk-backend,
    one chat turn that uses the knowledge base logs the `private` line, then
    `Pinecone multi-namespace search completed` with `results=N/M` and N above
    0, and no `search failed`. On the worker, one knowledge-source refresh logs
    the `private` line and the source ends Ready with more than 0 chunks. On
    dashboard-backend, which may not log the line for a while, confirm the
    variable is set on its deployment. With the restriction on, Pinecone
    rejects data-plane requests that don't come through the endpoint, so a
    workload still on the public host loses retrieval or indexing.

## 0.16.6 — 2026-09-05

### Added

- **Application export and import.** Admins can export a versioned bundle
  from Configure > General and import one from the application list through
  an Import dialog. The bundle covers the authored application alongside its
  configuration: procedures, API connections and actions, integration
  connections, monitors, intent tags, and the self-healing schedule.
  Credentials are never included and are re-entered on the target.
  Integration connections in direct-filing mode are reported for completion
  rather than created. Import runs in one transaction, and the dry-run report
  lists what would be created, remapped identifiers, every value written
  differently from the bundle, and a re-entry checklist. The dashboard export
  produces the full bundle by default, and the configuration-only bundle
  remains available. Guidance flows are not part of the bundle. The endpoints
  are `GET /api/v1/applications/{id}/export` and
  `POST /api/v1/applications/import?dry_run=true`.
- **Dashboard-managed appearance controls (first pass).** A new theme slice
  and a footer background tint can be edited from the dashboard. The SDK
  applies dashboard-saved values over the host prop per leaf, so precedence
  is preset, then host prop, then dashboard value. Hosts must upgrade the SDK
  to 0.16.6 to see dashboard theme values.
- The SDK chat window can now be dragged from the full header and from the
  window edges.
- Dashboard toasts have a dismiss button, and error toasts stay until
  dismissed.

### Changed

- Clearing the last leaf of a configuration slice now removes the slice
  instead of storing an empty object.
- The SDK package no longer ships sourcemaps in the tarball and now carries a
  public README and package metadata.
- Upgrade order for split deployments: backend, then dashboard, then SDK.
- The application prune script now covers every application-owned table,
  removes stored DOM snapshot objects, resolves tables through the configured
  database schema, and refuses to run when it detects cross-application
  references or cannot count a table.
- No database migrations in this release.

### Known issues

- For a stored footer that contains only links, the public configuration
  endpoint reports `enabled: false`.
- Importing into an organization whose install already holds an application
  with the same name is refused. Application names are currently unique per
  install.

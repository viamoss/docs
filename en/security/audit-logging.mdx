## Overview

Moss records audit events and supports optional detailed request logging for compliance and security investigations.

---

## What Gets Logged

The tables below describe detailed request logs when enabled.

### Inbound Requests (SDK to Backend)

| Field | Description |
|-------|-------------|
| Timestamp | When the request was received |
| Application ID | Which application made the request |
| User ID | The authenticated user |
| Session ID | Associated chat session |
| Endpoint | API endpoint called |
| Request payload | Sanitized request body |
| Response status | HTTP status code |
| Duration | Request processing time |

### Outbound Requests (Backend to External Services)

| Field | Description |
|-------|-------------|
| Timestamp | When the request was made |
| Target service | LLM provider, embedding API, storage |
| Provider | Specific provider (OpenAI, Google, etc.) |
| Model | Model used for the request |
| Request summary | Sanitized request details |
| Response status | Success/failure |
| Token counts | For LLM requests |

## Sensitive Data Redaction

The request-log sanitizer redacts the following credential fields before storage:

### Redacted Fields

The following fields are automatically redacted:

- `api_key`, `apiKey`
- `authorization`
- `password`
- `secret`
- `token`
- `x-api-key`

### Redaction Example

```json
// Original request
{
  "headers": {
    "authorization": "Bearer eyJhbG...",
    "x-api-key": "app_abc123"
  },
  "body": {
    "query": "How do I reset my password?"
  }
}

// Logged (sanitized)
{
  "headers": {
    "authorization": "[REDACTED]",
    "x-api-key": "[REDACTED]"
  },
  "body": {
    "query": "How do I reset my password?"
  }
}
```

<Info>
    Credential redaction is recursive. It does not anonymize personal data or
    remove arbitrary sensitive content from free text. Keep such content out of
    logs where your agreement prohibits it; enable payload logging only for an
    appropriate, documented scope. Detailed logging covers instrumented paths,
    rather than a guaranteed record of every network call.
</Info>

## Per-Application Control

Detailed request logging can be enabled or disabled per application:

This setting controls detailed request logs, separately from administrative audit events.

### Dashboard Configuration

Navigate to **Settings > Developer Options > Audit Logging** to enable or disable logging for your application.

### Considerations

| Detailed Request Logging | Use Case |
|---------------|----------|
| **Enabled** | Compliance requirements, security-sensitive applications |
| **Disabled** | High-volume applications where storage costs are a concern |

<Tip>
    Enable detailed request logging when needed.
</Tip>

## Accessing Audit Logs

### Dashboard Access

View audit logs in the Dashboard under **Configure > Audit Log**.

Features:
- Filter by date range
- Filter by user or session
- Filter by endpoint or status
- Export to CSV

### API Access

Query audit logs programmatically using the Audit API:

```bash
# List audit events for an application
curl -X GET "https://moss-api.viamoss.ai/api/v1/applications/YOUR_APP_ID/audit-events?start_date=2024-01-01&end_date=2024-01-31" \
  -H "X-Audit-API-Key: YOUR_AUDIT_API_KEY"

# Export the same events as JSON or CSV
curl -X GET "https://moss-api.viamoss.ai/api/v1/applications/YOUR_APP_ID/audit-events/export?format=csv" \
  -H "X-Audit-API-Key: YOUR_AUDIT_API_KEY"
```

Results are paginated with `page` and `page_size`, and can be narrowed with `actor_id`, `action`, `target_type`, `outcome`, `start_date`, and `end_date`.

### Audit API Key

A separate API key is used for audit log access:

- **Isolated Access** - Audit key is separate from SDK API key
- **Read-Only** - Cannot modify logs or other data
- **Revocable** - Can be revoked independently

## Log Retention

| Record type | Default in the backend | Application of the period |
|-------------|------------------------|---------------------------|
| Optional detailed API request logs | 90 days | Per-application window; disabling collection does not erase existing records |
| Administrative/security audit events | 365 days | Operator-managed; customer-controlled records follow their documented instructions |

Applicable agreements, documented customer instructions, and lawful preservation
requirements determine the deployed schedule. A required minimum must be
reconciled with an expiry period before deletion. Confirm the active schedule
for your deployment with Moss. These defaults do not establish that a particular
deployment has run its cleanup successfully.

Billing records and deletion evidence are separate record classes; there is no
general seven-year rule for every audit or customer log.

## Use Cases

### Compliance Reporting

Generate reports for auditors:

1. Filter logs by date range
2. Export to CSV
3. Include in compliance documentation

### Security Investigation

Investigate suspicious activity:

1. Identify the user or session
2. Review all related requests
3. Check for anomalous patterns
4. Export evidence for incident response

### Performance Analysis

Analyze API usage patterns:

1. Review request durations
2. Identify slow endpoints
3. Track LLM token usage
4. Optimize based on data

### Cost Analysis

Track LLM usage costs:

1. Review token counts per model
2. Identify high-usage sessions
3. Optimize prompts and context

## Log Integrity

### Append-Only Audit Events

- Application users cannot edit or delete existing audit events through the dashboard or Audit API.
- The retention process removes expired audit events.

### Timestamps

Audit-event timestamps are generated by the server in UTC.

---

## Best Practices

### Enable for Production

Configure production audit and request logging to:

- Meet compliance requirements
- Enable incident investigation
- Track usage patterns

### Regular Review

Periodically review audit logs for:

- Unusual access patterns
- Access changes and recorded security events
- Unexpected API usage

### Secure API Keys

Protect your Audit API key:

- Store securely (not in code)
- Rotate periodically
- Monitor for unauthorized use
